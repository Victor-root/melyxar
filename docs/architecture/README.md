Ce dossier est la mémoire du projet. Il contient les revues d'architecture réalisées avant la première ligne de code, et les décisions actées. Tout ce qui est décidé ici doit être respecté par le code, et toute nouvelle décision doit y être ajoutée.

## Décisions actées

Ces décisions ont été prises après discussion et ne sont pas à rediscuter sans raison nouvelle.

| Décision | Choix | Pourquoi |
|---|---|---|
| Langage serveur | Rust, Tokio, Axum | Superviseur de processus, faible consommation, binaire unique. |
| Base de données | **SQLite** (mode WAL, une seule connexion d'écriture, transactions courtes) | Un seul binaire, sauvegarde par copie de fichier, plus rapide qu'un aller-retour réseau pour ce type d'usage, Emby et Plex prouvent l'échelle. PostgreSQL écarté définitivement. |
| Accès base | SQLx, SQL uniquement dans la crate `database`. **Requêtes vérifiées par des tests d'intégration sur une base réelle plutôt que par les macros à la compilation** | Décision révisée au moment d'écrire le code. Les macros imposeraient de régénérer et commiter des métadonnées à chaque changement de requête, une étape de plus qui peut casser la compilation dans le LXC. Chaque requête est exécutée par un test contre une base migrée, ce qui attrape la même classe d'erreur sans cette fragilité. Règle qui en découle : **toute requête doit être couverte par un test**. |
| FFmpeg | Programme externe, jamais les bibliothèques `libav*`, chemin configurable, une seule crate `ffmpeg` lance des binaires | Robustesse, mise à jour indépendante, accélération matérielle simple. |
| Streaming | HLS en fragments fMP4, playlist générée par le serveur, segments à la demande | Seeking instantané, un seul pipeline pour remux et transcodage. |
| Client web | React, TypeScript, Vite, hls.js, client TypeScript généré depuis la spécification OpenAPI | Écosystème d'interface le plus riche ; le frontend ne connaît que l'API. |
| Structure | Monolithe modulaire, workspace Cargo, direction unique des dépendances | Frontières imposées par le compilateur. |
| Modèle de données | Œuvre, source média et piste sont trois entités distinctes ; identifiants internes UUID v7 ; identifiants externes dans une table à part ; chemins relatifs à une racine ; millisecondes et UTC partout | Remplacer un fichier ne doit jamais effacer l'historique. |
| Les instants en base ont une largeur fixe | **Un instant est écrit en base toujours avec ses neuf chiffres après la seconde, zéros compris** (`2026-09-24T16:32:01.510000000Z`). Une migration a réécrit sous cette forme ceux déjà enregistrés. Ce qui part vers l'interface garde la forme courte habituelle | La base compare les instants comme du texte. Sous la forme courte, les zéros de fin sont retirés : `01.51Z` venait après `01.515Z` alors que c'est l'inverse, et la cloche pouvait oublier une connexion refusée tombée juste après un instant rond. À largeur fixe, l'ordre du texte est celui du temps. |
| Modèle multi-domaines | La bibliothèque a un type explicite (films, séries, musique) ; le tronc commun (source, piste, progression, favoris, images) est séparé des métadonnées propres à chaque domaine | La musique est prévue à terme ; un schéma qui suppose « un film » imposerait une refonte. |
| Sonie audio | Colonnes EBU R128 sur les pistes audio dès la première migration, mesurées au scan, appliquées au gain à la lecture | Sans la colonne, toute la bibliothèque devrait être réanalysée plus tard. |
| Repliement stéréo | Plusieurs méthodes proposées, celle du standard industriel par défaut, plus un gain de compensation suivi d'une limitation pour éviter la saturation. Préférence par utilisateur avec valeur par défaut du serveur. Méthodes définies comme préréglages de filtre dans la crate des commandes | Sans repliement soigné, dialogues inaudibles et effets assourdissants, le défaut le plus courant des serveurs multimédias. |
| Repliement et décision | **Une préférence de repliement force le transcodage audio** et devient donc une entrée du moteur de décision, exposée dans ses raisons. L'interface précise que le réglage ne s'applique pas en lecture directe | Sans cela, le réglage semble sans effet sur les fichiers lus directement, ce qui est pire qu'un réglage absent. |
| Progression | État explicite (non commencé, en cours, vu), date de lecture, marquage manuel prioritaire, position horodatée jamais écrasée par une plus ancienne, copie locale côté client | Déduire « vu » d'un pourcentage empêche le marquage manuel ; sans horodatage, la reprise peut reculer. |
| Compteurs | Nombre d'épisodes et d'épisodes non vus stockés par utilisateur et par saison ou série, mis à jour à l'écriture | Les compter à la lecture ruine la réactivité. |
| Personnalisation | Paramètres du serveur (nom, logo, fonds, CSS global) et préférences utilisateur (thème, couleur, langue, volume, CSS personnel) dans des tables dédiées ; fichiers envoyés dans les données ; route publique d'identité visuelle sans divulgation | La page de connexion doit afficher le logo avant toute authentification. |
| Thème | Aucune couleur, aucun espacement, aucun rayon en dur dans le frontend : tout par jetons. Modes clair, sombre et automatique. CSS personnalisé désactivable avec adresse de secours | Ajouter un thème après coup oblige à repasser sur chaque composant ; un CSS cassé ne doit jamais bloquer l'accès. |
| Erreurs de l'API | Code d'erreur et données structurées, jamais de phrase toute faite | Sans cela, les clients ne peuvent pas traduire les messages. |
| Chiffrement | Le serveur sait servir en HTTPS lui-même ; quatre options proposées (reverse proxy, auto-signé, certificat fourni, certificat reconnu par nom de domaine) avec leurs limites annoncées honnêtement | Un certificat auto-signé ne supprime pas l'avertissement du navigateur ; le promettre serait mentir. |
| Clients natifs | Un seul projet Android, base commune (API, session, cache, lecteur), interfaces séparées, télévision d'abord | Deux applications distinctes coûtent cher en doublons ; une interface unique est médiocre partout. |
| Personnes | Table des personnes unique et table de participation (rôle, personnage, ordre) | Sans identité unique, la filmographie d'un acteur est impossible. |
| Collections | Une seule table pour les sagas automatiques et manuelles, avec l'origine indiquée | Sinon un rafraîchissement des métadonnées efface les collections créées à la main. |
| Droits par utilisateur | Accès par bibliothèque, limite d'âge, téléchargement, suppression, sessions simultanées | Chaque fonction sensible s'y rattache ; les ajouter après multiplie les migrations. |
| Images extraites d'un fichier | Toujours converties en SDR quand la source est HDR, par défaut | Sans conversion, les vignettes d'un film HDR sont délavées et grisâtres. |
| Aperçu de la barre de lecture | **Indispensable, demandé explicitement par le mainteneur.** Vignettes regroupées en planches, intervalle et résolution configurables, activable par bibliothèque. Les miniatures qui défilent au survol de la barre, comme chez Emby | Des fichiers individuels donneraient des centaines de milliers de petits fichiers. À ne pas confondre avec le relevé des images clés, qui passe au même moment dans l'analyse et ne produit aucune image : l'un sert à voir où on va, l'autre à y arriver. |
| Segments repérés | Table des segments (récapitulatif, générique de début, générique de fin) sur la source média | Base du saut d'intro et du bouton « épisode suivant ». |
| Suppression sur disque | Jamais de chemin venant du client, chemin résolu et vérifié sous une racine déclarée, case décochée par défaut, droit d'administrateur, entrée au journal | C'est l'opération la plus dangereuse du projet. |
| Métadonnées multilingues | Textes stockés par langue dans une table de traductions, français prioritaire, repli anglais | Des colonnes de texte sur l'œuvre interdiraient le repli et le changement de langue. |
| Versions multiples | Sélecteur de version sur la fiche, décrit par résolution, codec, pistes et taille. Version par défaut choisie par résolution puis débit, jamais selon la connexion. Choix valable pour la session seulement. Progression attachée à l'œuvre, pas à la version | Le mainteneur aura plusieurs copies d'un même film pour ses tests et doit pouvoir passer de l'une à l'autre. |
| Identité visuelle | Rouge `#c81e1e` en **remplissage** (bouton de lecture, barre de défilement, éléments actifs) avec texte blanc dessus, même valeur en thème clair et sombre. Variante éclaircie réservée aux liens et petits textes colorés sur fond sombre. Couleur de thème du script d'installation | Mesuré : blanc sur ce rouge donne 5,7 pour 1 ; le même rouge en texte fin sur fond sombre ne donne que 3,2. |
| Noms de fichiers du mainteneur | Jamais dans le dépôt : ni code, ni tests, ni documentation, ni message de commit. Les tests utilisent des titres inventés couvrant les mêmes formes. **Une exception, demandée par le mainteneur** : le jeu d'essai de la lecture des noms est bâti sur des titres de films réels, lus dans un catalogue public | Demande explicite du mainteneur, dans les deux sens. Un titre inventé a toujours la forme que son inventeur avait en tête, et c'est précisément ce qui laissait passer des cas : un titre qui n'est qu'une année, un titre portant une année, un titre entre parenthèses, un titre qui se termine par un mot pris pour une étiquette technique. Ces titres-là ne viennent d'aucun disque : ils sont publics, et aucun nom de fichier du mainteneur n'entre pour autant dans le dépôt. |
| Analyse des noms | Découpage sur la dernière année plausible, tout ce qui suit est écarté du titre, soulignement traité comme séparateur, casse et accents normalisés, étiquettes exploitées mais jamais opposables à l'analyse du fichier | Les fichiers sont posés à plat, sans dossier par film : le nom est la seule source. |
| Choix des pistes | Version, piste audio et piste de sous-titres se choisissent **sur la fiche**, avant le lancement. La décision de lecture n'est calculée qu'au moment du lancement | Évite de démarrer un transcodage pour rien avant de changer d'avis. |
| Image de titre | Type d'image distinct de l'affiche et du fond, récupéré et stocké comme tel | Le bandeau de la fiche affiche le titre sous forme d'image. |
| Champs techniques | Analyse du fichier stockée au niveau de détail attendu par la fiche, couleurs comprises (primaires, espace, courbe de transfert, profondeur) | Ces champs commandent la décision de conversion en SDR, ils ne sont pas décoratifs. |
| Chemin et taille du fichier | Visibles par l'administrateur seulement, contrairement à Emby qui les montre à tous | Ce sont des informations sur le serveur, pas sur le film. |
| État sur les cartes | Pastille de vu en coin de carte, dans les rangées comme dans les grilles | Relevé sur la référence, utile partout. |
| Textes qui peuvent déborder | Aucune hauteur fixe : le bloc occupe la place disponible, le texte la remplit, et le lien de dépliage n'apparaît que si le texte déborde vraiment | Emby coupe à hauteur fixe et laisse un vide quand le texte est court. Défaut à ne pas reproduire. |
| Emploi de l'accentuation | Nettement plus présente que chez Emby, mais réservée à ce qui est actif, sélectionné, en progression ou actionnable en premier. Neutre pour le texte courant, les grandes surfaces et les bordures ordinaires. Chaque emploi est un rôle nommé dans les jetons | Emby sous-emploie sa couleur ; étalée partout, elle ne signalerait plus rien. |
| Interface mobile | L'interface web doit être utilisable depuis le navigateur d'un téléphone | Presque gratuit si prévu au premier écran, coûteux ensuite. Le préchargement au survol n'existe pas au doigt : préchargement à l'apparition de la vignette. |
| Clavier | Vrais boutons et vrais liens, ordre de tabulation, contour visible, **et gestionnaire de focus directionnel écrit en même temps que la première grille** | Greffé après coup sur des grilles existantes, il coûte plusieurs fois plus cher. Prépare le client télévision. |
| Installation | Script shell unique reprenant les conventions du dépôt `Proxmox-Tools` du mainteneur : bilingue intégré, couleurs 256 niveaux désactivables, bannière, indicateur animé, encadrés, menu numéroté, sauvegarde avant modification, aucune dépendance | C'est la signature du mainteneur sur tous ses dépôts. |
| Publication | Une étiquette de version GitHub par version ; le serveur signale l'existence d'une version plus récente, sans jamais se mettre à jour seul ; vérification désactivable | L'administrateur décide du moment de la mise à jour. |
| Temps réel | Un seul flux permanent par client connecté, transportant des événements typés et légers (bibliothèque modifiée, tâches, sessions, maintenance). Le client agit toujours par les routes ordinaires | Commencer par de l'interrogation en boucle imposerait de réécrire la couche de données du client. |
| Fichiers d'accompagnement | Par défaut tout sur le disque système, rien à côté des médias. **Écriture et lecture des fichiers d'accompagnement proposées en option**, désactivées par défaut. Quand l'écriture est activée : droit vérifié d'abord, écriture en tâche de fond, et la base reste la source de vérité | Le défaut permet des disques en lecture seule et une sauvegarde complète du seul serveur ; l'option sert à ceux qui veulent une bibliothèque autonome. |
| Droits sur les racines | Quatre états distingués (introuvable, illisible, lecture seule, lecture et écriture), établis par un **test réel d'accès** et non par lecture des droits affichés. Visibles dans l'assistant, l'administration, le tableau de bord et la commande de diagnostic. Une fonction exigeant l'écriture est désactivée avec sa raison plutôt que de tomber en panne | Jellyfin et Emby laissent dans le flou et le problème se découvre au pire moment. Les droits affichés mentent dès qu'il y a groupes, montages réseau ou conteneur non privilégié. |
| Port | 2100, vérifié dans le registre officiel : attribution historique sans usage réel. Seul conflit réaliste, le service FTP du module XML d'Oracle Database, hors de propos ici. Modifiable en configuration, et le script vérifie qu'il est libre à l'installation | Choisi sur vérification, pas de mémoire. |
| Fichiers non identifiés | Visibles dans la bibliothèque avec le repère « à identifier », plus une liste dédiée côté administration | Un fichier mis de côté invisible est un fichier oublié. |
| Fournisseur injoignable | Le scan ne s'arrête jamais : fichiers enregistrés et analysés, identification mise en attente, réessais espacés | Impose que l'identification soit une étape séparée du scan, rejouable seule. |
| Sessions | Un jeton par appareil, de longue durée, révocable individuellement, avec la liste des appareils et leur dernière activité | Pas de reconnexion permanente sur la télévision, et reprise de contrôle possible si un appareil est perdu. |
| **Connexion dans le navigateur** | **Cookie** fermé aux scripts, limité à ce site, et marqué comme exigeant une connexion chiffrée seulement quand le serveur en sert une. Le jeton d'appareil reste prévu pour les futurs clients natifs, et mène au même compte | Décision révisée : la revue disait « jetons plutôt que cookies », en pensant aux clients natifs. Dans un navigateur c'est le mauvais choix. Un jeton rangé dans le stockage du navigateur est lisible par n'importe quel script arrivé sur la page, un CSS personnel ou une extension comprise, et il faut l'accrocher à la main à chaque requête. Un cookie fermé aux scripts n'est ni l'un ni l'autre, et il part tout seul avec les images et les segments de film, qui sont l'essentiel de ce que ce serveur sert. Exiger le chiffrement par défaut rendrait la connexion impossible sur un serveur atteint en clair sur un réseau local, qui est la façon dont ils commencent tous. |
| **Une session est un appareil** | Une ligne de la table des appareils, sans date de fin : elle vit tant qu'elle sert. Son âge ne la fait jamais refuser : au bout d'un an sans usage, le balayage quotidien la supprime (voir « Rien ne refuse un jeton pour son âge »). Son dernier usage n'est réécrit qu'une fois périmé, au plus une fois par heure et par appareil | Un navigateur connecté est un appareil, exactement comme une télévision : deux tables voudraient dire écrire deux fois la révocation, le balayage et la liste. Sans le délai de réécriture, un film regardé demanderait une écriture par segment derrière chaque scan, sur l'unique connexion d'écriture. |
| **Le jeton n'est jamais stocké** | Seule son empreinte est écrite à côté de la session, et la session est *retrouvée* par cette empreinte | Une copie de la base ne donne la session de personne. Et retrouver par index plutôt que comparer, c'est une comparaison de moins qui pourrait trahir sa réponse par le temps qu'elle met. |
| **Fermé sauf mention contraire** | Quatre adresses répondent sans compte : la santé du serveur, le nom et la marque pour la page de connexion, se connecter, créer le premier compte. Tout le reste exige un compte, images et segments de film compris | Une route ajoutée demain et non réfléchie est une route que personne ne peut atteindre, ce qui est le bon sens. Dans l'autre sens, une route ajoutée à la hâte est une route ouverte et rien ne le dit. |
| **Ce qu'une requête demande** | Un gestionnaire déclare ce dont il a besoin : le compte, ou le compte et les droits d'administrateur. Le compilateur refuse qu'il lise un compte qu'il n'a pas demandé | Un contrôle qu'on peut oublier d'écrire est un contrôle qu'on oublie d'écrire. |
| **Réservé à l'administrateur** | Le journal, le rapport de diagnostic, l'explorateur de dossiers du disque, les travaux de fond et toute la gestion des médiathèques | Tous nomment de vrais fichiers sur un vrai disque, avec leur chemin complet. Ce sont des informations sur le serveur, pas sur les films. |
| **Frein sur les mots de passe** | Dix essais ratés d'affilée sur un compte le mettent en pause une minute, et de nouveau à chaque nouvelle série. Seuls les comptes qui existent sont comptés | Deux raisons. Deviner doit coûter du temps plutôt qu'une poignée d'essais ; et vérifier un mot de passe est volontairement coûteux en calcul et en mémoire, donc mille essais par seconde reviendraient à demander au serveur de s'étrangler lui-même. En pause, aucun n'est vérifié. Ne compter que les comptes existants borne la mémoire : un nom qui n'existe pas est refusé avant tout calcul. |
| **Aucun premier compte imposé** | Un serveur neuf n'a aucun compte. La première chose qu'il propose est d'en créer un, et cette porte se referme derrière elle. Le nom est choisi par la personne | Le compte `admin` sans mot de passe créé au démarrage était un compte à expliquer et le même sur chaque installation du monde. Et la porte doit se fermer : sinon la deuxième personne à atteindre un serveur neuf se fait administrateur dessus. |
| **Un refus ne dit pas ce qui existe** | Une médiathèque qu'un compte n'a pas reçue répond comme une médiathèque qui n'existe pas, jamais comme une qu'il n'a pas le droit de voir. Idem pour une œuvre | Distingués, un compte restreint pourrait demander un identifiant après l'autre et apprendre ce que le serveur contient, ce qui est précisément ce qu'on lui cache. |
| **Les médiathèques autorisées, dites à voix haute** | Une colonne dit si un compte voit toutes les médiathèques ; sinon il voit celles qu'on lui a données, et rien, y compris rien du tout | Lu depuis l'absence de lignes, un compte à qui on avait donné une médiathèque, puis dont la médiathèque était retirée, se mettait à tout voir sans que personne soit prévenu : l'autorisation part avec la médiathèque qu'elle nomme. |
| **Couleur d'accentuation** | Un dièse et six chiffres hexadécimaux, ou refusé. Une couleur déjà enregistrée qui n'en est pas une retombe sur le rouge par défaut | C'est la seule valeur choisie par une personne qui finit dans une feuille de style. Plus large, ce serait un moyen d'y écrire n'importe quoi. Retomber plutôt qu'échouer à la lecture : un compte qui ne se charge pas enferme son propriétaire dehors, ce qui est bien pire qu'une préférence remise à zéro. |
| **Les images restent ouvertes à tout compte connecté** | Une affiche est servie à qui est connecté, sans regarder de quelle médiathèque elle vient | Une adresse d'image ne dit pas à quelle médiathèque elle appartient : la filtrer voudrait dire une recherche par image, sur le chemin le plus chaud du serveur, pour cacher une affiche à quelqu'un qui ne peut de toute façon pas la trouver (le nom porte une empreinte du contenu et n'apparaît sur aucun écran qu'il peut ouvrir). Écrit ici pour que ce soit un choix et non un oubli. |
| **Le premier compte ne peut être créé qu'une fois** | Le regard et l'écriture dans une seule transaction, sur l'unique connexion d'écriture | Sans cela, deux personnes atteignant un serveur neuf dans le même souffle le trouvent vide toutes les deux et s'en font toutes les deux administratrices. |
| **Une session de lecture appartient à qui l'a ouverte** | Celle d'un autre se lit comme une session qui n'existe pas, et la fermer ne fait rien | Son nom suffit pour recevoir chaque segment de ce qui est regardé. Être connecté ne peut pas vouloir dire être connecté en tant que celui qui l'a ouverte. |
| **Limite d'âge : reportée** | Les colonnes et les règles existent et sont testées ; rien ne les applique encore. À faire seule, après ce chantier | L'appliquer veut dire filtrer les grilles, la recherche, l'accueil, la fiche et la lecture. C'est exactement le genre de filtre qu'on oublie à un endroit sur cinq, et l'endroit oublié est celui qui montre l'affiche à un enfant. Mieux vaut un chantier à part, sérieusement testé, qu'une case cochée dans celui-ci. |
| Tests | Unitaires sur la logique pure, intégration sur base temporaire, chaîne de lecture sur fichiers vidéo générés à la volée | Aucun contenu réel nécessaire, et les cas difficiles se fabriquent à la demande. |
| Restauration | Entrée du menu du script d'installation : arrêt, remplacement de la base et des fichiers envoyés, vérification, redémarrage | La sauvegarde sans restauration testée ne vaut rien. |
| Bibliothèque « Émissions » | Type à part entière (documentaires et programmes de télévision), réutilisant le modèle série, saison, épisode et le même fournisseur | Navigation distincte des séries de fiction, sans dupliquer le modèle. |
| Licence | GNU AGPL v3, comme les autres dépôts du mainteneur | Cohérence avec `Proxmox-Tools`. |
| Utilisateurs | Un utilisateur par défaut et un jeton de session dès la V0.1 | Toute donnée de progression est rattachée à un utilisateur dès le départ. |
| Réactivité | Rien de lourd sur le chemin de lecture : tout est précalculé à l'écriture | Exigence forte, voir le document 02. |
| Compilation | **Directement dans le LXC de production**, via une commande unique de mise à jour (récupérer, compiler, migrer, redémarrer). Compile à la priorité la plus haute tant que le projet est en plein développement, ce qui devra repasser en priorité basse une fois la collection en usage réel au quotidien | Les PC du mainteneur sont sous Windows ; aucun transfert de fichier. En développement, une reconstruction rapide compte plus qu'une lecture en cours, qui n'arrive presque jamais pendant ces sessions. |
| Ressources du LXC | 100 Go de disque, 16 Go de mémoire, 12 threads (monter à 16 si les autres services de l'hôte le permettent) | Le 16 Go et les threads servent surtout à la compilation ; le serveur lui-même est léger. |
| Matériel de transcodage | Intel Arc A380 passée au LXC via `/dev/dri`, distribution FFmpeg de Jellyfin recommandée | Décodage, encodage H.264, HEVC, AV1 et tonemapping HDR sur la carte. |
| Accès | Local en `ip:2100` pour commencer, reverse proxy nginx (autre LXC) et HTTPS plus tard | Voir la ligne « Port » pour le choix du numéro. |
| Configuration et répertoires | TOML dans `/etc/melyxar/melyxar.toml` ; données (base) dans `/var/lib/melyxar` ; cache d'images et segments de transcodage dans `/var/cache/melyxar` ; utilisateur système `melyxar` ; service `melyxar.service` | Conventions Debian, tout sur le NVMe du LXC, jamais dans les dossiers médias. |
| Métadonnées | TMDb, avec la clé de l'application embarquée dans le binaire, brouillée plutôt qu'écrite en clair. Aucun réglage à faire pour l'utiliser | La clé identifie l'application et non la personne qui l'installe, comme chez Jellyfin et Emby : personne n'a de compte à créer. Le brouillage évite qu'elle traîne dans une recherche ou une capture d'écran, sans prétendre la rendre secrète. Elle n'ouvre qu'un catalogue de films public ; si elle est un jour désactivée, on en embarque une autre. |
| Journaux | Noms de médias affichés en clair, fichier et chemin complet, aucun réglage de censure | Ce journal n'est vu que par le mainteneur, qui connaît déjà ses propres fichiers : le lui cacher à lui-même n'apportait rien. Décision revenue en arrière sur celle du départ (« censure des noms de médias »), qui prévoyait de partager ces journaux plus largement. Sans lien avec la règle séparée qui interdit tout nom réel dans le dépôt (code, commentaires, tests, documentation, commits, pull requests, GitHub) : celle-là porte sur ce qui est écrit et publié, pas sur ce qu'un journal affiche en direct sur le propre serveur du mainteneur. |
| Œuvre et fichier | Une œuvre n'est jamais un fichier. Deux copies d'un même film sont deux fichiers d'une même œuvre, reconnus par le titre trié et l'année | C'est ce qui met un sélecteur de version sur la fiche au lieu du même titre deux fois dans la grille, et ce qui fait survivre l'historique au remplacement d'un fichier. |
| Fichier disparu | Marqué absent, jamais supprimé. Une racine illisible est ignorée sans toucher aux autres racines de la bibliothèque | Un disque débranché doit coûter une soirée, pas une bibliothèque. |
| Fichier déplacé ou renommé | **Un fichier absent dont le jumeau exact est présent ailleurs dans la même médiathèque a été déplacé ou renommé**, pas perdu. Jumeau exact : même taille à l'octet près, même date de modification à la nanoseconde près, et un seul candidat dans les deux sens (un fichier disparu qui ressemble à deux présents, ou un présent qui ressemble à deux disparus, n'est pas touché). Le nom n'est pas demandé : il l'était au départ, et un film renommé devenait une œuvre neuve qui perdait où chacun en était et ce qu'il avait vu. La ligne de l'ancien emplacement est retirée ; si l'œuvre qu'elle portait n'a plus rien d'autre, elle rejoint l'œuvre du nouvel emplacement, avec ce que chacun en a vu, où il en était et ses favoris. Vérifié à chaque scan sur toute la médiathèque, pas seulement sur les fichiers qui viennent de bouger | Ranger un dossier, par exemple créer un dossier de saison, laissait chaque fichier en double : l'œuvre neuve au bon endroit et l'ancienne marquée « le fichier n'est pas sur le disque » pour toujours. Relevé sur la collection du mainteneur. Un déplacement ou un renommage garde la taille et la date, alors qu'un disque débranché ne présente aucun jumeau : la règle « jamais supprimé » tient toujours pour ce cas-là. Vérifié sur l'état de la base plutôt que sur ce que le scan vient de voir, pour réparer aussi les déplacements faits avant que la règle existe. |
| Supprimer une œuvre | **Depuis sa carte ou sa page, une fenêtre demande quoi supprimer : de la médiathèque seulement, ou aussi du disque.** Elle dit avant ce qui partira : combien d'œuvres (un film, une série avec ses saisons et épisodes, un dossier avec tout ce qu'il contient) et quels fichiers. Retirer de la médiathèque demande le droit de supprimer ; effacer du disque demande en plus le droit de supprimer du disque, et la case n'apparaît pas à qui ne l'a pas. Ce qui part de la base : l'œuvre, tout ce qui est dessous, ce qui a été vu, les favoris, les images, et ce que plus rien ne désigne ensuite (personnes, genres, collections), exactement comme le retrait d'une médiathèque. Refusé pendant un scan de la même médiathèque | Demandé par le mainteneur, sur le modèle de Jellyfin, mais avec le choix que Jellyfin ne donne pas : chez lui supprimer efface toujours le fichier. Le compte de ce qui part est montré avant la confirmation, parce qu'une série de deux cents épisodes et un film se suppriment du même bouton. |
| Retiré de la médiathèque, pas du disque | **Les fichiers restent sur le disque et sont notés comme écartés** : le scan passe à côté sans les reprendre. Écarté, c'est un chemin précis ; un fichier renommé ou déplacé est un autre chemin et revient. Les réglages d'une médiathèque listent les fichiers écartés, par chemin ; on en reprend un, plusieurs ou tous, et **la reprise lance aussitôt un scan de la médiathèque**, qui les remet en place | Sans cette note, le fichier encore sur le disque revenait au scan suivant, et « retirer de la médiathèque » ne faisait rien que le temps d'un scan. C'est la raison pour laquelle Jellyfin efface toujours le fichier. La reprise existe pour qu'un retrait fait par erreur ne coûte pas un renommage de fichier à la main ; fichier par fichier, parce que reprendre tout pour en retrouver un seul ramènerait aussi ce qu'on avait retiré exprès. Le scan suit la reprise parce que « au prochain scan » laissait l'écran dire une chose et la médiathèque en montrer une autre. |
| Effacer du disque | **Seuls les fichiers que la médiathèque connaît pour cette œuvre sont effacés** : chaque copie, les sous-titres rangés à côté dans leur propre fichier, les bandes-annonces posées à côté. Puis chaque dossier que cela a vidé, en remontant, sans jamais toucher au dossier racine de la médiathèque ni à un dossier qui contient encore quoi que ce soit, même caché. Un chemin qui sortirait du dossier racine est refusé. Si un seul fichier ne peut pas être effacé (disque en lecture seule, droits), l'œuvre reste dans la médiathèque et la fenêtre le dit : le prochain scan verra ce qui a vraiment disparu. Chaque fichier effacé est écrit au journal | Un effacement de fichier ne se rattrape pas : il ne doit porter que sur ce que l'utilisateur voyait à l'écran, jamais sur un dossier entier deviné. Les dossiers vidés partent parce qu'une série effacée qui laisse ses dossiers « Saison 1 » vides n'est pas effacée. Garder l'œuvre quand un fichier résiste évite une médiathèque qui ne connaît plus un fichier encore présent. |
| Sélection multiple | **Dans la grille d'une médiathèque et dans un dossier perso, on coche plusieurs éléments puis on agit sur tous d'un coup.** Une case apparaît au survol d'une carte, ou l'entrée « Sélectionner » de son menu ; dès qu'une carte est cochée, un clic sur une autre la coche au lieu de l'ouvrir, Maj + clic coche tout l'intervalle, Échap abandonne. Une barre dit combien sont cochés et propose « Tout sélectionner » (ce qui est affiché) et « Supprimer ». La suppression groupée pose la même question qu'une seule, avec le total de ce qui part et des fichiers, et se fait d'un bloc : elle est refusée entière si une médiathèque concernée est en plein scan ou si un disque n'accepte pas l'écriture. Une œuvre cochée en même temps que sa série n'est comptée qu'une fois | Demandé par le mainteneur pour faire le ménage sans répéter cent fois la même fenêtre. Une seule demande au serveur plutôt qu'une par élément : le compte montré est celui qui part, les vérifications ont lieu avant le premier effacement, et ce que plus rien ne désigne est balayé une fois au lieu de cent. |
| Épisode rangé nulle part | **À chaque scan d'une médiathèque de séries, d'animés ou d'émissions, chaque épisode qui n'est rangé sous aucune série voit son nom relu** par les règles du moment. S'il dit maintenant de quel épisode il s'agit, l'épisode rejoint sa place sous sa série et sa saison, avec ce que chacun en a vu. Seulement un épisode que personne n'a nommé, qui porte un seul fichier présent sur le disque, et jamais une copie qu'une personne a séparée à la main : ce geste dit que la lecture du nom s'était trompée, et la même lecture ne la remet pas en place d'elle-même | Un scan ne rouvre jamais un fichier qui n'a pas bougé sur le disque. Un épisode mal lu une fois restait donc seul dans la grille pour toujours, même après que les règles ont appris à le lire. Relevé sur la collection du mainteneur : des dizaines d'épisodes orphelins dans la médiathèque d'animés. |
| Sous-titres externes | Un sous-titre dans son propre fichier est une piste de l'œuvre. Langue, forçage et malentendants sont lus dans le nom du fichier ; un mot qui pourrait être un groupe de release n'est jamais pris pour une langue | Une langue que personne ne parle dans le sélecteur est pire que pas de langue du tout. |
| Fichiers de description (`.nfo`) | Lecture facultative, **désactivée par défaut**. Seuls les identifiants des fournisseurs sont repris, jamais un titre ni un synopsis | Un identifiant peut être vérifié auprès du fournisseur ; un titre serait cru sur parole et écraserait silencieusement le sien. |
| Tâches de fond | Écrites en base avant de démarrer, annulables, avec progression. Deux tâches de même nature ne tournent jamais sur le même sujet à la fois ; un redémarrage clôt ce qu'il a interrompu | Un écran doit pouvoir montrer ce qui tourne, et l'arrêt doit arrêter le travail, pas seulement ignorer sa réponse. |
| Analyse des fichiers | Étape distincte du parcours des dossiers, reprise par le scan suivant, bornée à quelques fichiers à la fois | Un scan doit laisser intacte la lecture qui se déroule à côté. |
| Ce que fait un scan, et ce qu'il ne fait pas | **Le scan reste léger.** Il parcourt les dossiers, note ce qui a bougé, relit les noms et demande à l'analyseur ce que chaque nouveau fichier contient. Les **deux lectures intégrales d'un film**, les endroits où un saut peut atterrir et les vignettes de la barre, n'en font plus partie : ce sont deux travaux à part, l'entretien, qui tournent **la nuit** ou **au bouton**. Chaque médiathèque porte deux interrupteurs disant si son propre scan les fait quand même, **décochés par défaut**. Le plafond de cinq mille fichiers par passe disparaît : chaque lot redemande ce qui reste, et la lecture continue jusqu'à ce qu'il ne reste rien | Mesuré sur la collection du mainteneur : ces deux lectures transformaient un scan de quelques minutes en scan de plusieurs jours, et le plafond faisait que le reste attendait le scan suivant, qui s'arrêtait au même endroit. Les séparer est exactement ce que font Jellyfin et Emby, et la documentation de Jellyfin met en garde contre l'interrupteur sur une grosse médiathèque. Décochés par défaut parce que c'est la bonne réponse pour la médiathèque assez grosse pour que le réglage existe ; une petite médiathèque sur une machine qui a du temps coche les deux et a tout d'un coup. L'heure du passage de nuit se règle depuis l'interface, voir les deux lignes qui suivent. |
| Désigner un dossier depuis l'interface | **Un explorateur de dossiers dans la page**, comme chez Jellyfin : il ne remonte **que des dossiers**, jamais un nom de fichier, il saute ce qui commence par un point, il ne suit pas les liens symboliques, il borne ce qu'il rend, et il dit pour chaque dossier combien de vidéos il contient directement. Le chemin vient du navigateur, ce qui est l'exception à la règle « jamais de chemin venant du client » : elle reste entière partout ailleurs, et en particulier pour tout ce qui ouvre, sert ou supprime un fichier. Ici rien n'est ouvert : un chemin est rendu canonique, listé, et sert ensuite de racine déclarée, c'est-à-dire exactement ce que le fichier de configuration donnait avant. Réservé à l'administrateur, et le contrôle est écrit là où il doit l'être **dès maintenant**, même s'il ne mord pas encore | C'était la dernière chose qui obligeait à ouvrir un terminal, et la règle de travail dit que rien ne doit l'exiger. L'autre voie, déclarer dans le fichier les dossiers autorisés à devenir des racines, gardait un terminal dans le chemin pour la seule opération qui en avait encore besoin : elle déplaçait le problème au lieu de le régler. Le prix est dit franchement : une personne qui atteint le serveur peut énumérer l'arborescence des dossiers de la machine. **À savoir tant que la connexion n'existe pas** : ce serveur n'a aucune authentification pour l'instant, donc cette route est aussi ouverte que toutes les autres, y compris le rapport de diagnostic qui nomme déjà des dossiers. Le jour où l'on se connecte, le contrôle déjà écrit commence à mordre sans que rien d'autre ne bouge. |
| Refuser la conversion des couleurs pour tout le serveur | **Un réglage général**, décoché par défaut, distinct de l'interrupteur par spectateur prévu au jalon 8. La règle automatique reste le défaut : un film à large gamme est converti parce qu'aucun navigateur ici ne l'affiche correctement, et ça coûte une reconstruction complète de l'image. Ce réglage-ci sert un processeur trop lent pour tenir cette reconstruction film après film, et non un écran réellement HDR : décoché, le film part inconverti dès que rien d'autre n'oblige à le reconstruire, et apparaît délavé plutôt que dans ses vraies couleurs. **Le Dolby Vision sans couche de base compatible n'y est jamais soumis** : laissé tel quel il n'est pas délavé, il est cassé, vert et violet, donc il reste converti quoi qu'il arrive | Le réglage par spectateur prévu au jalon 8 répond à une autre question, « je regarde sur un écran qui affiche ces couleurs », et n'a pas sa place sur une machine qui ne peut simplement pas se permettre la reconstruction. Séparer les deux évite qu'un futur réglage par spectateur ne redevienne accidentellement ce court-circuit serveur. La distinction Dolby Vision existait déjà dans le moteur de décision pour une autre raison, choisir la phrase du refus ; ce réglage s'appuie dessus plutôt que de la refaire. |
| Chemin d'une racine dans l'écran des bibliothèques | **Affiché en entier**, à côté du libellé et non à sa place, sur ce seul écran : c'est là que l'administrateur gère les racines, et c'est précisément là qu'il doit pouvoir vérifier à quel dossier réel un libellé correspond. Le journal, lui, continue de ne montrer que le libellé | Un libellé est ce qui distingue deux racines à l'oreille ; il ne dit pas à l'écran quel dossier du disque il désigne, et la seule façon de le savoir sans cet affichage aurait été d'ouvrir un terminal sur le serveur, ce que la règle de travail interdit. |
| Retirer une racine ou une médiathèque | **Ne touche jamais au disque**, comme chez Jellyfin. Ce qui part est ce que le serveur sait : les films de cette médiathèque, leurs fiches, leurs affiches, ce qui en a été vu, les fichiers en tant que lignes, et les dossiers en tant que dossiers déclarés. **Aucun fichier n'est ouvert, déplacé ni effacé.** Retirer un dossier emporte les films qui n'existaient que par lui ; un film détenu aussi ailleurs reste et perd cette copie-là. L'écran annonce les nombres exacts **avant**, et demande une confirmation. Refusé tant qu'un travail tourne sur cette médiathèque, parce que retirer sous les pieds d'un scan revient à le faire échouer sans raison lisible | C'est la seule façon de défaire ce qu'un bouton peut faire, et sans elle une faute de frappe dans un dossier reste là pour toujours. Les fichiers sont intouchables parce que le serveur n'est pas propriétaire de la collection : il la lit. Effacer sur disque est une fonction distincte, demandée film par film, réservée à l'administrateur, avec sa propre case décochée par défaut, et elle ne passera jamais par ici. Annoncer les nombres avant plutôt que de dire « êtes-vous sûr » : personne ne peut être sûr sans savoir combien. |
| Ce qu'un retrait emporte derrière les films | **Tout ce que plus rien ne désigne.** Un film traîne derrière lui du partagé, qui n'appartient à aucun film en particulier et ne suit donc aucun film en sortant : les personnes qu'il crédite, la collection dont il fait partie, ses genres et ses studios, et toutes leurs images. Le retrait les balaie, **bornés par ce qui reste** et jamais par ce qui part : une personne qu'un film encore présent crédite garde sa ligne et sa photo. Une collection faite à la main reste, vide ou non, parce qu'elle appartient à quelqu'un. Côté cache, les planches de vignettes **et** les images (affiches, fonds, logos, visages) des éléments partis sont effacées, fichier par fichier d'après la ligne qui les nommait, puis le dossier s'il est devenu vide. Les sous-titres convertis restent : ils pèsent quelques dizaines de kilo-octets et ont déjà leur propre bouton | Rien de tout cela ne pend à une médiathèque dans le schéma, donc rien de tout cela ne part avec elle : sans balayage, des années d'usage remplissent la base de noms que plus aucune page n'atteint et le cache de visages que personne ne reverra. Borner par ce qui reste plutôt que par ce qui part est ce qui rend le balayage sûr après n'importe quel retrait, et ce qui évite d'effacer l'affiche d'un film encore là. Le journal dit les comptes de chaque poste, ligne par ligne, parce que « ça se nettoie » est une affirmation qui doit se vérifier et pas se croire. |
| Ce qui vit dans le fichier de configuration | **Seulement ce qui dépend de la machine** : où sont les dossiers, sur quel port écouter, où est l'outil, combien de travail peut tourner à la fois, comment le serveur est joint. Tout ce qui décide de ce que le serveur fait des films est un réglage du serveur, gardé en base et modifiable depuis l'interface : l'heure de l'entretien, la forme des vignettes de la barre, la lecture des fichiers de description. Un fichier qui porte encore une section déplacée démarre quand même, elle est simplement ignorée | La règle de travail dit que rien ne doit exiger un terminal, et ces trois réglages en exigeaient trois : ouvrir un éditeur de texte sur le serveur, écrire une ligne, redémarrer. Aucun des trois ne parle de la machine ; ils disent ce que quelqu'un veut qu'on fasse de ses films. Ignorer une section devenue inutile plutôt que la refuser évite le pire cas : un serveur qui ne démarre plus à cause de trois lignes que plus personne ne peut voir, et qu'il faut donc un terminal pour retirer. |
| Heure d'un travail périodique | **Gardée en temps universel**, choisie et affichée à l'heure du navigateur qui la règle. Conséquence assumée et écrite à l'écran : l'heure affichée décale d'une heure au changement d'heure, jusqu'à ce que quelqu'un la remette | L'heure qu'une machine appelle la sienne se lit dans un réglage qu'aucun programme ne devrait interroger depuis plusieurs fils d'exécution à la fois, et une valeur qui aurait l'air locale serait fausse sur tout serveur réglé autrement. Le navigateur, lui, connaît son décalage avec certitude : la conversion se fait donc du seul côté où elle est honnête. Pour un entretien de nuit, une heure de décalage deux fois par an ne coûte rien, et le dire vaut mieux que le cacher. |
| Étendue d'un scan | **Trois modes, choisis au lancement**, comme chez Jellyfin : les fichiers nouveaux et modifiés, compléter ce qui manque, tout refaire. Le deuxième est celui d'un scan que personne n'a paramétré, y compris celui qu'un redémarrage reprend. « Tout refaire » oublie d'abord ce qui avait été lu dans chaque fichier et remet chaque film dans la file du fournisseur ; un film identifié à la main n'y est jamais touché | Ce sont les trois questions réellement posées, et elles ne coûtent pas la même chose : la première ne touche rien de ce qui est déjà là, la dernière peut durer des heures. Le défaut reste « compléter ce qui manque » parce que redemander les images d'un film qui n'en a aucune est une décision actée de ce projet et non un mode parmi trois : un défaut qui l'ignorerait la déferait en silence. Chaque mode dit aussi ce qu'il coûte dans l'interface, parce que les nommer sans l'expliquer est précisément le reproche fait à Jellyfin depuis des années. |
| Reprise après un redémarrage | Une tâche coupée ne reprend jamais au milieu d'un fichier : **chaque passe demande ce qui reste à faire** plutôt que de dérouler une liste établie au départ, et un fichier n'est écrit en base qu'une fois traité en entier. Un scan relancé repart donc exactement où il en était, sans refaire ce qui était fait. Une coupure par un redémarrage est **un état à part, ni un échec ni un arrêt demandé**, et c'est le seul que le serveur reprend de lui-même : au démarrage il relance les scans et les identifications coupés, en priorité basse. Une tâche qui a échoué échouerait de nouveau, une tâche arrêtée à la main l'a été exprès : ni l'une ni l'autre n'est reprise. Seul le serveur fait cela, jamais le diagnostic ni la ligne de commande | Un scan de la collection entière prend des heures : le recommencer depuis le début à chaque mise à jour du serveur reviendrait à ne jamais le finir, et devoir y penser soi-même revient à l'oublier. Demander ce qui reste plutôt que de retenir où on en était supprime le problème au lieu de le gérer : il n'y a pas de position à sauvegarder, donc rien à perdre, et cela vaut aussi pour un arrêt brutal ou une coupure de courant. Priorité basse parce que personne n'attend cette reprise, contrairement à un scan lancé depuis un bouton. L'état distinct sert deux fois : il dit au serveur quoi reprendre, et il évite d'afficher en rouge comme une erreur une tâche à laquelle rien n'est arrivé. |
| Journal étiqueté, lisible depuis l'interface | Chaque ligne que Melyxar écrit porte une **étiquette** d'un mot disant quelle partie du serveur l'a écrite (`scan`, `playback`, `subtitles`, `card`, `metadata`...), **déduite du code** et jamais posée à la main. Les dernières milliers de lignes sont gardées en mémoire, quel que soit leur niveau, et un écran de l'interface permet de cocher les étiquettes voulues, de restreindre à un mot, puis de copier exactement ce qui est affiché. Le niveau réglé dans la configuration ne décide que de la copie envoyée à la console | La question posée vingt fois par jour est « ça n'a pas marché » / « qu'est-ce que le serveur a dit ». Y répondre demandait de connaître le nom d'un service, la syntaxe d'un filtre de journal et la forme d'une date, sur une machine où l'on n'est pas forcément assis. Avec des étiquettes, l'un dit « envoie-moi `playback` et `subtitles` », l'autre coche deux cases et colle : personne n'explique rien. Déduite du code parce qu'une étiquette que personne n'a à écrire est une étiquette toujours juste. Gardée quel que soit le niveau parce qu'une ligne qu'il faut activer n'est jamais là le soir où on la veut : le niveau décide comment on retrouve une ligne, pas si elle existe. En mémoire et non dans un fichier parce qu'un fichier veut un dossier, des droits, une rotation et un ménage, pour un besoin qui dure le temps d'un test ; ce qu'une panne laisse derrière elle reste l'affaire du journal du système, qui reçoit toujours tout. |
| Étape d'une tâche | Chaque passe d'une tâche dit son nom, et les compteurs comptent cette passe seule : changer d'étape remet le compte à zéro dans le même mouvement. Une étape que la version en place ne connaît pas s'affiche comme aucune étape, au lieu de rendre la ligne illisible | Un scan enchaîne quatre passes et les plus longues sont à la fin, donc la barre se remplit, retombe à zéro et repart. Sans un mot disant laquelle, cela ressemble exactement à un serveur qui a planté et tout recommencé, ce qu'il ne doit jamais avoir l'air de faire. Additionner les passes serait pire encore : quatre cents fichiers analysés puis trois cent quarante relus compteraient deux fois les mêmes films. |
| Client HTTP sortant | `reqwest` avec `rustls`, jamais OpenSSL, délais d'attente explicites et un seul client réutilisé | `rustls` évite de dépendre d'une bibliothèque système et donc d'un paquet de développement de plus à installer dans le LXC. Un client partagé garde les connexions ouvertes vers le fournisseur au lieu d'en rouvrir une par film. |
| Fournisseur de métadonnées | Derrière un trait, avec un fournisseur de remplacement dans les tests. Un fournisseur injoignable n'arrête jamais un scan : la tâche est réessayée à intervalles qui s'écartent | Le scan et l'identification sont deux étapes séparées ; la bibliothèque reste consultable même si TMDb est en panne. |
| Langue des fiches | **Fait.** Réglage de chaque médiathèque, modifiable dans ses paramètres depuis l'interface, comme chez Jellyfin. Sa valeur par défaut est « suivre la langue de l'administrateur » plutôt qu'une langue écrite en dur, et chaque médiathèque peut en choisir une autre. Rien à voir avec la langue de l'interface, qui appartient à celui qui regarde et change d'un spectateur à l'autre. Changer la langue **re-télécharge toutes les fiches de la médiathèque**, pas seulement celles à venir, comme une tâche de fond ordinaire : visible, chiffrée, annulable. Ce qui avait été récupéré reste rangé sous son ancienne langue plutôt que d'être effacé, ce qui ne coûte rien et sert de repli pour un film que le fournisseur ne décrit pas dans la nouvelle. Le fichier de configuration ne donne plus que la langue de départ d'une médiathèque qu'il crée : il ne la réimpose plus à chaque démarrage, faute de quoi un choix fait à l'écran serait défait au redémarrage suivant, sans que rien ne le dise. Reste la valeur par défaut, qui est l'anglais et non la langue de l'administrateur | Une médiathèque d'animés japonais et une de films français ne veulent pas la même langue sur le même serveur, donc le réglage appartient à la médiathèque et non au serveur. Un défaut qui suit l'administrateur évite d'imposer la préférence de celui qui a écrit le code à tous ceux qui l'installent. Et le spectateur n'a pas à choisir : les fiches sont téléchargées une fois et gardées, alors que la langue de l'interface se change à chaque visite. Le schéma le permet déjà, puisqu'un texte est rangé par œuvre **et par langue**, avec repli sur celles qui existent : c'est aussi ce qui rend le re-téléchargement sans risque, puisque rien n'est écrasé et qu'un retour en arrière est immédiat. |
| Images | Téléchargées une fois, converties par FFmpeg en WebP aux largeurs fixes, servies sous un nom tiré de leur contenu. Jamais redimensionnées à la demande | Un serveur qui redimensionne à chaque requête passe son après-midi sur la même affiche. Le nom permet au navigateur de garder une image pour toujours et de voir la nouvelle le jour où elle change. |
| Chemin du fichier sur la fiche | Affiché en entier, avec le disque, la date d'ajout et le débit total, puis une carte par piste avec tous les champs relevés par l'analyse. La lecture passe toujours par l'identifiant, jamais par le chemin | Sur une page qui parle d'un fichier, la première chose qu'on veut quand quelque chose cloche avec lui, c'est où il est. Un chemin affiché n'est pas une adresse : rien ne s'ouvre à partir de lui. Le jour où les comptes auront des rôles, ce bloc deviendra une information d'administrateur. |
| Images qui ne sont pas arrivées | Une image est demandée au moment où un film est nommé. Si elle n'arrive pas ce jour-là, disque plein, dossier non inscriptible, fournisseur en panne une minute, le film garde son titre et son rectangle gris pour toujours. Une passe en fin d'identification redemande les images des films qui n'en ont aucune, et le rapport les nomme | Sans cela, rien ne redemande jamais, et rien ne le dit : le travail a réussi, le titre est bon, et le seul signe est un trou que quelqu'un croise en faisant défiler la grille. |
| Synopsis absent dans la langue demandée | Le résumé d'origine est utilisé à la place. Le titre reste dans la langue de la bibliothèque | Beaucoup de films sont décrits dans une langue et pas encore dans une autre. Une page à moitié vide est pire qu'une page avec un paragraphe lisible. |
| Couleur de carte | Moyenne de l'affiche, lue en la réduisant à un pixel | Une carte a une couleur à montrer avant l'arrivée de son image. |
| Interface | **Décision révisée.** React, construite par le script d'installation, et **servie depuis son propre dossier** (`/usr/local/share/melyxar/web` par défaut, réglable dans la configuration) plutôt qu'embarquée dans le binaire. Le serveur lit chaque fichier sur le disque au moment où on le lui demande : une nouvelle interface est donc servie dès qu'elle est posée, sans redémarrage. Le script ne refait que ce qui a changé depuis la dernière installation réussie de chaque partie : l'interface seule se construit et se pose en quelques secondes sans toucher au serveur ; le moteur seul ne reconstruit plus l'interface. Quand les deux changent, l'interface est posée juste avant le redémarrage, jamais pendant la compilation, pour qu'une interface neuve ne parle jamais longtemps à un moteur ancien. Chaque fichier est remplacé d'un seul coup, la page d'entrée en dernier, et les fichiers de l'interface précédente sont gardés une mise à jour de plus, pour qu'un onglet resté ouvert puisse encore charger le lecteur. Aucun nom de fichier demandé ne sort du dossier | Embarquée, la moindre retouche de couleur recompilait le serveur (1 min 15 mesurée) et le redémarrait, coupant les lectures en cours, au rythme où l'interface est retouchée en ce moment. Lue sur le disque, elle ne coûte rien de mesurable : le système garde en mémoire des fichiers qui font en tout moins de deux mégaoctets, et le navigateur ne redemande presque rien, puisqu'il garde pour toujours ce qui porte une empreinte dans son nom. Mesuré avant et après, les deux serveurs compilés et interrogés à tour de rôle : un dixième de milliseconde pour la page, deux dixièmes pour le plus gros fichier, dans les deux cas. Le fichier est lu sur place plutôt que confié aux fils réservés au travail lent : ce détour coûtait à lui seul la moitié du temps de la réponse, pour quelques microsecondes de lecture. Le déploiement ne passe que par le script et, plus tard, par une image Docker qui contiendra les deux : aucun binaire seul n'est distribué, donc un seul fichier ne rapportait rien. |
| Grille | Défilement continu par curseur, avec `content-visibility` plutôt qu'une bibliothèque de virtualisation | Le navigateur saute le dessin de ce qui est hors écran sans dépendance supplémentaire ni gestion manuelle des hauteurs. |
| Vérification | Pas d'intégration continue GitHub. Compilation, `clippy` et tests dans l'environnement de travail avant chaque commit, puis compilation réelle dans le LXC par le mainteneur | Le mainteneur rapporte les erreurs directement. |
| Playlist de lecture | Écrite par le serveur sur une grille fixe de quatre secondes, jamais par FFmpeg | Le serveur connaît la durée du film, donc il liste tous les segments avant qu'aucun n'existe. C'est ce qui rend le saut ordinaire au lieu d'un cas particulier. |
| Lecture des noms de fichiers | L'année est la frontière : ce qui la précède est le titre, ce qui la suit est jeté. Pour un nom sans année, le titre s'arrête au premier mot qui ne peut que décrire le fichier. Et dans tous les cas, deux choses sont retirées de la fin du titre : le mot qui nomme la version du film, et un marqueur qui crie en majuscules à la fin d'un titre qui ne crie pas. Un mot technique écrit en deux mots reste un mot technique | La liste des mots techniques est infinie et grandit ; une année à quatre chiffres reste une année. Les deux coupes de fin traitent ce que la frontière ne peut pas atteindre, parce qu'écrit avant l'année. Une étiquette écrite avec une espace au milieu passait inaperçue et laissait la description collée au titre, ce qui ne ramène rien du tout chez le fournisseur. |
| Accents dans les noms de fichiers | Un accent arrive écrit de deux façons : un seul caractère, ou la lettre suivie de l'accent comme marque séparée. Les deux s'affichent à l'identique. Le repli sur lettres simples retire les marques séparées, donc les deux formes se trient et se comparent pareil. Et si une recherche ne ramène rien, le titre est redemandé en lettres simples | Mesuré contre le vrai fournisseur : la forme composée ramène sept résultats, la forme décomposée zéro. Personne ne devinerait jamais que c'est ça le problème, puisque les deux titres sont identiques à l'écran. |
| Signature d'une bibliothèque | Le mot dont son propriétaire signe ses fichiers est **appris de la bibliothèque elle-même** : le dernier mot de chaque nom est compté, et ceux qui reviennent au moins trois fois sont des signatures. Jamais écrit dans le code | Aucune liste ne peut tenir toutes les signatures possibles, et une signature écrite dans le dépôt nommerait celui qui l'utilise. Ce qui se dit généralement, c'est qu'une signature se répète et qu'un titre non. C'est le seul moyen de la retirer d'un titre écrit entièrement en majuscules, où aucune règle de forme ne peut la distinguer d'un mot. |
| Un échec d'identification porte le nom lu | La liste des films sans nom montre, à côté du titre cherché et de la raison de l'échec, le **nom du fichier** dont ce titre a été lu, jamais les dossiers qui y mènent | Un titre lu dans un nom de fichier ne vaut que ce que vaut ce nom. Un titre qui se lit bizarrement pose donc exactement une question, et y répondre demandait d'ouvrir la base à la main : c'est précisément ce que le rapport existe pour éviter. |
| Ce qui est collé devant un nom | Quelques caractères collés au début d'un nom, sans séparateur, sont retirés. Rien n'est deviné sur leur forme : c'est un préfixe seulement si le reste du nom est, en entier et à la lettre, un autre nom de la même bibliothèque. Il doit aussi être d'un seul tenant, sans séparateur dedans | La copie sans le préfixe est la preuve qu'il a été ajouté : c'est une constatation, pas une supposition. La contrainte du seul tenant protège les vrais titres, parce qu'un morceau qui se termine sur une limite de mot est un mot, et que deux vrais films peuvent s'appeler une chose et cette chose précédée d'un mot. |
| Une année à la toute fin d'un nom | **C'est l'année**, même si rien ne la suit. `Titre Année.mkv` se lit titre plus année, là où la règle d'avant gardait le nombre dans le titre | Mesuré chez le fournisseur plutôt que discuté : sur un échantillon large de films réels, un titre sur cent quarante porte une année dans son propre nom, alors que `Titre Année` sans rien d'autre est une des formes les plus courantes qui soient. Et interrogé avec l'année encore collée au titre, le fournisseur n'a rien répondu du tout vingt-cinq fois sur vingt-huit. Garder le nombre dans le titre n'était donc pas la lecture prudente : c'était celle qui ne retrouve jamais le film. Ce que ça coûte, dit franchement : un film dont le titre se termine vraiment par une année et dont le nom ne dit rien d'autre perd cette année. Rien dans un tel nom ne permet de trancher. |
| Une année écrite devant le titre | Lue là où elle est, **à condition d'être entre parenthèses**, et le reste du nom est alors lu comme un nom sans année. Écrite sans parenthèses elle reste dans le titre | C'est la seule forme où la frontière est à l'envers, et elle se signale toute seule : aucun film ne s'appelle `(2019)`. Lire le reste comme un nom sans année règle du même coup le cas d'un titre qui porte un nombre ressemblant à une année, puisque la date que quelqu'un a pris la peine d'écrire devant ne se fait plus doubler par lui. Sans parenthèses, rien ne distingue une année d'un titre : un film peut s'appeler `1917`. |
| Ce qui est écrit devant un nom, et qui n'est pas le titre | Deux choses retirées avant tout le reste : l'**adresse du site** d'où le fichier a été distribué, et le **nom d'un groupe entre crochets** en tête de nom. L'adresse doit se dire comme telle, par un `www.` ou par ses propres crochets ; le groupe se reconnaît aux crochets droits ou aux accolades, jamais aux parenthèses | Les deux se tiennent là où le titre est attendu, et le fournisseur interrogé avec ça ne trouve rien. Pour l'adresse, aller jusqu'à reconnaître un simple `quelquechose.truc` coûterait son titre à un film : le point sépare les mots dans ces noms, donc `Dr.No` est une adresse aussi valable qu'une autre. Pour le groupe, les parenthèses sont exclues parce qu'un vrai titre peut commencer par un nombre entre parenthèses, et un film connu le fait. Un mot entre crochets ailleurs dans le nom reste intact : c'est ainsi que s'écrivent une année et une étiquette. |
| Un titre écrit entièrement en majuscules | Le marqueur final n'est retiré que si le titre, lui, ne crie pas. Ce jugement ne se fait plus que sur les mots **qui peuvent crier** : un nombre, un mot d'une seule lettre et un mot composé des lettres d'un chiffre romain n'y participent pas | Ils faisaient dire au titre qu'il ne criait pas, et son dernier mot partait avec le marqueur. Trois vrais films l'ont montré : `12 ANGRY MEN` perdait `MEN` à cause du `12`, `A CLOCKWORK ORANGE` perdait `ORANGE` à cause du `A`, et `DIX POUR CENT LE FILM` perdait `FILM` parce que `DIX` s'écrit avec les lettres d'un chiffre romain. |
| Deux fiches qui sont un seul film | Quand la relecture d'un nom donne un titre déjà présent dans la bibliothèque, le fichier rejoint ce film au lieu d'en former un second. Seules les fiches encore sans nom sont concernées | Les règles de lecture s'améliorent, donc des copies nommées différemment finissent par se lire pareil. Les laisser séparées, c'est le même titre plusieurs fois dans une grille, exactement ce que le sélecteur de version existe pour éviter. Une fiche jamais identifiée n'a ni affiche, ni distribution, ni résumé : il n'y a que ses fichiers à déplacer. |
| Relire le nom d'une œuvre encore sans nom | **Chaque sorte est relue comme elle a été nommée : un film d'après son propre fichier, une série d'après le dossier au-dessus de ses épisodes.** Les deux lectures sont différentes et aucune ne remplace l'autre ; un épisode relu comme un film revient sous le nom de sa propre série et l'avale. Une série dont le nom relu existe déjà rejoint celle-là, saison par saison et épisode par épisode | Les règles qui lisent les noms de dossiers s'améliorent comme celles qui lisent les noms de fichiers, et rien ne relisait jamais un nom de dossier. Relevé sur la collection d'un proche du mainteneur : une série dont le dossier portait un mot que les règles d'alors ne reconnaissaient pas dans cette orthographe est restée non identifiée, et le serait restée pour toujours. Chaque nuit reposait au fournisseur la même question fausse, et la seule sortie aurait été de jeter la bibliothèque et de la refaire. |
| Un identifiant du fournisseur, un film | Dans une bibliothèque, deux fiches auxquelles le fournisseur répond le même identifiant sont le même film : la plus ancienne reste, l'autre lui donne ses fichiers. Vérifié à la fin de chaque identification | Deux copies peuvent porter des noms qu'aucune règle ne rapprochera jamais, l'une nommée d'après le titre de tournage et l'autre d'après le titre de sortie ici. Seul le fournisseur peut dire que c'est le même film, et il le dit en répondant le même identifiant. Les laisser séparées, c'est le même titre, la même affiche et le même résumé deux fois dans la grille. |
| Identification à la main | Depuis la fiche de **n'importe quel** film, identifié ou non : un champ prérempli avec le titre actuel, les propositions du fournisseur avec affiche et synopsis, un clic pour choisir. Le choix est retenu comme un choix et aucune exécution ultérieure ne le défait | Les règles s'améliorent et ne finiront jamais le travail. Et un film mal nommé ressemble exactement à un film bien nommé : seul celui qui le regarde peut faire la différence, donc l'option doit être là même quand rien ne paraît anormal. |
| Ce qui identifie un film | **Le nom, et rien d'autre.** Une proposition n'est retenue que si elle porte le nom cherché, sous son titre de sortie ou son titre de tournage. L'année ne fait que départager les films de ce même nom. Si rien ne porte le nom, le film reste sans nom et attend | Une recherche faite d'un nom que le fournisseur ne connaît pas renvoie quand même des films, parce qu'une recherche renvoie toujours quelque chose. Prendre le premier, c'est tirer un film au hasard : ça a collé un making-of sur deux films différents d'une série, et comme les deux portaient alors le même identifiant, ils ont été réunis sur une seule fiche. Une date en commun est une coïncidence, pas un nom. Un film sans nom se voit dans le rapport et se corrige ; un film mal nommé ne se voit pas. |
| Comparaison de deux titres | Sur les mots seuls : accents repliés, majuscules enlevées, et tout ce qui n'est ni lettre ni chiffre remplacé par une espace. L'apostrophe part sans laisser d'espace, c'est la seule marque qui vit à l'intérieur d'un mot. Une suite numérotée en chiffres romains devient le nombre qu'elle est. Jamais de fusion de deux mots en un | Celui qui a nommé le fichier a sauté un deux-points ou écrit un nom à trait d'union en deux mots, et rien de tout ça n'en fait un autre film. Coller deux mots ensemble, en revanche, fabriquerait un nom différent. |
| Un nom presque juste | Une proposition qui n'est pas mot pour mot celle cherchée est retenue si elle est **assez proche** et que son année concorde. La proximité est la part des mots que les deux titres emploient tous les deux, comptée dans les deux sens ; la barre est à la moitié. Un mot et le même mot avec un `s` final comptent pour un seul mot | Celui qui nomme le fichier et celui qui écrit le catalogue sont deux mains différentes : l'une oublie le numéro de volume, l'autre garde le numéro d'épisode. Compter dans les deux sens est ce qui garde un making-of à distance, puisqu'il porte tout le titre du film plus plusieurs mots. Sous la moitié, les mots en commun sont ceux que deux titres quelconques partagent. L'année est ce qui empêche un nom presque juste d'être un autre film. Le pluriel a été relevé sur la collection du mainteneur : un dossier nommait une série avec un `s` que le fournisseur n'écrit pas, et les deux noms ne partageaient plus que leur article. |
| Séparer une copie | Depuis la fiche d'un film détenu en plusieurs exemplaires, chaque copie peut être déclarée « autre film ». Elle repart comme film à part entière, nommée d'après son propre fichier, en attente d'identification. Refusé s'il ne reste qu'une copie | Le regroupement se fait tout seul, des deux côtés : par la lecture des noms et par l'identifiant du fournisseur. Tout ce qui agit tout seul doit pouvoir être défait à la main, sinon un regroupement erroné coûte un film que personne ne peut récupérer. |
| Choix entre plusieurs films du même nom | L'année écarte les films que ce ne peut pas être, à un an près, et l'ordre du fournisseur décide parmi ceux qui restent | Un film a plusieurs dates de sortie, festival, pays, plateforme, chacune d'une année différente. L'année est donc fiable pour écarter un film d'une autre décennie et sans valeur pour départager deux films distants d'un an. L'ordre du fournisseur est l'inverse : il n'écarte rien et départage bien, parce que sur vingt films portant un titre courant, un seul est celui que presque tout le monde désigne. |
| Le son d'un segment après un saut | Quand l'image est recopiée, on demande à l'outil de **ne pas rogner** ce qu'il a lu avant la position demandée. Jamais quand l'image est reconstruite | Une image recopiée ne peut commencer que sur une image clé, donc l'outil recule jusqu'à la précédente. Laissé à lui-même il rogne ensuite le son jusqu'à la position demandée, puisque le son, lui, est reconstruit et peut démarrer n'importe où. Le segment portait alors une image d'un moment et un son d'un autre : mesuré à dix secondes d'écart sur un film dont les images clés sont espacées de dix secondes. Une image reconstruite démarre exactement où on le lui demande, et c'est le rognage qui rend cela vrai : d'où la condition. |
| Ordre des filtres d'image | L'image est **réduite avant** que ses couleurs soient converties, et non l'inverse | Convertir les couleurs est ce qu'on fait de plus cher à une image : chaque pixel passe par une étape en virgule flottante. Le faire sur un quart des pixels coûte un quart du travail. L'ordre inverse était la règle ici, au motif qu'une image redimensionnée encore dans sa plage large reste plus propre : c'est vrai sur le papier. Mesuré sur quatre threads avec un vrai film 4K HDR, cet ordre tournait à un tiers du temps réel, soit un diaporama sonore, contre plus vite que le temps réel dans l'autre sens. Personne ne voit la différence de qualité, tout le monde voit un film qui saccade. |
| Taille d'une image reconstruite au processeur | Plafonnée à 1080p. Un client qui demande moins obtient moins ; une image déjà plus petite est laissée telle quelle | Aucun processeur généraliste ne reconstruit une image 4K en temps réel. Une image fluide vaut mieux qu'une plus grande que personne ne peut regarder. Le plafond ne concerne que le logiciel : une carte fait ce travail sans s'en apercevoir, et le jour où elle est utilisée il ne s'applique pas à elle. |
| Ce qu'une carte sait faire | **Établi en essayant, jamais en lisant.** Au démarrage, une fraction de seconde d'image fabriquée est encodée sur la carte, une fois par codec, plus un essai pour la réduction et un pour la conversion des couleurs. Ce que l'outil a répondu quand il a refusé est conservé mot pour mot, et va au journal et au rapport. L'appareil est ouvert directement avant qu'on parle au pilote, parce que c'est ce qui sépare les trois causes | Trois choses doivent être vraies et une seule se lit quelque part : que la compilation porte le chemin, que la machine ait l'appareil, et que le pilote accepte le travail. Un conteneur non privilégié à qui on n'a jamais donné `/dev/dri` ressemble exactement à une machine sans carte, et un pilote absent aussi, et un compte sans le droit d'ouvrir l'appareil aussi. L'outil les formule toutes les trois pareil, et elles se réparent à trois endroits différents. |
| Preuve de la conversion des couleurs | Un échantillon est **encodé** avec les chiffres de l'écran d'étalonnage écrits dedans, et c'est lui qui sert à l'essai, pas une image fabriquée à la volée | Le filtre de conversion ne demande pas une image étiquetée large gamme : il demande ces chiffres, parce que c'est de là qu'il part. Une image fabriquée n'en a aucun et aucun filtre ne peut en ajouter : l'essai répondait donc « cette carte ne convertit pas les couleurs » sur toutes les cartes qui le font. Constaté sur la carte du mainteneur, qui passait les quatre autres essais. Conséquence assumée : un vrai film HDR qui ne porterait pas ces chiffres, ce qui arrive, sera refusé par la carte en cours de lecture et repassera une fois sur le processeur. |
| Décodage sur la carte | La carte lit le film elle-même **dans les codecs qu'elle a prouvé savoir lire**, établis un par un comme pour l'encodage. Dans les autres, le processeur lit et remonte l'image | Lire et écrire sont deux capacités distinctes et deux listes distinctes : une carte lit des codecs qu'elle ne sait pas écrire, et la génération qui a su écrire l'AV1 le lisait depuis des années. Un film dans un codec non prouvé passe par le processeur, ce qui marche quel que soit le fichier et déplace quand même la moitié chère du travail. |
| Échantillons des essais de lecture | Écrits **par la carte elle-même** là où elle sait écrire le codec, et par l'encodeur logiciel dix bits pour le HEVC | Sinon la question devient « cette compilation porte-t-elle un encodeur logiciel pour ce codec », et une carte parfaitement capable serait déclarée incapable parce que ffmpeg n'a pas été compilé avec de quoi fabriquer le témoin. Pour le HEVC l'échantillon dix bits est le bon témoin : c'est ce que sont les films qui valent la carte, et savoir lire huit bits ne prouve rien sur dix. |
| Disposition de l'image rendue par la carte | Quand la carte a lu le film, une passe sur la carte remet l'image dans la disposition que l'encodeur accepte, sauf quand la conversion des couleurs s'en charge déjà. Et un redimensionnement placé avant une conversion ne l'aplatit pas : la conversion part de ces bits-là | Une carte rend le film dans la disposition où il est écrit, et tout ce qui vaut une carte est écrit avec dix bits par canal quand l'encodeur en prend huit. Mesuré sur la vraie carte : elle lisait le film parfaitement et l'essai concluait qu'elle ne savait pas le lire, parce que le refus arrive au bout de la chaîne et pas à la lecture. D'où la règle générale : **un essai passe par la chaîne entière d'un vrai film, jamais par un morceau**. |
| Repli quand la carte refuse | Une **échelle** de barreaux, du plus ambitieux au moins : la carte lit et reconstruit, puis la carte reconstruit seulement, puis tout au processeur. Un barreau par refus, jamais deux fois le même | Les barreaux ne se valent pas. Une carte qui refuse de lire un film reconstruira quand même son image très bien, et abandonner la carte entièrement au premier refus jetterait l'essentiel de ce qu'elle faisait. |
| Quand la carte n'est pas employée | Une carte qui ne sait pas convertir les couleurs larges est écartée de ces films-là et pas des autres ; des mots incrustés dans l'image gardent le film sur le processeur ; une carte qui n'a pas produit le codec plancher à l'essai n'est pas employée du tout | Une carte qui rendrait un film gris est pire qu'un film simplement plus petit. Incruster des mots se fait là où sont les mots. Et une carte qui ne porte pas le codec que tout le monde lit laisserait des clients sans rien : mieux vaut pas de carte du tout qu'une carte qui sert la moitié des spectateurs. |
| Si la carte refuse en cours de route | La session repasse **une fois** sur le processeur, en l'écrivant au journal avec la phrase de l'outil, puis reste dessus | L'essai du démarrage porte sur une image fabriquée : c'est le bon sens de la preuve, mais ça ne prouve pas chaque film. Un pilote refuse une taille, une disposition de couleurs, un film auquel personne n'a pensé. Ce refus ne doit pas arriver au spectateur sous forme d'écran noir. Une seule fois, parce qu'une carte qui a refusé ce film le refusera encore et que deux essais coûtent deux attentes pour le même résultat. |
| Codec d'une image reconstruite | Le meilleur que le client **et** la carte portent tous les deux, dans l'ordre AV1, HEVC, H.264. En logiciel, toujours H.264. Un client qui n'a rien mesuré reçoit H.264 | Une carte produit les trois à peu près à la même vitesse : les récents ne coûtent donc rien ici et valent beaucoup pour qui a demandé un flux plus léger. En logiciel c'est l'inverse : AV1 et HEVC sont hors de portée en temps réel. Et produire un codec sur une supposition fausse donne un écran noir sans message. |
| Ce que le client sait lire | Deux questions distinctes : ce que le navigateur ouvre tout seul, et ce qu'il accepte **morceau par morceau**. Posées séparément au navigateur, transmises séparément au serveur | Ce sont deux parties différentes du navigateur qui répondent, et elles ne répondent pas toujours pareil. La seconde seule décide de ce qu'une image reconstruite peut être. |
| Réglage d'une carte | Toujours par un débit, jamais par une qualité | Chaque codec compte la qualité sur une échelle qui lui est propre sur une carte : le même nombre veut dire trois choses différentes pour les trois codecs. Un débit veut dire la même chose pour tous les trois. |
| Choix de qualité par le spectateur | Une échelle fixe de barreaux (taille et débit ensemble), le film tel qu'il est en haut et par défaut. Le choix devient un plafond dans le profil client et est retenu d'un film à l'autre | Personne ne veut taper un débit en bits par seconde. Un débit seul sur une grande image donne une image baveuse, une taille seule laisse le débit où il est tombé : les deux vont ensemble. Et un film déjà sous le plafond est servi tel quel plutôt que reconstruit pour l'atteindre. |
| Débit de référence d'un fichier | Le débit de l'image quand le fichier l'annonce, sinon celui du fichier entier | La plupart des films d'une collection n'annoncent aucun débit par piste. Une limite qui ne fait silencieusement rien sur la plupart des films est pire qu'une limite absente : quelqu'un la règle, ne voit rien changer, et en conclut que le réglage est cassé. Le débit du fichier entier compte aussi le son, donc il est un peu haut : c'est le prix d'un réglage qui marche. |
| Arrêt de l'outil quand on saute | Arrêté **là où il en est**, sans lui demander de finir, et ce qu'il laisse à moitié écrit est effacé tout de suite | Tout ce qu'il faisait devient sans valeur à la seconde où quelqu'un saute ailleurs. Mesuré sur un vrai film : la demande polie coûtait entre 450 et 900 ms de l'attente du spectateur, à chaque saut. Effacer le segment inachevé achète exactement ce que la politesse achetait, un fichier à moitié écrit servi tel quel plus tard, pour le prix d'une suppression de fichier. |
| Un film qui dit qu'une partie de son cadre n'est pas son image | **Les marges annoncées sont lues et gardées, et tout ce qui raisonne sur la forme de l'image travaille sur l'image et non sur le cadre.** Et pour ces fichiers-là seulement, **la carte ne lit pas le film** : le processeur le décode, coupe les marges au passage, et remonte l'image à la carte qui l'encode. La carte reste ce qui reconstruit l'image, elle cesse seulement de la lire | Un fichier peut porter son image dans un cadre plus grand et dire, à côté de l'image plutôt que dedans, combien de lignes retirer de chaque bord. La taille qu'il annonce est alors celle du cadre, pas celle de l'image, et les deux n'ont pas la même forme. Prendre l'une pour l'autre transforme un film large en film haut : la même image, étirée pour remplir un cadre qui n'a jamais été le sien. Constaté sur un film d'une médiathèque, où la fiche d'information affichait le cadre, les miniatures montraient l'image juste parce qu'elles décodent vraiment, et la lecture par la carte sortait l'image étirée d'un tiers en hauteur. Les autres serveurs affichent le cadre eux aussi sur leur fiche, et lisent le film correctement : la différence est au décodage, pas à la description. Une carte rend ses images en cadres entiers et rien ensuite ne sait en couper les bords, alors que le décodeur logiciel les coupe en lisant. Le coût est réel : **mesuré chez le mainteneur, un film 4K HDR à vingt-cinq mégabits par seconde occupe environ soixante-cinq pour cent de douze fils** pendant la lecture. L'estimation faite avant, un cœur et demi, venait d'une mire de synthèse à 3,4 fois le temps réel sur quatre cœurs : une image de synthèse se décode bien plus vite qu'un vrai film, et l'écart est là. Le chiffre à retenir est celui mesuré sur un vrai film. La carte, elle, n'a plus qu'à encoder au lieu de lire et d'encoder, ce qui la soulage. Le point à surveiller est le passage des images vers la carte, de l'ordre de six cents mégaoctets par seconde. L'autre route, couper sur la carte elle-même, demande de faire passer l'image par un second dispositif parce que le filtre de redimensionnement ne sait pas couper : elle reste à faire si le bus ne suit pas. |
| Quand un segment est réputé fini | **La forme du fichier répond, et rien d'autre.** Un segment est une suite de boîtes annonçant chacune sa longueur, et il est fini quand la dernière finit exactement où finit le fichier. Qui l'a écrit, et si un outil travaille à cet instant, n'y changent rien | Les deux réponses précédentes étaient fausses, chacune à sa façon, et chacune a cassé un film net chez le mainteneur. Celle de l'outil d'abord : mesuré, il garde un segment entier en mémoire et le déverse d'un coup une fois qu'il en a dépassé la fin, par tranches d'un demi-mégaoctet. Le fichier n'existe donc jamais qu'à un moment où l'outil annonce déjà être au-delà, et tant que le déversement dure il s'arrête au milieu de ses propres images. Sur une machine chargée ça dure assez longtemps pour être attrapé : un cinquième de segment est parti au navigateur, qui a refusé le film et l'a redémarré au début. Celle du fichier suivant ensuite : vraie, mais en retard d'un segment de travail, puisque l'outil n'ouvre le fichier d'après qu'une fois qu'il a un segment entier à y mettre ; et elle supposait qu'un fichier présent juste après celui qu'on réécrit venait de la même lecture, ce qui est faux dès qu'une lecture est relancée quelques segments en arrière d'une autre. Relevé dans le journal : segment 594 rendu alors que l'outil était encore dedans, parce que 595 existait depuis une lecture d'une minute plus tôt. Lire les boîtes répond au premier instant où la réponse est oui, tient aussi quand un outil meurt sans qu'on ait pu nettoyer derrière lui, et coûte quelques lectures de huit octets quel que soit le poids du segment. |
| Ce qu'un arrêt a le droit d'effacer | **Un seul fichier : le plus récent que cette lecture-là a écrit.** L'outil ferme un segment avant d'ouvrir le suivant, donc un fichier qui en a un après lui est fini par construction. À qui appartient un fichier se lit sur le fichier, à l'heure où il a été écrit, comparée à l'heure où la lecture a été lancée ; les numéros ne disent rien, puisqu'une lecture relancée au milieu du film écrit par-dessus le début de ce qu'une autre y avait déjà fini | La règle d'avant effaçait tout ce qui suivait la position annoncée par l'outil, d'un seul tenant, jusqu'au premier fichier manquant. Deux erreurs : l'annonce arrive dix fois par seconde pendant que l'outil travaille à trente fois le temps réel, donc elle retarde ; et rien ne distinguait le travail de cette lecture de celui d'une autre. Relevé dans le journal du mainteneur : douze arrêts ont emporté cent soixante-six segments, dont douze au plus pouvaient être inachevés, un seul arrêt en emportant quatre-vingt-quatre, soit sept minutes de film à refaire. Le spectateur qui revient en arrière retombe alors sur du film déjà produit et effacé derrière lui, et attend une seconde fois. Ne plus se servir de l'annonce supprime le retard au lieu de le compenser. |
| Cadence des rapports de l'outil | Dix fois par seconde, au lieu du défaut | C'est sur cette annonce qu'on décide d'attendre l'outil là où il est ou de le relancer ailleurs, et c'est elle qui nourrit ce que la page montre d'une lecture qui démarre. Au rythme par défaut, une annonce vaut pour la seconde écoulée, pendant laquelle l'outil peut produire une demi-minute de film : la décision se prend alors sur une position qui n'est plus la sienne. Ça coûte une ligne de texte de temps en temps. Elle ne sert plus à dire qu'un segment est fini, ce que la forme du fichier dit mieux qu'elle. |
| Les films les plus lourds, dans le rapport | **Les dix fichiers les plus lourds de la médiathèque, écrits piste par piste** : image, chaque bande son et chaque piste de texte, avec tout ce que le fichier dit d'elles. Trié sur le poids, rien d'autre. Un fichier absent du disque est exclu | Un serveur ne se teste pas sur ses films ordinaires mais sur ses pires, et on ne sait pas lesquels c'est tant qu'ils ne sont pas nommés. Le poids est la seule mesure qui ne demande ni lecture ni règle à se mettre d'accord : un fichier est gros à cause de ce qu'il y a dedans. Écrit en détail plutôt que résumé, parce que la question à laquelle ça sert à répondre est « est-ce qu'un autre serveur en fait la même chose », et deux serveurs sont d'accord sur le titre de la ligne et divergent sur les détails. Le rapport nomme les films ; ce que Melyxar décide pour chacun se lit ensuite dans le panneau des données de lecture, au moment de le lancer. |
| Conversion des couleurs d'un film HDR | **La règle automatique ne bouge pas** : un film à large gamme est converti parce qu'aucun navigateur ici ne l'affiche correctement, et c'est le comportement par défaut. Ce qui s'y ajoute est un **refus possible du spectateur**, à deux endroits : un interrupteur **pendant la lecture**, valable pour cette lecture-là, et un réglage **dans ses paramètres** disant de ne jamais convertir, qui devient son défaut. Décoché par défaut dans les deux cas | Le serveur ne peut pas savoir ce qu'il y a devant l'écran. Sur un PC dont l'écran est en HDR et dont le système l'a activé, convertir fait perdre exactement ce que le film contient, et coûte en plus une reconstruction complète de l'image, puisque changer les couleurs oblige à redessiner chaque pixel. Deviner dans l'autre sens coûte cher aussi : un film servi tel quel sur un écran ordinaire est gris et délavé, et ça ne se remarque pas tout de suite. D'où le choix : la réponse automatique reste la bonne par défaut, et la seule personne qui sait vraiment est celle qui regarde. Un cas à traiter à part : une image Dolby Vision de profil 5 servie sans conversion n'est pas délavée, elle est verte et violette, donc l'interrupteur doit prévenir à cet endroit plutôt que laisser quelqu'un casser sa lecture sans comprendre. Et le refuser ne donne pas la lecture directe pour autant : le film peut rester reconstruit pour son codec, son son ou ses sous-titres. **À faire**, jalon 8. |
| Ce que la machine est en train d'abattre | **Images par seconde et vitesse par rapport au temps réel**, lues sur l'outil lui-même et renvoyées avec l'état de préparation de la lecture. Le panneau des données de lecture les demande **une fois par seconde, et seulement tant qu'il est ouvert**. Rien n'est annoncé tant que l'outil n'a rien dit, ni une fois qu'il a fini : ce qui est montré est le travail de cette seconde-ci. Sous 1×, le nombre passe en couleur | C'est le seul chiffre qui dit si le matériel suit, et il n'existait nulle part : ni dans l'interface, ni dans le journal autrement qu'à la fin d'un segment. Sous 1×, la machine produit le film moins vite qu'il ne se regarde, et l'image finira par s'arrêter ; au-dessus, elle prend de l'avance. Les deux chiffres ensemble parce qu'aucun ne répond seul : les images par seconde sont le travail fait et ne veulent rien dire sans savoir quel film c'est, la vitesse est ce travail rapporté à ce que coûte le regarder. Une image simplement recopiée n'est pas dessinée, l'outil ne compte alors aucune image par seconde et seule la vitesse est montrée. Mesuré ici sur une reconstruction complète en 1080p : 36,7 images par seconde à 1,58× le temps réel, rafraîchi en continu. |
| Ce que la page a vu | La page peut écrire dans le journal du serveur, sous l'étiquette `page`, mais **elle ne choisit pas ses mots** : elle envoie un fait d'une liste fermée définie par le serveur, qui n'accepte rien d'autre, et le serveur le rédige lui-même. Route de l'API ordinaire, réservée à un spectateur connecté, taille bornée. Les faits : où la bibliothèque de lecture a décidé de commencer le film, à côté de ce que la playlist lui avait dit et du premier segment demandé ; le saut d'un spectateur, avec les deux bouts ; le film qui s'arrête faute d'avoir quelque chose à montrer, avec la tranche que le navigateur tient autour et le nombre de morceaux séparés qu'il tient ; le film qui repart ; **la forme de l'image que le navigateur a réellement reçue**, dans ses propres termes, à côté de la taille de la boîte où la page la dessine ; **le temps qu'un saut met à remettre une image à l'écran**, lu sur une image que le navigateur dit avoir posée et non sur une image qu'il a décodée, à côté de la mention de savoir s'il tenait déjà l'endroit visé ; l'horloge qui avance pendant que l'image reste figée, comptée en images montrées et non regardée, parce que de l'extérieur une image figée avec le son qui continue et un film complètement arrêté sont la même plainte et deux pannes différentes ; et le cas où la bibliothèque abandonne un film, dans ses propres mots, avec la mention de savoir si le navigateur a pris le relais. Ce second fait est **le seul qui porte du texte et non des nombres**, parce que les mots sont la réponse : c'est la bibliothèque qui nomme ce qu'elle n'a pas su faire d'un film produit par ce serveur. Le serveur le tronque, et cela reste un fait qu'il a nommé. Ajouter un fait est un changement du serveur, jamais une décision du navigateur | La moitié de ce qui se passe à la lecture se passe dans le navigateur, et le journal n'en montrait rien : le serveur disait avoir demandé de commencer à la dix-septième minute, la page demandait le début du film, et aucune trace ne disait lequel des deux se trompait. Mesuré au navigateur sur la playlist exacte du serveur : la bibliothèque saute bien au bon endroit, donc le désaccord est ailleurs, et il n'y a aucun moyen de le voir sans cette ligne. Liste fermée plutôt que texte libre parce que c'est la seule garantie qui tient vraiment : une page ne peut pas raconter au journal ce qu'elle n'a pas le vocabulaire de dire, quoi qu'il arrive dans le navigateur. Cela vaut aussi comme promesse au mainteneur : **rien de ce qui se passe hors de Melyxar ne peut atterrir dans ses journaux**, ce que la règle des origines du navigateur garantissait déjà, et que le vocabulaire fermé rend vérifiable en lisant trente lignes de code. |
| Codec d'une image reconstruite | Le client annonce, **pour chaque codec, jusqu'à quelle taille il le décode sans saccader**, mesuré sur la machine et non déduit du nom du navigateur. Le serveur prend alors le meilleur codec dont la limite couvre la taille qu'il va produire. Rien n'est écrit en dur sur un codec ni sur une taille : la réponse change avec la machine, et le jour où le spectateur regarde depuis un autre appareil elle change toute seule | « Tu décodes AV1 ? » et « tu décodes ce film-là, en 4K, en temps réel ? » ne sont pas la même question, et seule la seconde compte. Constaté chez le mainteneur : un film reconstruit en AV1 mettait tous ses morceaux en mémoire sans jamais montrer une image en 4K, et se lisait parfaitement en 1080p, même codec et même chemin. Les navigateurs savent répondre à la vraie question : on leur donne le codec avec la taille, le débit et la cadence, ils répondent s'ils décodent, si c'est fluide, et si c'est la puce dédiée qui travaille. Le principe est celui du projet depuis la revue d'architecture, le moteur de décision prend le profil du client en entrée ; il n'était appliqué qu'à moitié, le client répondant par oui ou non là où il pouvait répondre par une limite. Une règle du genre « pas d'AV1 au-dessus de 1080p » aurait été fausse sur la machine suivante. |
| Où un saut peut atterrir | **Décidé et fait.** Le film est lu une fois, à l'analyse, pour relever les endroits où son image se suffit à elle-même, et la playlist est découpée là plutôt que sur une grille arbitraire. Un film qui n'a pas encore été lu, ou qui n'a rien donné, garde la grille fixe : une lecture qui marche mal vaut mieux qu'une lecture impossible | Une image recopiée ne peut commencer que là où le film a déjà une image complète, et une image reconstruite en reçoit une à chaque frontière, posée par le serveur. La grille n'était donc vraie que dans le second cas : dans le premier, le serveur annonçait un segment commençant à une seconde et en servait un commençant six secondes plus tôt, mesuré. Deuxième effet, moins évident : coupé aux bonnes positions, l'endroit demandé est lui-même une image complète, donc l'outil démarre exactement là et son compte redevient croyable, ce qui raccourcit aussi l'attente. Relever coûte une lecture complète du fichier, d'où un travail de fond de l'entretien, repris là où il s'était arrêté, jamais sur le chemin de lecture. Lire directement l'index du conteneur, ce que fait Jellyfin pour les fichiers Matroska, serait bien plus rapide et reste à faire. |
| Où l'on coupe une image recopiée | **À chaque image clé, toutes, sans longueur minimale**, et l'outil reçoit une longueur visée plus courte qu'un intervalle d'images clés pour qu'il coupe là aussi. C'est la seule règle dont la réponse ne dépend pas de l'endroit où l'outil a été lancé, et un saut relance l'outil n'importe où. Le serveur ne devine plus la règle de découpe de l'outil : il en choisit une que l'outil ne peut appliquer que d'une seule façon | La règle d'avant posait une coupe à la première image clé assez loin de la précédente. Elle avait l'air d'être celle de l'outil. Elle ne l'est pas : mesuré sur un film fabriqué exprès, l'outil vise une longueur qui **avance d'un pas fixe à chaque coupe au lieu d'être remise à zéro**, donc dès qu'un segment dépasse le pas, la visée reste en retard et l'outil coupe ensuite à toutes les images clés. Trente segments annoncés, quarante-neuf produits, et le décalage entre ce que la playlist annonçait et ce que le fichier contenait atteignait **deux minutes après cinq minutes de film**. Seuls les films portant deux images clés à moins de la longueur visée sont touchés, ce qui explique qu'un seul film d'une médiathèque parte en vrille pendant que les autres vont bien : une comédie à coupes rapides en porte, un film ordinaire non. Le symptôme est exactement celui qu'a décrit le mainteneur : le début juste, l'image de plus en plus en retard sur la barre, et la fin qui s'arrête alors qu'il reste vingt minutes. |
| Ce qu'on sert d'un segment | **Entier ou attendu.** Un fichier qui existe ne suffit pas : l'outil est peut-être en train de l'écrire à cet instant, et on attend alors qu'il l'ait fini, exactement comme pour un segment qui n'existe pas encore | Un segment coupé au milieu est servi à un navigateur qui en montre le début puis plus rien jusqu'au segment suivant. Constaté chez le mainteneur : un saut en avant est tombé pile là où l'outil était arrivé, l'image est restée figée cinq secondes avec le son qui continuait, et elle est revenue à la seconde exacte où le segment d'après commençait. Une fois sur deux, parce que cela dépend de si l'on tombe sur celui qui s'écrit. C'est la même panne que celle des sous-titres servis depuis le cache pendant leur écriture, et la même réponse. Le chemin lent vérifiait déjà qu'un segment était fini ; le chemin rapide, celui qui sert ce qui est déjà là, ne vérifiait rien du tout. |
| Ce que le navigateur tient quand on saute | **Gardé quand on atterrit dedans, jeté sinon.** Un saut qui tombe dans un morceau de film que le navigateur tient déjà le laisse tranquille : il y cherche sa place et affiche tout de suite, ce sur quoi repose tout lecteur au monde. Un saut qui tombe ailleurs vide ce qu'il tenait, puisqu'il n'y a rien à perdre et que le film d'avant ne sert plus à rien. Les coutures qui restent, le navigateur les enjambe seul : on lui dit d'accepter un trou d'un demi-seconde au lieu du dixième qu'il prend par défaut | **Première version : tout jeter à chaque saut. Mesuré ensuite comme pire que le mal soigné.** Vidé d'abord, le navigateur doit se faire re-servir le même film et repartir à froid au milieu d'un groupe d'images, et il n'affiche alors plus rien jusqu'à l'image complète suivante : constaté quatre fois de suite, entre deux secondes et demie et cinq secondes, **avec une seule tranche tenue sans le moindre trou, commençant avant l'image complète et allant trente cinq secondes au delà du spectateur, et le navigateur annonçant qu'il avait tout ce qu'il lui fallait**. Le mal soigné, lui, était la couture entre deux lectures du film : l'image recopiée telle quelle se recolle au millième, le son reconstruit tombe jusqu'à une trame entière à côté, une vingtaine de millièmes. Le dixième de seconde que la bibliothèque accepte par défaut se mesure depuis l'endroit où le film en est et non en travers du trou, si bien qu'un trou de six centièmes atteint avec un vingtième encore à jouer compte pour plus d'un dixième : mesuré, et cela coûtait deux secondes d'attente avant l'enjambement. Un demi-seconde couvre la couture largement et reste bien trop court pour enjamber quoi que ce soit qu'un spectateur remarquerait. Les autres serveurs évitent la couture en ne mélangeant jamais deux productions ; ici on la tolère, ce qui revient moins cher qu'un navigateur remis à froid. |
| À quelle cadence on guette un segment | **Toutes les dix millisecondes**, au lieu de cent vingt. Le délai d'attente que s'accorde une demande d'en-tête avant de lancer l'outil elle-même est devenu une vraie durée, au lieu d'être « un tour de guet » | Une attente se termine quand le fichier demandé est entier. Guetter lentement ne raccourcit pas l'attente, ça l'arrondit au tour suivant : relevé dans le journal du mainteneur, **toutes les attentes sans exception tombaient sur un multiple de cent vingt et un millièmes**, et un segment déjà fini coûtait encore un tour entier avant d'être rendu, sur chaque segment de la lecture. Mesuré ici sur un film d'essai : la production d'un segment passe de 128 à 101 ms, et la part « apparition » cesse de mentir, 77 ms réels au lieu de 121 annoncés. Un tour de guet, c'est un verrou, deux nombres et un coup d'oeil au dossier : rien à côté de produire du film. Regarder plus souvent ne peut pas faire servir un fichier à moitié écrit : ce qui est rendu est entier ou attendu, et c'est le fichier lui-même qui le dit à chaque coup d'oeil. |
| La forme de l'image, des deux côtés | **Le serveur écrit la forme que le film contient** (combien de pixels en largeur et en hauteur, et en quelle forme ils doivent être montrés) **au moment où il décide une lecture ; la page écrit la forme que le navigateur a reçue**, plus la taille de la boîte où elle est dessinée | Les deux ne sont pas la même chose : un film peut contenir des pixels qui ne sont pas carrés, donc une image de 854 points de large se montre bien plus large que ça. Un film montré étiré, c'est ces deux formes qui ne concordent plus, et rien nulle part ne disait laquelle des deux était juste ni où la forme s'était perdue. Les trois endroits possibles se distinguent maintenant d'un coup d'oeil : le film lui-même, ce qui est ressorti de la reconstruction, et la boîte que la page dessine. Vérifié de bout en bout sur un film aux pixels non carrés : le serveur annonce 854 sur 480 montré en 7:3, le navigateur reçoit 1120 sur 480, ce qui est exactement 7:3. |
| Ce que coûte un saut, vu du spectateur | **Mesuré de bout en bout par la page**, du dernier mouvement de la main jusqu'à l'image posée à l'écran, avec la mention de savoir si le navigateur tenait déjà l'endroit visé | Le serveur sait quand il a produit un segment et quand il l'a rendu ; il ne sait rien de la suite. Le spectateur, lui, ne compte que l'attente entre le moment où il lâche et le moment où il revoit le film, et ce nombre-là n'existait nulle part. Mesuré ici sur un film de découpe identique à celui du mainteneur : un saut à froid coûte entre 260 et 450 ms, dont environ 130 ms de production côté serveur, et un saut qui retombe dans du film déjà tenu coûte entre 4 et 26 ms. Les deux ne doivent jamais être lus comme un seul nombre, d'où la mention. Sur la machine du mainteneur le même saut coûtait près d'une seconde : tout le chemin y est plus lourd, et sans cette ligne il n'y a aucun moyen de dire quelle part vient du serveur, du réseau ou du navigateur. |
| Où l'outil est lancé pour un saut | Au **milieu du segment demandé**, pas à son début. La recherche en arrière sert de toute façon l'image clé qui précède, et le milieu la désigne sans ambiguïté | Mesuré : demander exactement l'horodatage d'une image clé sert l'image clé **d'avant**, donc chaque saut décalait tous les segments suivants d'un cran pour le reste de la lecture. Demander quatre-vingts millièmes plus tard tombait juste. Le milieu du segment est la même idée sans nombre magique : il est forcément après l'image clé voulue et avant la suivante. |
| Extraction des sous-titres | **Une seule lecture du film pour toutes ses pistes de texte.** Demander une piste les sort toutes, un seul outil, une sortie par piste, et un film n'est lu qu'une fois à la fois | Le coût n'est pas l'écriture, quelques dizaines de kilo-octets de texte : c'est que les mots sont mêlés à l'image d'un bout à l'autre, donc le fichier doit être traversé en entier. Une passe par piste traverse le film autant de fois qu'il porte de pistes, et le spectateur qui choisit la dernière attend toutes les autres. Mesuré sur un film à sept pistes : 575 ms en sept passes contre 89 ms en une, pour un résultat identique à l'octet près. C'est aussi ce que fait Jellyfin, vérifié dans son code plutôt que supposé. |
| Ce qui entre dans un cache | Un fichier de cache est écrit **à côté**, sous un nom que rien ne va chercher, et mis en place d'un seul geste une fois fini. Ce que le cache expose est donc toujours entier, jamais en cours d'écriture, et ce qu'une tentative ratée laisse derrière elle est effacé | L'outil écrit au fil de sa lecture. Sous son nom définitif, un fichier existe donc bien avant d'être fini, et la question « est-il déjà converti ? » répond oui à un fichier qui n'a que le début du film dedans. Constaté dans le journal du mainteneur : une piste demandée une seconde après le début d'une lecture qui en a duré huit a été servie depuis le cache alors que l'outil écrivait encore, avec les sous-titres des premières minutes et plus rien ensuite. Le mettre en place d'un seul geste ne coûte rien et supprime la question : celui qui demande pendant la lecture attend la fin au lieu de lire par-dessus l'épaule. |
| Miniatures de la barre de lecture | Une image toutes les **dix secondes**, large de 320 pixels, rassemblées **par cent** dans des planches JPEG de dix sur dix. Une seule lecture du film en produit toutes les planches : les images clés seules, sur la carte quand elle sait lire le codec, avec conversion des couleurs pour un film large gamme. Le nombre de miniatures est **compté sur ce qui est vraiment sorti de la lecture**, jamais calculé depuis la durée annoncée. Travail de fond de l'entretien, après les images clés, repris là où il s'était arrêté ; rangées dans le cache, régénérables | Un film de deux heures fait sept cent vingt miniatures. Une par fichier, c'est sept cent vingt requêtes pour glisser le long d'une barre, et un navigateur qui en lance quarante par seconde pendant un glissement. Une planche de cent couvre mille secondes de film en une requête, et la suivante est chargée avant d'être atteinte : c'est ce que font Jellyfin et Emby, pour cette raison. Les images clés seules parce que le coût est le décodage : mesuré ici, 4,4 fois plus rapide, et sur trois cents films en 4K c'est la différence entre une nuit et une semaine. Compté plutôt que calculé parce que les deux ne tombent pas juste : la durée annoncée par un conteneur est fausse assez souvent pour qu'on ne bâtisse rien dessus, et un film dont la dernière tranche n'est pas entière rend une miniature de moins que sa durée ne le laisse croire. Une seconde sortie d'un pixel par miniature donne le compte exact dans la même lecture. Enfin l'image retenue pour un créneau est celle **du repère lui-même** : par défaut le filtre rend la dernière image de la tranche, et mesuré sur un film portant l'heure écrite dedans, la vignette du tout début montrait quatre secondes et neuf dixièmes, toutes les suivantes décalées d'autant. |
| Un lecteur qui recule pas à pas | **Le premier pas en arrière est servi là où il demande ; à partir du deuxième d'affilée, la lecture est lancée une poignée de segments plus tôt** et couvre d'un coup la tranche dans laquelle le lecteur avance à reculons. Un pas en arrière, c'est une demande du segment situé juste avant celui où l'outil vient d'être lancé ; un spectateur qui tire le curseur atterrit n'importe où et ne fait donc jamais deux pas de ce genre à la suite | L'outil ne va que vers l'avant, donc tout ce qui est derrière lui le fait repartir de zéro. Relevé dans le journal du mainteneur : la bibliothèque de lecture du navigateur s'est mise à réclamer les segments à l'envers, 578 puis 577 puis 576, soixante-cinq fois en vingt-deux secondes. Chaque demande arrêtait l'outil et en relançait un pour un seul segment, à 300 ms l'unité, et l'image est restée figée jusqu'à ce que le mainteneur ferme le lecteur. Le premier pas reste servi au plus vite parce qu'il peut être tout ce que le lecteur voulait, et qu'élargir tout de suite triplerait l'attente de n'importe quel saut en arrière. Le deuxième pas dit que le lecteur marche : les six suivants sortent alors de la même lecture et ne coûtent plus rien. Ce qui pousse la bibliothèque à reculer ainsi est une autre question, encore ouverte : elle recule tant qu'elle ne trouve pas un segment commençant par une image complète. |
| Ce qu'un arrêt n'a pas le droit d'effacer | Le fichier le plus récent d'une lecture arrêtée n'est effacé que **s'il est vraiment inachevé** : la forme du fichier répond, comme partout ailleurs ici, et l'outil est déjà arrêté quand on la lui demande | Être le plus récent n'est pas une preuve. Une lecture qui a atteint la fin du film, ou qui a fermé son segment juste avant d'être arrêtée, laisse un fichier entier. Relevé dans le journal du mainteneur : une lecture avait produit le film jusqu'à son tout dernier segment, et ce dernier segment a été emporté comme s'il avait été attrapé en pleine écriture. Le spectateur qui va à la fin le repaie. |
| Qui tient le film | **Le moteur, et lui seul.** L'élément vidéo lui appartient : tout ce qui déplace le film, règle le son, le démarre ou l'arrête, et tout ce qui écoute ce que l'élément raconte, passe par lui. Ce qui dessine le lecteur reçoit une référence à poser sur l'élément, des nombres à afficher et des fonctions à appeler, et rien d'autre. Seule exception, assumée : la hauteur d'une ligne de sous-titre, qui est écrite sur la ligne elle-même et qu'aucune feuille de style ne peut atteindre | La séparation précédente avait sorti le gros du moteur mais laissé trois choses derrière : la barre posait l'aiguille elle-même, les sous-titres étaient attendus et surveillés depuis le fichier de l'interface, et le son comme la lecture étaient câblés directement sur l'élément depuis les boutons. Tant que deux endroits bougent le film, ils finissent par ne pas être d'accord : mesuré, une flèche du clavier déplaçait le film de vingt secondes au lieu de dix parce que la page et la barre écoutaient la même touche. Et ce qui était accroché à l'élément depuis le dessin (position atteinte, point de reprise, image refusée par le navigateur) n'a rien à voir avec l'apparence : un lecteur redessiné sans les recâbler est un lecteur qui repart du début du film sans que personne sache pourquoi. Les écouteurs sont posés avant que le navigateur puisse toucher à l'élément, et non après, parce que ce décalage est exactement ce qu'est le point de reprise. |
| Ce qui déclenche une nouvelle session | **Une seule chose : ce que le serveur a dit qu'il produirait.** La décision et la qualité demandée sont les deux moitiés d'une même question et n'arrivent pas ensemble, donc la décision est gardée avec la qualité à laquelle elle répond, et rien n'est ouvert tant que les deux ne parlent pas du même barreau. La qualité, la piste sonore et le sous-titre incrusté ne réveillent plus la chose eux-mêmes : ils sont déjà dedans | Réveillée par le barreau lui-même, l'ouverture de session partait une première fois sur la décision de l'ancienne qualité, puis une seconde sur la nouvelle. Deux sessions pour un seul changement, mesuré au navigateur. Un sous-titre fait de mots ne déclenche toujours rien, ce qui est la règle d'avant et reste vérifié : changer de sous-titre n'ouvre ni ne ferme aucune session, changer de piste sonore en ferme une et en ouvre une. |
| Une demande d'ouverture n'est jamais abandonnée | **Seule requête de la page qu'on ne lâche jamais en cours de route.** Toutes les autres sont abandonnées quand le spectateur passe à autre chose ; celle-là est attendue jusqu'au bout, et la session est refermée tout de suite si plus personne n'en veut | Le serveur ouvre la session pendant que la demande est en vol : l'abandonner jette le seul exemplaire de son nom. La réponse n'arrive jamais, la page n'a rien à fermer, et un outil reconstruit un film pour personne jusqu'à ce que le serveur balaie la session tout seul. Mesuré : un changement de qualité laissait une session orpheline à chaque fois, et la page se retrouvait sans lecture du tout, un lecteur figé sur « préparation » sans rien à montrer et sans rien à dire. Attendre coûte un aller-retour que personne ne regarde. |
| Ce qui a bougé le film | La ligne du saut porte **le geste qui l'a causé** : un clic sur la barre, un glissement de la barre, un pas fixe, le film remis où le spectateur l'avait laissé, ou rien de la page, c'est-à-dire le navigateur ou la bibliothèque de lecture qui a bougé le film toute seule. Liste fermée comme les faits eux-mêmes. Un seul endroit bouge le film, le moteur, et c'est lui qui le dit | Un clic et un glissement laissent le film exactement au même endroit et ne sont pas du tout le même geste : un glissement retient la bibliothèque tant que la main est posée et la relance une fois, un clic la retient et la relance dans le même souffle, et cliquer le long de la barre fait ça une fois par clic. Vu de la ligne du journal, les deux étaient identiques. Cas réel : une série de segments réclamés à l'envers a été mise sur le compte d'un glissement, et le mainteneur clique. Une panne poursuivie sur le mauvais geste est une panne corrigée au mauvais endroit. « Rien de la page » est le cas qui compte le plus : c'est le seul qui dit que personne n'a rien demandé. En vérifiant ce point on a trouvé au passage que les flèches du clavier bougeaient le film de vingt secondes au lieu de dix dès que la barre avait le focus, la page et la barre écoutant toutes les deux la même touche. |
| La barre de lecture | Dessinée par Melyxar, plus par le navigateur. Le lecteur garde ses propres commandes : lecture, position, son, plein écran, et la barre montre la miniature de l'endroit survolé | Une miniature au survol suppose de savoir où le curseur est sur la barre et d'y poser une image. La barre native du navigateur ne dit ni l'un ni l'autre : aucun événement, aucune position, rien à quoi accrocher quoi que ce soit. Elle était le bon choix tant qu'on ne lui demandait rien de plus, et la demander fait basculer le choix. C'est la raison pour laquelle Jellyfin, Emby et tous les autres dessinent la leur. |
| Comment on apprend où un film peut être démarré | **Dans l'index que le fichier porte déjà, quand il en porte un lisible.** Une crate `container` lit la table des images qui se suffisent d'un MP4, d'un MOV ou d'un M4V, et les repères de recherche d'un MKV ou d'un WebM, sans lancer le moindre outil et sans traverser le film. Tout le reste, conteneur inconnu, fichier fragmenté, index absent, index d'une forme dont le sens n'est pas certain, retombe sur la lecture du film de bout en bout, qui n'a pas changé. La crate ne rend jamais de réponse à demi sûre : elle répond, ou elle ne répond pas | Un lecteur de bureau saute instantanément dans un film parce qu'il lit cette table, pas parce qu'il a lu le film. Melyxar, lui, traversait chaque fichier en entier pour la même information, une fois par film et par bibliothèque, et c'est la passe qui fait durer un entretien des heures sur une grande médiathèque. Les deux chemins répondent exactement la même chose : vérifié position par position contre la lecture complète sur MP4, MOV, MKV et WebM, avec images B, listes de montage, décalages de composition négatifs, piste sonore placée avant l'image, H.264 et HEVC. Mesuré sur un film de 477 Mo, fichier déjà en cache donc au pire pour l'index : 1,8 ms en MKV et 0,7 ms en MP4 contre 431 ms de lecture complète, soit 239 et 611 fois moins, pour des listes identiques. Sur disque froid l'écart ne peut que grandir, l'index lisant quelques kilo-octets là où l'autre lit le fichier entier. Le point délicat est la liste de montage d'un MP4, que l'outil applique et qui décale tout le film de quelques centièmes si on l'ignore : mesuré, 83 millièmes d'écart sur un fichier ordinaire, donc toute forme de liste de montage qui n'est pas la forme simple fait renoncer plutôt que deviner. Deux familles couvrent ce qu'une médiathèque et un téléphone produisent, ce qui était la condition posée : le contenu personnel à venir est du MP4 et du MOV, et il est pris en charge le jour où il arrive sans rien changer ici. |
| Quand les sous-titres faits de mots sortent du film | **Pendant l'entretien, comme troisième tâche à côté des images clés et des vignettes**, et non plus à l'ouverture du film. Seuls les films portant une telle piste à l'intérieur entrent dans la file, et une ligne par fichier dit qu'il a été traversé : le cache est un dossier de fichiers nommés d'après les pistes et ne dit rien sur les films. Vider le cache efface ces lignes, les deux ne pouvant pas se désynchroniser. La lecture au moment de l'ouverture reste, en filet de sécurité pour un film ajouté depuis le dernier entretien | Les mots sont entrelacés avec l'image d'un bout à l'autre, donc les sortir demande de faire défiler le fichier entier : trois quarts de minute sur un film 4K. Déclenchée à l'ouverture, cette traversée tombait sur la seule personne qui attendait. Pas de bouton « pendant le scan » pour celle-ci, contrairement aux deux autres : les mots ne servent qu'à quelqu'un qui regarde, le film les réclame lui-même si l'entretien n'est pas encore passé, et rien n'est perdu à les laisser à la nuit ; un interrupteur ici serait un réglage sans question derrière. Les sous-titres en images ne passent jamais par là : il n'y a rien à convertir dedans, ils sont peints dans l'image au moment de la lecture. |
| Où s'arrête l'interface et où commence le moteur | **La même règle que pour le lecteur, appliquée à toute l'interface.** Un écran ne parle plus jamais au serveur lui-même : il reçoit des valeurs à montrer et des fonctions à appeler, et rien d'autre. Sous les écrans, trois étages : une seule façon de poser une question au serveur et d'en lire le refus (`asking.ts`), un moteur par écran (`screens/`) qui tient les questions, les rythmes et l'état, et les règles de lecture d'une valeur (`readable.ts`) rassemblées en un seul endroit. Les noms de langues sortent du dossier du lecteur : une piste sonore et la langue de description d'une bibliothèque n'ont rien à voir l'une avec l'autre | L'interface web sera refaite de zéro, et ce qui est enfermé dans un écran est réécrit avec lui. Relevé avant : le trio « contrôleur d'annulation, requête, annulation au départ » écrit **treize fois**, la ligne qui ignore une requête abandonnée **dix fois**, et la lecture d'un refus du serveur **huit fois sous trois formes qui ne concordaient pas**, dont deux copies littérales l'une de l'autre. Trois lectures d'un même refus, ce sont trois réponses à « que dit le serveur quand il dit non », et un écran écrit la semaine suivante hérite de celle qui a été recopiée. Environ 840 lignes de moteur vivaient dans onze composants. Résultat mesurable : il ne reste plus un seul `AbortController`, `DOMException` ou `ApiError` sous `pages/` ni sous `components/`. Un choix nommé au passage : un écran qui se relit tout seul sur son rythme ne touche à rien de ce qui est affiché tant que rien de neuf n'est revenu, alors qu'une demande faite par quelqu'un oublie le refus précédent et annonce qu'elle cherche ; sans cette distinction, le journal qui se relit toutes les deux secondes ferait clignoter un message d'erreur au nez de celui qui le lit. Vérifié comme l'avait été le lecteur : la forme entière de neuf écrans prise avant et après, caractère par caractère, avec les requêtes réellement parties, puis une série de gestes rejoués sur l'ancien et le nouveau code, identiques ligne pour ligne. Le fichier envoyé au navigateur grossit de 2,3 Ko sur 346, soit 0,65 %. |
| Ce qui fait un épisode | **Le marqueur d'épisode est la frontière du nom, comme l'année l'est pour un film.** Ce qui le précède est le nom de la série, le marqueur donne la saison et le numéro, ce qui le suit est le titre de l'épisode puis les marqueurs techniques. Formes reconnues par leur forme et non par une liste : `S01E02` et ses variantes de séparateur, `1x02`, la forme en toutes lettres dans les deux langues, l'épisode double `S01E01-E02`, et le numéro seul `E02` qui demande alors sa saison au dossier. Un nombre nu comme `102` voulant dire saison 1 épisode 2 est **refusé** | La règle de lecture des films dit « l'année est la frontière », et un épisode n'a presque jamais d'année dans son nom : appliquée telle quelle, elle lit `Serie.S01E01.1080p.mkv` comme un film intitulé « Serie S01E01 » et le cherche chez le fournisseur du côté des films, qui ne répond rien. C'est l'échec unique constaté sur les 327 fichiers d'une collection réelle. Un marqueur est une frontière plus sûre qu'une année : il ne peut pas être confondu avec l'année de sortie que quelqu'un a écrite dans le titre. Le nombre nu est refusé parce que sa forme est aussi celle d'une année, d'une résolution et d'un bout de titre : mal rangé, un fichier ne se voit pas, alors que non rangé il se voit et se corrige. |
| Ce que le dossier a le droit de dire | **Un dossier de saison dit que le dossier au-dessus est la série, et c'est alors lui qui la nomme.** Partout ailleurs le nom du fichier est lu en premier et le dossier ne fait que compléter. Donc : si le chemin passe par un dossier de saison, le dossier qui contient ce dossier de saison nomme la série, son nom et l'année qu'il porte, et tous les fichiers qu'il contient vont dans cette série-là, quelle que soit la façon dont chacun est nommé ; sinon la série est celle que nomme le fichier, et à défaut le premier dossier au-dessus. La saison vient du nom du fichier, et sinon du dossier de saison le plus proche, où qu'il soit dans le chemin. Un dossier de série est lu comme un nom de fichier l'est, mots techniques et année compris, sauf qu'il n'a pas d'extension à retirer. Formes de dossier de saison reconnues : `Saison 1`, `Season 01`, `S01`, et `Specials` ou saison zéro pour les hors-séries | Quatre rangements existent dans la vraie vie et il faut les quatre : un dossier par série avec un sous-dossier par saison, ce que fait le mainteneur et ce que recommandent les autres serveurs ; un dossier par série sans sous-dossiers ; tout en vrac dans un seul dossier ; et des dossiers de saison nommés dans n'importe quelle langue ou absents pour une série d'une seule saison. Lire le nom du fichier d'abord marche partout, sauf précisément là où quelqu'un a pris la peine de ranger : relevé sur la collection du mainteneur, une série dont la saison 1 vient d'une équipe qui la nomme par son titre anglais et la saison 3 d'une autre qui la nomme par son titre français s'est coupée en deux séries, dont une que le fournisseur ne reconnaissait sous aucun des deux noms. Un dossier de saison est la seule marque qui dise sans ambiguïté « ce qui est au-dessus est une série » : là où elle est présente, le dossier est ce que quelqu'un a voulu, et deux noms de fichiers qui se contredisent ne peuvent plus séparer ce qu'il a réuni. Là où elle est absente, rien n'a changé : un dossier fourre-tout ne regroupe toujours rien de force, et le vrac se lit toujours au nom du fichier. L'année suit le nom : quand c'est le dossier qui nomme la série, c'est lui qui donne l'année, donc tous les fichiers qu'il contient en donnent la même. C'est ce qui permet de continuer à chercher une série par son nom **et** son année, comme un film, et de garder ainsi séparées deux séries homonymes de deux époques : ce qui coupait une série en deux n'était pas l'année demandée, c'était l'endroit d'où elle venait, relue sur chaque fichier alors qu'un fichier la porte et le suivant pas. |
| Un numéro seul en tête de nom | **Dans un dossier de saison, et seulement là, un nom de fichier qui ne porte aucun marqueur mais commence par un nombre d'au plus trois chiffres donne le numéro de l'épisode**, le reste du nom étant son titre. Partout ailleurs, un nom sans marqueur reste un épisode qui n'appartient à rien, visible seul dans la grille | Relevé sur la collection du mainteneur : une série de cinquante-deux épisodes, rangée dans un dossier de série et un dossier de saison, dont les fichiers ne portent que `01 - Titre`. Sans cette règle, chacun de ces cinquante-deux fichiers devenait une œuvre à lui seul et la série n'existait nulle part. La règle ne mord que là où quelqu'un a déjà rangé : le dossier de saison a déjà dit la saison et le dossier au-dessus a déjà dit la série, donc un nombre en tête n'a plus qu'un sens possible. Trois chiffres au plus, parce qu'un quatrième est une année et jamais un numéro d'épisode. Le prix est dit franchement : dans un dossier de saison, un fichier sans marqueur dont le titre commence par un nombre verrait ce nombre pris pour son numéro. C'est toujours mieux que le fichier flottant seul, et le nom de la série, lui, vient du dossier de toute façon. |
| Les noms d'animés | **Dans une médiathèque d'animés, et seulement là, deux formes de plus donnent l'épisode quand aucun marqueur ordinaire n'a été trouvé** : le numéro après un tiret, `[Groupe] Titre - 12 [1080p][ABCD1234]`, et le numéro entre crochets, `[Groupe][Titre][12][1080p]`. Le numéro peut porter une révision (`12v2`) et quatre chiffres tant que ce n'est pas une année plausible. Une saison écrite juste avant le tiret est lue aussi : `Titre S2 - 05`, `Titre Season 2 - 05`, `Titre 2nd Season - 05`. Ce qui suit le numéro est le titre de l'épisode jusqu'au premier crochet, à la première parenthèse ou au premier mot technique. Les marqueurs ordinaires passent toujours en premier | C'est ainsi que presque toutes les sorties d'animés sont nommées, et aucune ne porte de `S01E02` : sans ces formes, chaque fichier devenait un épisode orphelin. Réservé aux animés parce que la même forme lue dans une médiathèque de séries ou de films refait l'erreur que la règle du nombre nu évite : `Titre - 2` y est aussi bien la suite d'un film. Un nombre collé au titre sans tiret n'est **pas** lu, contrairement à Jellyfin : `Titre 100` est trop souvent le nom même de la série. |
| La numérotation absolue des animés | **Un épisode d'animé dont ni le nom ni aucun dossier ne dit la saison porte un numéro compté sur toute la série, et il est retenu comme tel.** Il est d'abord rangé en saison 1 sous ce numéro. Quand la série est identifiée, le fournisseur dit combien d'épisodes compte chacune de ses saisons, ce nombre est gardé, et chaque épisode numéroté ainsi est replacé : le 29 d'une série dont la saison 1 en compte 28 devient le premier de la saison 2. Un numéro qui dépasse tout ce que le fournisseur compte continue la dernière saison. Un épisode arrivé après l'identification est placé directement grâce aux longueurs gardées. Un épisode dont le nom ou le dossier dit la saison n'est jamais déplacé | Le fournisseur range les animés en saisons, les fichiers les numérotent d'un bout à l'autre : sans ce pont, tout ce qui suit la première saison n'a ni titre, ni résumé, ni image. Le numéro d'origine est gardé plutôt que recalculé depuis la place actuelle, pour qu'une nouvelle identification, avec un autre découpage, replace tout correctement. Les longueurs sont gardées pour qu'un nouvel épisode ne demande pas au fournisseur de redire toute la série. Le fournisseur reste le même que pour les séries, qui est aussi le choix par défaut de Jellyfin pour les animés ; un second catalogue spécialisé appartient au chantier des fournisseurs multiples. Limite assumée : dans un dossier de saison, un numéro est toujours lu comme compté dans cette saison. |
| Photos et vidéos perso | **Un type de médiathèque à part, pour ce qu'on a filmé et photographié soi-même** : les vidéos et les photos d'un même dossier y vivent ensemble, comme chez Jellyfin. **Aucun fournisseur n'est interrogé** : ce qu'on a tourné soi-même n'est dans aucun catalogue. Chaque fichier est sa propre œuvre, nommée d'après son nom de fichier tel quel, sans la lecture des noms de sortie : `IMG_0042` reste `IMG_0042`, et deux fichiers de même nom dans deux dossiers ne sont jamais fusionnés | Les règles qui lisent un nom de film arrachent des mots et prennent des nombres pour des années ; sur `Vacances 2019 - plage.mp4` elles se trompent à coup sûr, et fusionner les `IMG_0001` de dix téléphones perdrait dix fichiers. Un fournisseur interrogé sur une vidéo de vacances ne peut répondre que faux. |
| Photos et vidéos perso sur l'accueil | **Jamais dans le bandeau du haut, jamais dans le rang « Récemment ajoutés » qui mélange toutes les médiathèques** : elles ont leur propre rang, en cartes couchées. Sur la page d'une médiathèque perso, elles restent évidemment là | Relevé par le mainteneur : mêlées aux films, elles prenaient la forme d'une affiche debout et coupaient la vidéo en son milieu ; les coucher dans ce rang aurait donné des cartes de tailles différentes côte à côte. Le bandeau est un mur d'affiches, et une vidéo de vacances n'en a pas. |
| Ce qui a sa place dans le bandeau | **Seulement une œuvre qui a tout ce que le bandeau dessine** : une grande image, son titre dessiné, un résumé et ses genres. Une œuvre à qui il manque une seule de ces choses est passée, et la suivante prend sa place, même si elle était épinglée ou en cours. Un épisode emprunte à sa série ce qu'il n'a pas | Relevé par le mainteneur : une œuvre sans image ni titre dessiné laissait un grand bloc vide en haut de l'accueil. Mieux vaut quatre œuvres complètes que cinq dont une trouée. |
| Photo de profil | **Chacun choisit la sienne dans ses réglages, la recadre et la zoome à la main dans une fenêtre, puis l'envoie** : le recadrage se fait dans le navigateur, qui envoie le carré choisi et rien d'autre ; c'est le premier fichier que le serveur reçoit d'un navigateur. Il n'accepte qu'une image (JPEG, PNG, WebP ou GIF, reconnue à son contenu et non à son nom), de 20 Mo au plus. L'outil vidéo la remet à l'endroit d'après l'appareil photo, la coupe au carré en son centre et l'écrit en une seule taille, 256 points de côté, sous un nom tiré de son contenu, dans les données du serveur et non dans le cache, puisque rien ne permettrait de la refaire ; l'image envoyée n'est pas gardée. L'ancienne est effacée quand on en change, et la photo part avec le compte. Elle est servie **sans connexion**, pour que l'écran de connexion la montre à côté du nom : c'est la même divulgation volontaire que la liste des noms, et un nom de fichier tiré du contenu ne se devine pas | Montrée carrée aux coins à peine arrondis, comme chez Emby, partout, en-tête compris. Recadrer dans le navigateur plutôt que d'envoyer l'image entière avec des coordonnées : le navigateur la voit déjà à l'endroit, le carré envoyé est donc exactement celui qu'on a vu, et une photo de dix mégaoctets part en quelques dizaines de kilos. Une seule taille suffit : le plus grand cadre qui la montre fait une centaine de points, deux fois plus sur un écran fin. La garder dans la colonne déjà prévue pour elle dans la table des comptes évite une question de plus à chaque page. |
| Accueil sans bannière | **Un réglage par compte, dans les réglages de la bannière, la retire de l'accueil**, qui commence alors par ses rangées. Affichée par défaut. Le serveur ne la calcule pas du tout quand elle est cachée, et les autres réglages de la bannière restent gardés, grisés, pour le jour où on la remet | Demandé par le mainteneur pour voir à quoi ressemble l'accueil sans elle. Ne pas la calculer plutôt que la cacher à l'écran : choisir et habiller ses œuvres est la partie la plus chère de la page, pour un résultat que personne ne verrait. |
| Barre du haut qui s'efface | **En descendant dans une page, la barre du haut glisse hors de l'écran ; au premier mouvement vers le haut elle revient, et elle reste tant qu'on ne redescend pas.** Tout en haut de la page elle est toujours là. Les petits tremblements de la molette ou du pavé tactile ne la font pas bouger, et elle ne part jamais pendant qu'un de ses menus est ouvert ou que la recherche est utilisée. Réglage par compte, dans l'apparence : « se cache en défilant » (par défaut) ou « toujours visible » | Demandé par le mainteneur. C'est le comportement qu'on appelle en anglais *hide on scroll* ou *headroom* : la page gagne toute la hauteur quand on lit, et la barre est là dès qu'on la cherche en remontant. Gardé par le compte comme les autres réglages d'apparence, pour suivre la personne d'une machine à l'autre. |
| Les dossiers d'une médiathèque perso | **La navigation suit les dossiers du disque.** Chaque dossier devient une œuvre « dossier » qui contient ses sous-dossiers, ses vidéos et ses photos ; la grille de la médiathèque montre ce qui est à la racine, et un dossier s'ouvre sur une grille de ce qu'il contient, classé par nom. Un même nom de dossier sur deux disques de la même médiathèque est un seul dossier, comme les dossiers de même nom forment une seule médiathèque. Un dossier montre l'image de la première chose qu'il contient qui en a une | Des photos n'ont pas d'autre ordre que celui qu'on leur a donné en les rangeant : un dossier par voyage, par année, par événement. Les mettre à plat dans une grille unique mélangerait mille photos sans rien pour s'y retrouver. Le modèle parent et enfant qui porte déjà les séries et les saisons porte aussi les dossiers, sans table de plus. |
| Ni identifiée ni en attente | **Un état d'identification de plus, « à soi »**, pour une œuvre qui n'est dans aucun catalogue et n'en attend aucun. Elle ne compte jamais parmi les œuvres en attente d'identification, n'est jamais proposée au fournisseur, et compte comme nommée partout où une œuvre identifiée l'est, par exemple pour les affiches du bandeau | Laissées « en attente », des milliers de photos auraient affiché pour toujours « en attente d'identification » et gonflé le compteur de l'accueil. Les marquer « identifiées » aurait menti, et « à la main » aussi : personne n'a rien choisi. |
| Les images d'un fichier perso | **Tirées du fichier lui-même, au scan.** Une photo est réduite en images de carte ; une vidéo donne une image prise au dixième de sa durée, après son analyse, pour éviter l'écran noir du tout début. L'orientation écrite par l'appareil photo dans le fichier est appliquée, sinon une photo prise en portrait apparaît couchée. La photo en grand est servie telle quelle, depuis le disque, et c'est le navigateur qui l'affiche | Aucun catalogue n'a d'image d'un fichier perso, et une grille de rectangles gris ne sert à rien. Préparer les tailles de carte une fois au scan suit la règle de toutes les autres images : le serveur ne redimensionne jamais à la demande. La photo en grand n'est vue qu'une fois à la fois : la préparer pour chaque photo doublerait la place prise sur le disque pour rien. |
| Les photos et l'entretien | **Une photo n'est jamais lue par les tâches faites pour les vidéos** : ni images clés, ni vignettes de la barre de lecture, ni génériques, ni sous-titres. Elle est analysée comme un fichier, ce qui donne sa taille | Ces tâches demandent une durée et un flux vidéo ; sur une photo elles échoueraient une fois par photo, à chaque passage, et le compteur de l'entretien ne descendrait jamais à zéro. |
| Regarder ses photos et ses vidéos | **Des cartes couchées** dans la grille et la rangée de l'accueil de ce type de médiathèque, parce que ce qu'on filme et photographie est surtout plus large que haut et n'a pas d'affiche debout. **Une vidéo s'ouvre en lecture directe depuis son dossier. Une photo s'ouvre en grand sur fond noir**, et les flèches du clavier ou de l'écran passent à la photo d'avant ou d'après dans le même dossier ; ce passage remplace la page au lieu d'en empiler une, et Échap ou le retour arrière ramène au dossier. Rien n'y propose d'identifier l'œuvre ni de choisir une image chez un fournisseur | C'est ce que fait Jellyfin, et ce qu'on attend d'un album : on feuillette. Empiler une page par photo obligerait à revenir cinquante fois en arrière après avoir regardé cinquante photos. |
| Dire qu'une image n'existe pas | **Une fois par œuvre qui a une vignette dans une grille, et une seule fois par série pour toutes ses saisons et tous ses épisodes.** Le bilan d'une série dit combien de ses parties le fournisseur n'a pas illustrées, sur combien | La ligne est utile : une œuvre sans image et une œuvre dont l'image n'est pas arrivée demandent deux gestes opposés, et sans elle les deux se ressemblent. Mais dite pour chaque partie d'une série, elle devient une ligne par fichier : relevé sur la collection du mainteneur, cinquante-deux lignes d'affilée pour une seule série dont le fournisseur n'avait aucune photo d'épisode. Un journal qu'on ne peut plus lire ne dit plus rien du tout. |
| Un fichier qu'on ne sait pas ranger | **Ne disparaît jamais.** Une saison s'ouvre depuis sa série et un épisode depuis sa saison, donc ni l'une ni l'autre n'apparaît dans une grille ; mais un épisode qui n'appartient à aucune saison se montre tout seul, faute de quoi il ne se montre nulle part | Le défaut existait déjà avant les séries : un fichier posé dans une bibliothèque de type séries devenait un épisode sans parent, et le filtre qui écarte les épisodes des grilles l'écartait aussi. Le fichier était scanné, analysé, stocké, et joignable par aucune page. Un fichier invisible est pire qu'un fichier mal nommé : le second se voit dans le rapport et se corrige, le premier ne se voit pas du tout. La règle vaut aussi pour la suite : un épisode dont le nom n'a pas livré de numéro reste visible plutôt que rangé au hasard. |
| Replier une piste, et la remonter | **On ne replie que ce qui est plus large que ce qui sort**, décidé d'après la piste de départ et non d'après la destination seule. **Le gain qui suit, lui, reste appliqué même à une piste déjà stéréo**, et c'est volontaire | La matrice de repliage nomme un centre et deux arrières qu'une piste stéréo n'a pas : appliquée à une piste déjà stéréo, elle rend exactement ce qu'on lui a donné, c'est un filtre qui n'avait rien à faire. Relevé dans le journal du mainteneur, demandé mot pour mot sur une piste stéréo. Le gain est une autre affaire. Il a été mis là pour compenser le repliage, qui baisse le niveau perçu, et il le fait. Mais il fait aussi autre chose : un film est masterisé bas, sa réserve gardée pour les explosions et pas pour les dialogues, et remis tel quel à un navigateur il sort très en dessous de tout le reste de la machine. Rapporté par le mainteneur sur deux autres serveurs, qui remontent une piste repliée et laissent une piste stéréo intacte : sur la même télévision au même réglage, leurs pistes stéréo sont presque inaudibles à côté de leurs pistes repliées, et c'est une gêne qu'il subit depuis des années sans en avoir trouvé la cause. Le retirer ici reproduirait exactement ce défaut. Mesurer chaque film et les mettre au même niveau les uns par rapport aux autres est la vraie réponse, et elle est au plan d'après la V0.1 ; en attendant, c'est ce gain qui tient le niveau. Une piste dont personne n'a pu lire la largeur est repliée comme avant : un repliage inutile ne coûte rien, un repliage oublié est une bande-son dont les dialogues restent dans un canal que personne n'entend. |
| Un son qui commence après l'image | **Au démarrage d'un film, le son est comblé avec du silence jusqu'à l'image** (`aresample=first_pts=0`), donc le flux remis au navigateur commence par les deux ensemble. Le son garde son moment : ce qui était à trois secondes y reste, et les trois secondes d'avant sont du silence au lieu de rien. Uniquement au démarrage, parce que c'est le seul endroit où ce trou existe : une reprise en plein film tombe au milieu d'un son continu, et y combler l'avant reviendrait à demander une heure de silence. Uniquement sur un son refabriqué, un son recopié ne pouvant pas être filtré | Un fichier peut déclarer que sa piste sonore commence après son image, et c'est une déclaration parfaitement légale : un lecteur de bureau attend, montre l'image et met le son quand il arrive. Un navigateur, lui, ne traverse pas le trou : il joue le son dès qu'il l'a, et tout le film défile avec le son en avance du début à la fin. Relevé sur la collection du mainteneur : une série dont la piste française commence trois secondes après l'image, lue avec trois secondes d'avance dans le navigateur alors que le même fichier lu par le réseau depuis un lecteur de bureau était parfaitement synchrone. L'outil avait raison depuis le début : mesuré, il conservait fidèlement le trou. Ce qu'il produisait était un flux qu'aucun navigateur ne sait placer. Vérifié en produisant le flux des deux façons : sans le remplissage le son sort à trois secondes et l'image à zéro, avec le remplissage le son sort à zéro et le vrai son est toujours à 3,005 s. |
| Le nom sous lequel une œuvre a été rangée | **Une œuvre garde les noms qu'on lui a lus sur le disque, à côté du nom qu'elle porte.** Le scan cherche d'abord par le nom porté, puis par les noms de rangement ; une relecture du fichier en ajoute un, une fiche de fournisseur jamais ; et une mise en commun emporte les noms de celle qui part vers celle qui reste | Le fournisseur renomme une œuvre avec son propre titre et lui pose son année, alors que le dossier sur le disque, lui, ne bouge pas. Cherchée seulement par le nom qu'elle porte, la série n'était plus reconnue : chaque fichier ajouté dedans en écrivait une deuxième, qui n'était rattrapée qu'au moment de l'identification, et seulement si le fournisseur répondait. Relevé sur la collection du mainteneur : quinze séries écrites deux fois d'affilée, quinze interrogations du fournisseur et quinze regroupements pour rien, à chaque passage. Emporter les noms lors d'une mise en commun est ce qui fait que le regroupement ne se refait pas la fois suivante. |
| Réunir deux œuvres que le fournisseur dit identiques | **Réunir une série, c'est descendre dans ses saisons et ses épisodes, jamais remplacer la ligne du haut.** Chaque saison rejoint la saison du même numéro, chaque épisode l'épisode du même numéro, et les fichiers ne changent de mains qu'en bas. Une saison ou un épisode que l'autre côté n'a pas change simplement de parent. Rien n'est supprimé avant que tous les étages aient été parcourus. Et un groupe, c'est un identifiant **et** un type ensemble : un film et une série qui portent le même numéro ne se rencontrent jamais | La mise en commun avait été écrite pour deux copies d'un même film, où une œuvre est une ligne et ses fichiers. Appliquée à une série, elle effaçait la ligne du haut, et la base emportait en cascade toutes ses saisons, tous ses épisodes et tous leurs fichiers : une série entière disparaissait de la bibliothèque sans un mot dans le journal. Le cas est arrivé pour de bon sur la collection du mainteneur, en ajoutant un second disque : la même série y était écrite autrement, le fournisseur a répondu le même identifiant pour les deux, et quinze regroupements ont été faits dans la foulée. Le type dans la clé du groupe vient de la même famille de pièges que les numéros de saison : un fournisseur numérote ses films et ses séries sur des compteurs séparés. |
| Arrêter une lecture qui traverse un film | **Le signal d'arrêt descend jusqu'à l'outil et le coupe là où il en est.** Les trois lectures de l'entretien, images clés, sous-titres et vignettes, le portent ; un film abandonné en route n'est pas écrit comme lu et n'est pas écrit comme en faute : il reste à faire, et le journal dit qu'on l'a laissé plutôt qu'il a échoué. Les lectures que personne n'attend, celle du lecteur et celle du scan, ne le portent pas : il n'y a personne pour demander | Un travail de fond se regardait entre deux fichiers : la demande d'arrêt était bien enregistrée, les films suivants refusés aussitôt, mais les deux en cours allaient jusqu'au bout et rien ne le disait. Sur un film 4K lu en entier pour ses vignettes, ça fait un quart d'heure pendant lequel le bouton « arrêter » ne rend pas la main, aucune ligne n'est écrite et rien ne bouge à l'écran. Constaté sur le serveur d'un proche du mainteneur, pendant l'entretien de nuit. Un bouton qui ne rend la main qu'un quart d'heure plus tard n'est pas un bouton d'arrêt : c'est un bouton dont on ne sait pas s'il a marché, et la seule chose qu'on ait envie de faire ensuite est de redémarrer le serveur, ce qui relance précisément le travail qu'on voulait arrêter. Le processus est tué sans ménagement plutôt que prié de finir, contrairement à ce que fait le moteur de lecture : ce que ces trois lectures écrivent est écrit à côté et mis en place d'un seul geste à la fin, donc il n'y a rien à refermer proprement et rien à tronquer. |
| Un seul jeu de règles pour choisir une fiche | **Le type qui porte une proposition du fournisseur et celui qui porte une fiche sont communs aux films et aux séries ; seul le fournisseur sait lequel des deux catalogues il a interrogé.** Les règles qui choisissent la bonne réponse parmi plusieurs, elles, sont écrites une seule fois et ne connaissent ni film ni série | Ces règles sont la partie la plus travaillée et la plus chèrement acquise du projet : titre exact d'abord, puis titre qui est le début de l'autre avec l'année qui concorde, puis proximité des mots comptée dans les deux sens, avec le refus explicite de prendre la première réponse venue. Elles viennent d'incidents réels, dont un making-of collé sur deux films différents ensuite fusionnés sur une seule fiche. Les dupliquer côté séries, c'est garantir que la prochaine correction ne sera faite que d'un côté, et que l'autre gardera la faute sans que personne le remarque. Rien dans ces règles ne parle de film : elles parlent de titres et d'années. |
| Repérer un générique que rien ne nomme | **Les épisodes d'une même saison sont comparés entre eux, par le son.** Le générique est la seule chose qui sonne exactement pareil d'un épisode à l'autre : on prend une signature du son de chaque épisode, on cherche la plus longue tranche que deux épisodes ont en commun, et c'est elle. Le son seul est lu, jamais l'image, et seulement le **début et la fin** de chaque épisode plutôt que le fichier entier. Ce qui est trouvé est écrit avec l'origine « repéré » : un chapitre qui se nomme passe devant, et ce qu'une personne a dit passe devant tout. **Le résumé de l'épisode précédent n'est jamais repéré ainsi**, et ce n'est pas une limite provisoire | Mesuré sur une collection réelle avant d'écrire la moindre ligne : sur cinquante épisodes tirés au hasard, quarante-cinq ne portent aucun chapitre du tout, et parmi les cinq qui en portent il faut encore qu'un chapitre s'appelle quelque chose comme « générique » ou « opening » pour dire quoi que ce soit. La lecture des chapitres, déjà faite et gratuite, ne couvre donc pas un dixième des fichiers : sans comparaison, le bouton n'existe que sur les rares fichiers soigneusement étiquetés. Le son plutôt que l'image parce qu'il est bien moins cher à décoder et que c'est lui qui est identique : le montage d'un générique peut changer d'un épisode à l'autre, sa musique non. Le début et la fin seulement parce qu'un générique ne se cache pas au milieu, et que traverser chaque épisode en entier ferait de cette tâche la plus longue des quatre pour rien. Pour le résumé, la raison est définitive : ce qui précède le générique est tantôt un résumé, tantôt une vraie scène d'ouverture, parfois les deux à la suite, et rien dans le son ne les distingue puisque les deux sont différents chaque semaine. Un bouton qui proposerait parfois de sauter le début réel de l'épisode ne serait plus jamais pressé, ce qui est pire que pas de bouton. |
| La forme du travail qui repère les génériques | **Une tâche planifiée à elle seule**, comme chez Jellyfin, à côté des images clés, des sous-titres et des vignettes : sa propre ligne à l'écran de l'entretien, son propre compte de ce qui reste, son propre bouton pour la lancer maintenant, son propre arrêt qui descend jusqu'à l'outil. Elle n'apparaît que pour les médiathèques rangées en saisons et épisodes. **Son unité de travail est la saison et non le fichier**, contrairement aux trois autres. Chaque fichier traversé est marqué comme traversé, y compris celui dont rien n'est sorti | Partager une tâche avec une autre lecture les rendrait indissociables : deux travaux de même nature ne tournant jamais sur le même sujet à la fois, les vignettes d'une médiathèque refuseraient de démarrer parce que ses génériques sont en cours de repérage. Une ligne séparée est aussi la seule façon de dire « celle-là, je n'en veux pas » ou « celle-là d'abord », et la seule façon de voir qu'elle a tourné cette nuit et n'a rien trouvé. Réservée aux médiathèques épisodiques parce qu'un film n'a pas de voisins : une ligne éternellement vide sur une médiathèque de films serait du bruit sur l'écran qui existe pour être lu d'un coup d'œil. L'unité en saisons change plus de choses qu'il n'y paraît : ce que l'écran compte n'est pas le même nombre que pour les trois autres, et une passe ne peut pas prendre les fichiers dans n'importe quel ordre ni les traiter séparément. Marquer ce qui a été traversé plutôt que se fier aux génériques trouvés vient de la même raison que pour les images clés : une saison où rien n'a été trouvé et une saison que personne n'a regardée se ressemblent exactement, et sans marque la nuit suivante relit les mêmes fichiers pour le même néant. C'est aussi ce qui règle une fois pour toutes la saison d'un seul épisode, qui n'a rien à quoi se comparer et ne répondra jamais. |
| Interface web compilée | **Reconstruite par le script d'installation lui-même, à chaque mise à jour**, plutôt que ce fichier compilé gardé dans le dépôt en plus du code source. Le script installe Node.js dans le LXC et reconstruit l'interface juste avant de compiler le serveur | Le fichier compilé était enregistré directement dans le dépôt pour que compiler le serveur n'exige aucun outil JavaScript sur la machine du mainteneur. Mais un correctif touchant seulement l'interface pouvait alors être poussé sans que ce fichier soit refait à côté, et une mise à jour réussie ne changeait rien à l'écran. Un futur utilisateur du projet n'aura personne pour s'en souvenir à sa place : le script s'en charge lui-même désormais, et le dépôt ne garde plus que ce qui est écrit à la main. |
| D'où vient Node.js | **De nodejs.org, comme Rust vient de rustup, et non des paquets de Debian.** Le script demande la dernière version de la ligne au support long (aujourd'hui la 24), la vérifie contre l'empreinte publiée à côté d'elle avant de la décompresser, la pose dans `/opt/node` et la relie dans `/usr/local/bin` ; le Node de la distribution, s'il est là, n'est ni touché ni combattu, il est simplement devancé dans le chemin. Aucun numéro de version n'est écrit dans le script : la liste des empreintes dit elle-même laquelle est la dernière, donc une mise à jour du serveur met Node à jour au passage. Si nodejs.org ne répond pas, le Node déjà installé est gardé et la mise à jour continue ; s'il n'y en a aucun, celui de la distribution est pris en disant pourquoi | Debian embarque le Node qui était courant le jour où Debian a gelé, et le garde des années : sur Debian 13 c'est une ligne déjà arrivée en fin de vie, et les outils de l'interface le disaient à chaque compilation par une pleine page d'avertissements que le mainteneur a fini par remonter. Le choix inverse, épingler une version dans le script, revient au même défaut un an plus tard, sans personne pour s'en apercevoir. La vérification par empreinte n'est pas du zèle : c'est une archive qui va être décompressée en root, et le seul moment où l'on peut encore refuser ce qui est arrivé est avant de l'ouvrir. |
| Banc d'essai | **Une commande du binaire lui-même** (`melyxar bench`), plutôt qu'un outil de charge extérieur comme `oha` ou `k6` prévu au document 02. Elle remplit une bibliothèque fictive, joue les scénarios de navigation contre le serveur en marche, et met ses centiles en face des budgets écrits, en sortant en erreur quand un budget est dépassé | Un outil extérieur veut être installé, et ni l'un ni l'autre n'est dans les paquets de Debian : c'était une deuxième chose à installer dans le LXC, à tenir à jour, et à expliquer, pour un mainteneur qui ne doit pas avoir à en connaître. Le binaire, lui, est déjà là et déjà à jour, il connaît les budgets puisqu'ils sont écrits dans le même dépôt, et il peut donc répondre « tenu » ou « dépassé de tant » au lieu de rendre des chiffres bruts que quelqu'un doit aller comparer à un tableau. Le script d'installation en fait une entrée de menu, et rien de tout cela n'exige un terminal. |
| Affiches de la bibliothèque fictive | **Les lignes d'images sont écrites, les fichiers ne le sont pas.** Les cartes de cette bibliothèque-là montrent donc la couleur de l'œuvre, comme toute carte avant l'arrivée de son image | Les lignes sont ce que la grille et la fiche lisent et ce que la réponse transporte : sans elles, la mesure serait plus rapide que la réalité et ne vaudrait rien. Le fichier, lui, est servi par son chemin, et ce qu'il coûte ne change pas avec la taille de la collection : cent mille aplats de couleur sur le disque mesureraient exactement ce qu'un seul mesure, pour plusieurs minutes d'écriture et trois cent mille fichiers à balayer ensuite. Conséquence traitée plutôt que subie : une image qui ne charge pas laisse la carte montrer sa couleur au lieu d'une icône cassée, ce qui vaut aussi pour une vraie bibliothèque dont le cache a été vidé. |
| Ce qu'une page compte | **Rien.** Ce qui répond sur la médiathèque entière plutôt que sur la page (combien d'œuvres la grille contient, quels genres, décennies et lettres elle propose avec combien sous chacun, combien de fiches attendent un nom) est compté une fois par changement et relu ensuite. Le compteur de version que porte déjà chaque médiathèque, et que toute écriture modifiant un listage fait monter, est ce qui dit quand recompter. La visite qui tombe sur un compte périmé recompte ; celle qui arrive pendant ce calcul reçoit le compte d'avant plutôt que d'attendre | Mesuré sur cent mille œuvres avant d'y toucher : les seuls menus prenaient 690 ms, contre les 50 ms d'une page entière, et la page d'accueil 156 ms. Ce n'est pas un cache générique, écarté ailleurs à raison : c'est exactement l'emploi prévu du compteur de version, et c'est le chemin chaud qui lit ce que le chemin froid a écrit. Un changement coûte donc une page lente et non une page lente par visiteur, et rien n'est jamais servi d'avant un changement une fois le calcul qui l'a suivi terminé. |
| Reconstruction quand une migration change | Le dossier des migrations est déclaré au système de compilation, qui reconstruit la crate `database` dès qu'une migration est ajoutée ou modifiée | Sans cette ligne, ajouter une migration et compiler ne change rien du tout : la compilation se croit à jour, le binaire garde les migrations d'avant, et la table ou l'index n'apparaît jamais. La panne est silencieuse, elle survit à un redémarrage, et le seul symptôme est un serveur qui se comporte comme si le changement n'avait pas été écrit. Même famille de piège que l'interface compilée gardée dans le dépôt, réglée le même jour. |
| **Ce que porte une carte** | **Tout ce qu'un survol montre, et rien de plus.** Sa sorte, sa médiathèque, où en est celui qui regarde (pas commencé, en cours avec sa position, vu), s'il l'a mise en favori, et pour une série le nombre d'épisodes qui lui restent. Le tout est joint à la ligne de l'œuvre au moment où la page est lue, en une seule question pour la page entière | Le survol décide de l'ergonomie entière : lecture au centre, coche en haut à droite, favori en bas à droite. Chacun de ces trois signes est une donnée qui appartient à celui qui regarde et non au film, donc une carte qui ne les porte pas oblige la page à poser une question par carte, soit cinquante questions pour une rangée. |
| **Ce que montre une carte du bandeau** | **Cinq vraies affiches de la médiathèque, en éventail**, prises parmi les œuvres de cette sorte les plus récemment ajoutées **qui ont été identifiées**, envoyées par le serveur à côté de la rangée : les plus récentes d'abord, celles qui ont une affiche avant celles qui n'en ont pas, donc les mêmes d'une visite à l'autre. La grande image de fond empruntée à la dernière œuvre a disparu, et avec elle la question posée à la base pour aller la chercher. L'éventail est dessiné deux fois, la seconde retournée sous ses propres pieds et effacée en tombant, ce qui lui donne un sol ; une lueur derrière lui, une peinture sur le panneau et la marque de la sorte sortant du coin haut complètent la profondeur. Une médiathèque qui a moins de cinq affiches en montre autant qu'elle en a, dans une disposition écrite pour ce nombre-là, une œuvre sans affiche montre la lettre de son titre comme partout ailleurs, et une médiathèque sans aucune œuvre identifiée montre sa propre icône en filigrane, entière et centrée | Une image de fond, c'est un film montré large, et ce qu'une porte d'entrée a à dire est « voilà une étagère de ça ». Un éventail le dit d'un coup d'œil là où une photo ne disait rien du nombre ni de la variété, et cinq est ce qui atteint les bords d'une tuile de cette forme, là où trois s'arrêtaient avant et laissaient un trou à chaque extrémité. Elles étaient d'abord prises dans les cartes de la rangée, pour ne rien télécharger de plus ; relevé sur la collection du mainteneur, les derniers arrivés d'une sorte sont souvent des fichiers encore sans fiche, et l'éventail montrait des lettres grises devant une médiathèque pleine d'affiches. Une question de plus par sorte, bornée à cinq cartes, coûte bien moins que cette fausse impression. La page a cessé de charger une image large par tuile. Stables plutôt que tirées au sort, parce qu'un éventail qui change à chaque rendu est une page qui n'a pas d'avis. Le nombre d'affiches est une classe sur le groupe et non une géométrie écrite en dur : le jour du chantier téléphone, trois se demandent, et les règles pour trois sont déjà écrites. Le reflet est le même composant replié plutôt qu'une seconde disposition, donc il ne peut pas se désaccorder de ce qui se tient dessus, et il ne coûte aucun téléchargement : mesuré, vingt-quatre balises d'image pour huit fichiers. |
| **Les épisodes restants sont comptés à la lecture** | **Décision révisée sur mesure.** La revue de départ disait de tenir un compteur par personne et par série, écrit à chaque changement, parce que compter à la lecture ruinerait la réactivité. Mesuré sur cent mille œuvres : remplir une page de vingt-quatre films coûte 0,1 ms, et une page de vingt-quatre séries, épisodes restants compris, 3,6 ms. Le compteur n'est donc pas écrit, et la table qui l'attendait reste vide | Un compteur doit être juste à chaque instant ou le badge ment, et le tenir juste veut dire l'écrire depuis chaque endroit qui touche à la progression **et** depuis chaque scan qui ajoute ou retire un épisode. C'est un prix réel, en risque de dérive silencieuse, pour gagner trois millisecondes sur un budget de trente. Compté à la lecture, il ne peut pas dériver. Le jour où la mesure dit autre chose, la table est déjà là. |
| **Jusqu'où remonte la rangée « À suivre »** | Elle regarde **les mille dernières choses lues** par le compte, pas tout ce qu'il a lu depuis toujours. Conséquence assumée : une série que personne n'a touchée depuis très longtemps cesse d'être proposée comme la prochaine à voir, tout en restant dans sa médiathèque, dans sa grille et sur sa page | Mesuré sur un compte de vingt mille lignes de progression : tout lire coûtait 58 ms contre un budget de 30, parce qu'atteindre la série demandait de joindre deux fois la table des œuvres pour chacune de ces lignes avant de pouvoir regrouper. Borné au récent, 4 ms. Et la rangée montre de toute façon une poignée de séries, les plus récemment touchées : ce qui a été lu il y a des années ne pouvait pas changer sa réponse, seulement la faire payer. |
| **Marquer vu à la main** | Sur un film, la ligne de progression le dit et le dit pour de bon. Sur une **saison** ou une **série**, le marquage descend sur chaque épisode qu'elle contient, et les compteurs d'épisodes restants sont réécrits dans la même transaction. Démarquer fait le chemin inverse et remet chaque épisode à zéro, position comprise | Une série n'est pas regardée, ce sont ses épisodes qui le sont : marquer la série sans descendre laisserait un compteur qui dit douze épisodes restants sur une série marquée vue, c'est-à-dire deux écrans qui se contredisent. Dans la même transaction parce qu'un compteur écrit à côté du marquage est un compteur qu'une coupure laisse faux pour toujours, sans que rien ne le signale. |
| **Épinglé** | **Par l'administrateur, pour tout le monde.** Une mise en avant du serveur, pas un marque-page : l'ordre est choisi, la liste est courte, et c'est elle qui remplit le hero avant tout le reste. Chacun garde sa liste à soi ailleurs, qui existe déjà sous le nom de favoris | Les deux se défendaient, ils ne donnent pas la même table ni le même écran. Choisi par le mainteneur. Et les deux existent au bout du compte : celle du serveur s'appelle épinglé, celle de la personne s'appelle favori. |
| **Suggestions** | **Ce que le serveur peut honnêtement dire aujourd'hui** : des œuvres jamais commencées, bien notées, tirées en priorité des genres que ce compte regarde le plus. Aucun moteur de recommandation, aucun apprentissage, et le nom ne promet rien d'autre | Il n'existe aucun historique exploitable au-delà de ce qui a été regardé, donc toute promesse plus grande serait une case grisée déguisée en fonction. Les genres de ce qui a été vu sont la seule matière disponible, et ils suffisent à ne pas proposer un film d'horreur à quelqu'un qui ne regarde que des comédies. Le jour où l'historique sera assez riche, la définition changera derrière le même nom. |
| **Le hero et les reprises** | Le hero prend **d'abord les reprises**, puis les épinglés, les nouveautés et les suggestions, jusqu'à cinq éléments. Les mêmes films apparaissent donc en grand dans le hero et en petit dans la rangée juste dessous, et c'est assumé | Le doublon a été signalé au mainteneur avant d'être codé, avec l'autre choix possible (épinglés et nouveautés en haut, reprises dans leur seule rangée). Il l'a tranché en connaissance de cause : reprendre son film est ce qu'on vient faire, et le trouver deux fois coûte moins que de le chercher. Écrit ici pour que personne ne le « corrige » plus tard en croyant à un oubli. |
| **La place des épinglés dans le hero** | **Ce qui est mis en avant a sa place réservée**, lue avant tout le reste ; les reprises remplissent ce qui reste, et passent toujours devant à l'écran. Ce qui est épinglé à la main y va quelle que soit sa sorte, épisode compris : la règle qui garde saisons et épisodes hors des grilles ne s'applique pas à une étagère où quelqu'un a désigné cette œuvre-là | Les reprises étaient prises en premier jusqu'à remplir les cinq places, et les épinglés n'étaient lus que s'il restait de la place. Quelqu'un qui regarde cinq choses en même temps, c'est-à-dire l'état normal d'un serveur en service, n'en avait jamais : « Mettre en avant » ne faisait donc strictement rien, sans le moindre message. Signalé par le mainteneur après avoir rechargé la page pour vérifier. |
| **L'administration pendant ce chantier** | *Close : ce chantier est venu, voir « L'administration a son propre espace ».* Elle restait **exactement où elle est**, et l'accueil est reconstruit à côté. Elle sera refaite dans son propre chantier, séparée comme prévu | Le déplacement sous une porte `/admin` avait été proposé pour ne pas perdre le scan et les journaux pendant les travaux. Le mainteneur l'a écarté : ce serveur n'est pas encore en service, il ne contient rien qu'il regrette, et déplacer une interface qui sera de toute façon réécrite est un travail qui ne survit pas à ce qui le suit. |
| **Les pastilles techniques du hero** | **Lues sur la copie qui est sur le disque**, jamais promises par le catalogue : la hauteur d'image de la meilleure copie encore présente, la plage dynamique qu'elle déclare, et la piste sonore la plus fournie. Le serveur envoie ce que le fichier dit (2160, `hdr10`, `Dolby Atmos`) et l'interface seule le traduit en pastille. Ces noms ne sont jamais traduits | Un catalogue dit ce qu'une œuvre est quelque part dans le monde, pas ce que ce serveur peut jouer ce soir : une fiche annoncée en 4K alors que le fichier est en 1080p est un mensonge que personne ne peut corriger. Les copies disparues sont écartées pour la même raison. La traduction en pastille reste à l'écran parce qu'une hauteur en pixels est un fait et « 4K » une façon de le dire ; et une personne qui lit l'interface en français cherche quand même « Dolby Atmos ». |
| **Où mène le titre d'une rangée** | **Vers une grille, et seulement quand il en existe une.** Les rangées adossées à une vraie grille (les nouveautés, chaque sorte de médiathèque) portent un chevron et un « Tout voir » ; celles qui n'existent que comme rangée, ce qu'on a laissé en cours et ce que les séries attendent, n'en portent aucun | Un chevron est une promesse de page suivante. Sur une rangée qui n'en a pas, il mène soit nulle part, soit vers une grille inventée pour l'occasion et vide la moitié du temps. Mieux vaut un titre qui ne promet rien qu'un titre qui promet une page qui n'existe pas. |
| **Le bandeau de catégories** | Sous le hero, **une tuile large par sorte de médiathèque réellement présente**, avec une image empruntée à l'œuvre la plus récente de cette sorte. Une sorte qui tient une seule médiathèque mène droit dedans et porte le nom que l'administrateur lui a donné, partout où la sorte est nommée ; plusieurs mènent à une grille filtrée sur la sorte, qui garde le nom de la sorte | L'accueil en rangées répond à « qu'est-ce qu'il y a », pas à « emmène-moi aux films », qui est ce que cherche quelqu'un qui sait déjà ce qu'il veut et qui l'obligeait à relire la barre du haut mot par mot. L'image vient de la rangée déjà lue pour l'accueil, donc en une question de plus pour tout le bandeau. |
| **L'ordre des sortes sur l'accueil** | **Un réglage par compte** : la liste des sortes de médiathèque dans l'ordre voulu. Les tuiles du bandeau et les rangées par sorte le suivent toutes les deux, puisqu'elles viennent de la même liste envoyée par le serveur. Sans choix, l'ordre standard : Films, Séries, Animés, Émissions, Musique ; une sorte que la liste ne cite pas se range après les autres, dans cet ordre. Se règle dans les réglages par deux flèches sur chaque ligne, et seules les sortes que le compte voit vraiment y figurent : les autres gardent leur place sans prendre de ligne | Demandé par le mainteneur. Chacun regarde surtout une sorte, et elle doit pouvoir venir en premier chez lui sans passer devant chez tout le monde. Constaté en l'écrivant : l'ordre annoncé comme standard n'était pas celui du code, qui suivait le nom des médiathèques par ordre alphabétique. |
| **Ce qu'une carte couchée montre** | **Une image plus large que haute, jamais l'affiche.** Cherchée dans cet ordre : la vignette de l'œuvre (image large avec le titre écrit dessus), puis son image large, puis pour un épisode sa propre image, qui est déjà une image prise dans le film, puis la vignette et enfin l'image large de la série deux crans au-dessus. Ces images ne sont demandées que pour les rangées qui couchent leurs cartes ; une grille d'affiches ne les demande pas et ne les paie pas | Une affiche fait deux tiers de large pour un de haut, une carte couchée presque deux de large pour un de haut. Remplir l'une avec l'autre découpe une bande au milieu de l'image et décapite tout le monde, ce qui était exactement l'allure de la rangée « Continuer la lecture » : les mêmes affiches qu'ailleurs, coupées. Le repli sur la série vient du même constat que pour la bannière : un épisode dont personne n'a d'image appartient quand même à quelque chose qui a une image. La vignette passe devant l'image large parce qu'une carte couchée n'a pas la place d'écrire le titre sous l'image : c'est l'usage que Jellyfin fait de la même image. |
| **Où une grande image est coupée** | **Un seul endroit, à un huitième de la hauteur, pour toutes les images.** Ce qui rend ce chiffre unique possible n'est pas une astuce mais la hauteur de la bannière : elle vaut un peu moins d'un tiers de la largeur de l'écran, donc elle garde environ 55 % de l'image au lieu de moins de la moitié. Ce qui part est le sol. | Il a fallu deux tentatives de lecture de l'image pour en arriver là, et les deux ont été pires que le chiffre fixe qu'elles remplaçaient. **La première mesurait le détail**, c'est-à-dire à quel point chaque ligne diffère de ses voisines : c'est de la texture, pas le sujet. Un champ d'herbe, une ville qui s'effondre ou un lettrage en contiennent bien plus qu'un visage, et la bande partait dans le coin le plus chargé en laissant les têtes au-dessus. **La seconde cherchait la couleur de la peau.** Mesurée sur les masques produits, elle prend un incendie pour un visage (30 % d'une image de série marquée comme peau, alors que les visages en sont une miette), un désert aussi, un mur chaud aussi, et ne trouve rien du tout sur une scène en lumière froide, où elle retombe au hasard. Les garde-fous ajoutés (trop peu, trop, ligne saturée) rattrapaient des cas et en cassaient d'autres. **Le troisième essai a été de ne rien coder du tout** : un réglage fixe, la bannière haute, vingt-huit images réelles, aucun visage coupé, y compris sur celles que les deux algorithmes avaient ratées. La lecture par image a donc été retirée entièrement, avec sa colonne en base et le passage de l'outil qu'elle coûtait sur chaque image préparée. La leçon tient en une phrase : **le problème n'était pas de savoir où couper, mais de couper trop.** Rien n'oblige à garder ce chiffre unique si la bannière rapetissait un jour ; c'est le rapport entre les deux qui compte. **Les deux chiffres inscrits sont ceux du mainteneur**, trouvés en réglant les curseurs sur sa propre médiathèque, qui est un échantillon bien plus large que l'étagère de vingt-huit images : un quart de la hauteur devient un huitième, et la bannière descend légèrement. Les deux disent la même chose, à savoir que ce qu'une bannière doit sacrifier est le sol. |
| **La bannière se règle** | **Trois réglages par compte** : la hauteur de la bannière (une part de la largeur de l'écran, de 20 % à 55 %), l'endroit où l'image est coupée (de son haut à son bas), et si elle tire une poignée différente à chaque ouverture de la page. Les deux premiers s'appliquent pendant qu'on les tire, écrits sur le document comme la couleur d'accent. | Les deux chiffres étaient écrits en dur, mesurés sur une étagère d'images réelles. Une médiathèque n'est pas une étagère : ce qui est juste sur vingt-huit images peut ne pas l'être sur trois mille, et le mainteneur doit pouvoir trancher sans recompiler. Le plafond de hauteur a été remonté après mesure : à 72 % de la hauteur d'écran, la bannière cessait de grandir passé environ deux cinquièmes de la largeur sur un écran ordinaire, donc la moitié haute du curseur ne faisait rien. Il ne sert plus qu'à empêcher une bannière plus haute que la fenêtre. Le tirage au sort laisse passer devant ce qu'un administrateur a mis en avant à la main : un choix délibéré n'est pas quelque chose qu'un tirage défait, et c'est exactement le défaut corrigé plus tôt quand la bannière pleine de films en cours faisait que « mettre en avant » ne faisait rien. Il ne tire que parmi les œuvres qui portent une image large, parce qu'une bannière sans son image est un aplat de couleur avec un titre dessus. |
| **La barre du haut tient sa propre bande** | **Opaque, en haut de l'écran, au-dessus de tout ce qui défile.** Rien ne passe dessous, donc rien n'a à être lu au travers. La bannière commence là où la barre finit. La ligne sous la barre compte dans la bande qu'elle occupe, et les deux sont écrites ensemble dans le même jeton : tout calcul de la place restante doit retirer la ligne aussi. | Elle a été posée par-dessus la page pendant un temps, translucide et floutée, pour porter la bannière au repos et les rangées dès qu'on descend. Remise comme avant sur décision du mainteneur : ce qu'il voulait est une barre, lue d'un coup d'œil et toujours la même, pas une vitre dont la lisibilité dépend du film derrière. Le retour a aussi défait tout ce qui compensait la superposition : la bannière et le fond d'une fiche ne sont plus rallongés de la hauteur de la barre, les pages ne commencent plus par un creux de cette hauteur, et les mots de la bannière ne sont plus décalés vers le bas. Le jeton de la ligne est né d'un défaut mesuré : sans elle dans le calcul, une bannière réglée sur « toute la fenêtre » dépassait d'un point et faisait défiler la page sur rien. |
| **Pas de flou d'arrière-plan sur une carte** | Les pastilles posées sur une affiche (l'état de lecture, le favori, le menu) ont un fond dense, **jamais un `backdrop-filter`**. Le flou reste réservé aux quelques endroits qui existent en un seul exemplaire à l'écran : la barre du haut, et les panneaux du lecteur | Mesuré, parce que le défilement ramait à partir de la moitié de l'accueil : la page portait **267 éléments à flou d'arrière-plan**, dont 264 sur les cartes, trois par carte. Chacun oblige le navigateur à relire et à flouter ce qu'il y a derrière, à chaque image. Sur la bibliothèque d'essai en 1920 : 95e centile de 22,4 ms et trois images au-dessus de 25 ms, contre 17,5 ms et aucune une fois les flous retirés. Sur une vraie collection, où les affiches se décodent en même temps, l'écart est plus grand encore. Un fond à 78 % au lieu d'un flou se lit pareil sur une affiche et ne coûte rien. |
| **Le bandeau des médiathèques peint à part** | **Le bandeau des portes d'entrée de l'accueil est posé sur sa propre couche** (`will-change: transform`), peinte une fois puis seulement déplacée pendant le défilement | Relevé par le mainteneur : l'accueil ramait dès que les portes revenaient à l'écran, et redevenait fluide dès qu'elles en sortaient. Chaque porte porte un reflet dans l'eau (un filtre de remous, un masque de lignes, un flou), une vingtaine d'ombres floues sur des affiches penchées et plusieurs dégradés. Peintes dans la même couche que la page, tout cela était refait à chaque morceau de page qui revenait à l'écran. Mesuré dans Chromium, dessin confié à la carte graphique, sur quatre portes : le dessin de la page pendant le défilement coûtait de sept à cent fois celui de la même page sans le bandeau selon sa longueur ; sur sa propre couche, il ne coûte plus rien de plus que la page sans lui. Le rendu est le même au pixel près, aux arrondis d'anticrénelage près. Toute décoration coûteuse dans une page qui défile suit la même règle. |
| **Les rangées se dessinent d'avance** | **Le rendu différé des cartes (`content-visibility: auto`) est gardé pour les grilles, et retiré des rangées.** Une rangée tient au plus deux douzaines de cartes : elles sont préparées à l'ouverture de la page, une fois, au lieu de l'être au moment où elles arrivent à l'écran | Relevé par le mainteneur : au premier défilement d'un accueil plein d'affiches, la page saccadait, puis restait fluide une fois parcourue. Chaque carte d'une rangée était mise en forme, placée et dessinée au moment exact où elle entrait à l'écran, donc pendant le défilement. Mesuré sur un accueil d'essai rempli d'affiches, processeur ralenti quatre fois : la pire image d'un premier défilement passe de 170 à 200 ms à 50 ms. Dans une grille de milliers d'œuvres, ne dessiner que ce qui est à l'écran reste ce qui la garde fluide. |
| **La bannière demande ses images une à une** | **Au chargement, seules l'image affichée et la suivante sont demandées, l'affichée en priorité ; chacune des autres l'est un cran avant d'être montrée, et toutes dès que quelqu'un prend la bannière en main.** | Les cinq images de fond, à la largeur de l'écran, partaient toutes au chargement, devant les affiches des rangées, pour une seule visible. Un cran d'avance suffit pour que la bannière change sans trou ; la prise en main, souris ou clavier, est le seul moment où n'importe laquelle peut être choisie. |
| **Un outil de mesure dans l'interface, éteint par défaut** | **L'interface embarque un enregistreur de fluidité, inerte tant qu'on ne l'arme pas depuis la console du navigateur** (`melyxar.measure()`). Armé, il démarre dès le chargement suivant de la page et note chaque image affichée, les longues images du fil principal avec ce qui les occupait, chaque image téléchargée (depuis le cache ou non, temps du serveur compris), les défilements et la machine. `melyxar.report()` rend le tout en texte, découpé par passage de défilement, et le désarme. Rien n'est envoyé nulle part : le rapport reste dans le navigateur jusqu'à ce que quelqu'un le copie | Une saccade ne se voit que sur la machine où elle arrive, et la machine de développement n'a ni l'écran, ni la carte graphique, ni la collection du mainteneur. Un outil permanent plutôt que des journaux ajoutés puis retirés : il ne coûte rien éteint, sert à chaque nouvelle question de fluidité, et mesure la vraie version, celle qui tourne en production. Ce n'est pas un journal de débogage au sens des règles : il n'écrit rien tant que personne ne l'a demandé. |
| **Où sont les flèches d'une rangée** | **Dans la marge de la page, de part et d'autre de la rangée, et rien de posé par-dessus les cartes.** Le chevron seul, sans pastille ni voile, et sa taille suit la marge quand la fenêtre rétrécit | Posées sur la première et la dernière affiche, elles portaient chacune un voile de fond qui s'effaçait sur le côté. Un dégradé qui finit sur du transparent finit quand même quelque part, et sur une affiche sombre cette fin se lit comme un liseret vertical aux deux bouts de chaque rangée. La marge de la page est vide et fait exactement la bonne largeur : les flèches y tiennent sans rien recouvrir, et la rangée se coupe net comme une rangée qui continue. |
| **Quelle image large on garde** | **Celle que le fournisseur met en avant tant qu'elle fait au moins 1920 de large ; sinon la plus grande qu'il propose**, départagée par ses votes, **et seulement parmi celles sans aucun texte dessus**. Pour cela on lui demande aussi les images sans langue, ce qu'on ne faisait pas | La bannière occupe tout le haut de l'écran : sa taille est la première chose qu'on voit, avant même le sujet. L'image mise en avant est celle que les votants ont choisie, donc la plus belle, mais rien ne garantit sa taille et c'est souvent la plus petite du lot. On garde donc le choix des votants quand il suffit, et la taille prend le dessus quand il ne suffit pas. Les images larges ne portent pas de langue : elles étaient exclues de la réponse depuis qu'on ne lisait cette liste que pour les titres dessinés. La réponse est environ deux fois plus longue, une fois par film, à l'identification. |
| **La vignette** | **Une sorte d'image à part : une image large avec le titre écrit dessus.** Le fournisseur range ces images avec les images larges et ne les distingue que par la langue qu'il leur donne : une image large qui porte une langue a du texte dessus, c'est une vignette ; celle qui n'en porte pas est une image large. Choisie comme le titre dessiné, dans la langue de la médiathèque d'abord, puis en anglais, puis par les votes. Récupérée à l'identification, et pour les œuvres déjà identifiées au prochain passage qui complète ce qui manque. Proposée dans la fenêtre des images comme les trois autres | Demandé par le mainteneur en comparant à Jellyfin, qui fait exactement ce tri et appelle ces images « Vignettes ». Elles servent aux cartes couchées de l'accueil. Mélangées aux images larges, elles pouvaient aussi finir derrière la bannière, qui dessine déjà le titre par-dessus : le titre apparaissait deux fois. |
| **Les largeurs d'une image large** | **640, 1280, 1920, 2560 et 3840.** La tuile d'une entrée, un portable, la plupart des écrans, un grand écran de bureau, un écran quatre mille lignes | Une bannière large fait la largeur de l'écran sur lequel elle est dessinée, et le mainteneur a des écrans 4K. Sans la marche du haut, un écran 4K étire du 1920. La règle « jamais agrandir » borne la dépense toute seule : un film dont le fournisseur ne tient qu'une petite image ne coûte que les premières marches. |
| **Jamais agrandir une image** | Les tailles préparées sont **ramenées à la taille réelle de l'image reçue** : une image de 1280 donne 640 et 1280, pas 1920. Et ce qui est écrit à côté de chaque image dit désormais **comment elle a été préparée**, pas seulement de quoi : une image préparée par une recette plus ancienne est refaite une fois, à la prochaine visite de l'œuvre, puis plus jamais | Agrandir n'invente rien : ça écrit un fichier quatre fois plus lourd avec le même détail, et surtout ça fait croire à l'interface qu'une image de cette largeur existe. Elle la demande de bonne foi pour la bannière, qui prend tout l'écran, et c'est là que le flou se voit le plus. Signalé par le mainteneur sur la bannière d'un film dont le fournisseur ne tient l'image qu'en 1280. Sans la recette écrite à côté, la correction n'aurait touché que les films ajoutés après elle : une bibliothèque déjà remplie garde ses images pour toujours, puisqu'une affiche présente est une affiche complète. |
| **La taille d'image qu'on demande** | **Chaque image offerte en plusieurs tailles dit en clair la place qu'elle occupe, en longueurs écrites à la main.** Jamais un jeton de style, jamais rien du tout. Les longueurs écrites sont celles que la feuille de style dessine, et la finesse de l'écran reste l'affaire du navigateur | Cet attribut est lu avant que la page ait une feuille de style : un `var()` dedans n'est pas une longueur, tout l'attribut est jeté, et le navigateur suppose alors la largeur entière de la fenêtre. Mesuré : **chaque carte réclamait l'affiche de 800 points de large pour la dessiner à 168**, soit seize fois trop de pixels, sur toutes les cartes de toutes les pages ; le tiroir du lecteur faisait pareil pendant qu'un film passait par la même connexion. D'où des affiches qui restaient un rectangle de couleur à droite de l'écran et qui arrivaient d'un coup dès qu'on allait vers elles, le navigateur les faisant alors passer devant. Après correction : 200 sur un écran ordinaire, 400 sur un écran fin, choisis tout seuls. |
| **Une rangée du serveur quand on coche une carte** | **Elle se vide sur-le-champ, elle ne se remplit jamais toute seule.** Cocher « vu » retire immédiatement la carte des rangées de ce qui est en cours et du hero, puis la page est relue et c'est la réponse du serveur qui fait foi | Ce qui part d'une de ces rangées, l'interface le sait : une œuvre finie n'est plus en cours. Ce qui la remplace, elle ne le sait pas : l'épisode qu'une série attend ensuite est une question à laquelle seul le serveur répond. Attendre l'aller-retour pour les deux laissait la carte cochée à l'écran assez longtemps pour qu'on la coche une deuxième fois, ce qui est exactement ce que le mainteneur a rencontré. |
| **Les outils restent au dernier stable** | **Tout est tenu à la dernière version stable, et on y va tôt plutôt que tard.** Rust suit le canal stable, les crates sont sur leur majeure courante, l'atelier web aussi. La montée se fait en un commit par étage, pour qu'une seule puisse être annulée sans perdre les autres. | Rien de tout ça ne bouge tout seul : un accent dans le manifeste web ne franchit jamais une majeure, et une dépendance Rust sous la 1.0 non plus. Elles restent donc exactement là où on les a posées jusqu'à ce que quelqu'un décide, et plus on attend, plus les ruptures s'empilent en une seule migration. Fait en une passe : trois crates d'une majeure en retard, l'édition 2021 vers 2024, et côté web quatre majeures dont deux à deux crans. Le bilan a été d'une seule vraie rupture dans tout le code, ce qui n'aurait pas été le cas deux ans plus tard. **Ce que ça coûte, mesuré** : reqwest 0.13 remplace *ring* par aws-lc comme moteur de cryptographie, donc davantage de C à compiler, mais sans aucun outil à installer et pour un atelier complet reconstruit de zéro en moins d'une minute et demie. Le C n'est pas une nouveauté : SQLite est déjà compilé avec le projet depuis le premier jour. Vite 8 construit l'interface en 0,8 seconde contre 2,3. |
| **Ce qu'un clic sur une flèche déplace** | **Un nombre entier de cartes**, et la rangée se repose sur le bord d'une carte : après un clic, la première carte visible est entière et alignée sur le titre de la rangée, dans un sens comme dans l'autre. Où commence une carte est lu sur les cartes elles-mêmes, pas calculé depuis la largeur qu'on leur a demandée | Déplacer d'une fraction de la largeur laissait la rangée là où cette fraction tombait : une première carte coupée en deux, une dernière coupée aussi, et le clic suivant qui les coupe ailleurs. Lire la place réelle des cartes évite l'autre piège : le navigateur arrondit chaque carte, et une erreur d'arrondi répétée dix fois le long d'une rangée fait une carte de travers. |
| **Le survol d'une carte** | **La carte entière grandit**, image et mots ensemble, comme tous les boutons de l'interface. Jamais l'image seule à l'intérieur d'une carte qui ne bouge pas | C'est une transformation, donc rien autour ne se déplace et la grille reste visable. L'image seule qui grossissait dans son cadre se lisait comme une image qui gonfle, pas comme une carte qui s'avance. La rangée garde de la marge pour ça, sinon elle rogne ce qui dépasse. |
| **La porte porte le serveur, pas Melyxar** | **Rien de Melyxar n'est écrit dans l'écran de connexion.** La marque, le nom et ce qui est derrière la carte viennent tous de ce que le serveur dit porter ; ce que le projet livre est le repli, pas la règle. Le fond est une décision à trois branches, dans cet ordre : une image posée par l'administrateur gagne sur tout, sinon l'un des deux fonds dessinés, celui que le serveur nomme. La couleur d'accent vient du thème comme partout ailleurs, jamais du composant. | Un écran de connexion est le premier et parfois le seul écran qu'un inconnu voit d'un serveur, donc c'est celui qu'un administrateur voudra à son image en premier. La base portait déjà le nom, la marque, l'écran de démarrage et une image de fond depuis la première migration, et l'écran n'en lisait aucun : il affichait la marque du projet en dur et ignorait l'image. Brancher ce qui existait déjà coûtait moins que de le refaire plus tard autour d'une page dessinée sans cette idée. Ce qui a été ajouté est la seule chose qui manquait pour que le choix soit exprimable : **quel fond dessiné**, écrit en toutes lettres plutôt qu'en numéro, pour qu'une base lue à la main se comprenne et qu'un troisième fond ne renumérote rien. Un mot que le serveur ne connaît pas est lu comme celui d'origine : un fond ne vaut pas de refuser de démarrer. **Ce qui manque encore** : la favicon n'a pas de colonne. Le slogan en a une depuis, et les fichiers déposés par l'administrateur sont servis (voir les lignes sur le fond et le slogan de la page de connexion). Le jour où l'écran d'administration existe, il écrit dans des colonnes déjà lues. |
| **« Rester connecté » veut dire quelque chose** | **La case décide de la date du cookie, et de rien d'autre.** Cochée, le navigateur est prié de le garder aussi longtemps qu'il l'accepte ; décochée, il ne reçoit aucune date, et un cookie sans date est un cookie que le navigateur jette en se fermant. Le choix est écrit à côté de l'appareil, pas déduit. | Une session vit déjà tant qu'on s'en sert : la case n'avait donc rien à changer côté serveur et n'aurait été qu'un décor. C'est le navigateur qui l'honore, ce qui la rend vraie même pour quelqu'un qui s'éloigne d'une machine restée allumée. Écrit en base parce qu'un changement de mot de passe ferme toutes les sessions et en rouvre une pour l'appareil qui a demandé : sans ce souvenir, cette nouvelle session repartirait pour la durée longue chez quelqu'un qui avait justement dit que la machine n'était pas la sienne. **Le chiffre du cookie n'est pas un choix** : les navigateurs plafonnent à quatre cents jours ce qu'ils acceptent d'honorer et rabotent silencieusement tout ce qui va plus loin, donc « rester connecté » vaut exactement ça en pratique, et chaque connexion réécrit la date. |
| **Rien ne refuse un jeton pour son âge** | **Le serveur ne compare jamais l'ancienneté d'une session.** Une ligne présente est une session qui marche, quelle que soit sa date. Ce qui met fin à une session : se déconnecter, changer son mot de passe, ou **le balayage qui supprime au bout d'un an les sessions dont personne ne s'est servi**, lancé au démarrage puis une fois par jour. | La règle d'avant refusait en silence après trente jours sans usage, et laissait la ligne en base pour toujours : le pire des deux mondes, puisque la promesse de la case était cassée et que le ménage n'était jamais fait. La fonction de balayage existait d'ailleurs déjà et **rien ne l'appelait**. Comparaison faite avec un serveur du même genre : chez eux un jeton ne meurt jamais tout seul, il n'y a aucune vérification d'ancienneté nulle part et aucune tâche de ménage dans le cœur du produit, le nettoyage par inactivité n'existe qu'en greffon tiers. Le mainteneur a tranché pour le même comportement, avec le ménage prévu dès le départ plutôt qu'en option. **Supprimer plutôt que refuser** est ce qui rend l'ensemble honnête : tant que le balayage n'est pas passé, la session marche vraiment, et une fois passé, la ligne a disparu. **Le balayage n'est pas l'entretien de nuit et n'en dépend pas** : ce que fait l'entretien, c'est lire des films, et un administrateur qui le coupe parle de sa médiathèque, pas de qui a le droit de se connecter. |
| **La porte dit qui est là** | **Une adresse publique donne les noms des comptes, et rien d'autre.** Pas d'identifiant, pas de droits, pas d'image, rien qui dise qui est administrateur : une rangée de noms. Coupée de deux endroits : un interrupteur pour tout le serveur, et une case par compte pour n'y pas figurer. Dans les trois cas où la liste est vide, la réponse est la même liste vide, jamais un refus. | **C'est la seule divulgation volontaire de ce serveur** : elle dit à quiconque peut l'atteindre quels noms existent ici. Ce qu'elle achète en échange est ce qu'elle coûte : se connecter tient en un clic et un mot de passe au lieu de se rappeler comment on a écrit son propre nom, ce qui sur un écran de télévision est la différence entre s'asseoir et abandonner. Le compromis était déjà acté avant d'être codé, l'interrupteur global existait en base et rien ne l'utilisait. Deux garde-fous plutôt qu'un, parce qu'ils répondent à deux questions différentes : l'administrateur décide pour le serveur, chacun décide pour soi. **Un compte masqué garde une entrée à lui** : le bouton « se connecter avec un nom d'utilisateur » ouvre le champ, sinon la case « ne pas m'afficher » deviendrait une case « ne plus pouvoir se connecter ». La réponse ne distingue pas un serveur qui refuse de dire, un serveur où tout le monde s'est masqué et un serveur neuf sans comptes : les trois donnent une liste vide, et l'écran dessine simplement aucune rangée. |
| **La porte s'ouvre sur les comptes, pas sur le formulaire** | **Une seule carte, deux faces.** Un serveur qui offre des noms montre d'abord leurs cartes et un seul bouton pour taper un nom ; presser une carte retourne la carte sur le mot de passe, avec la tuile et le nom en tête et un retour dans le coin. Un serveur qui n'offre aucun nom montre le formulaire tout de suite, sans retour. **La carte a la même largeur des deux côtés**, et elle s'élargit avec le nombre de comptes jusqu'à quatre de front ; au-delà, une deuxième rangée. | Le champ « nom d'utilisateur » n'a rien à faire en premier sur un serveur qui sait déjà qui est dessus : se connecter, c'est presser un visage et taper un mot de passe, et tout le reste est une sortie de secours. Le mettre derrière un bouton ne le retire pas, il le range : un compte masqué et quelqu'un qui préfère taper passent tous les deux par là. La largeur calculée à partir du nombre de tuiles plutôt qu'écrite en dur est ce qui évite qu'une carte prévue pour quatre comptes en serre trois par rangée le jour où il y en a huit. Elle ne change pas quand on presse un visage : une carte qui rétrécirait sous une main déjà partie vers le mot de passe est un écran qui bouge au mauvais moment. Le nom choisi reste sur la carte comme champ invisible, sinon un gestionnaire de mots de passe n'a plus rien à reconnaître. |
| **Deux entrées dessinées et éteintes** | **« Mot de passe oublié ? » et « Créer un compte » sont sur la carte, désactivés, avec la raison dans leur infobulle.** Pas de faux bouton qui ne fait rien : ce sont de vrais contrôles désactivés. | Demandé ainsi par le mainteneur, et il n'y a rien derrière elles aujourd'hui : il n'existe aucun moyen de redéfinir un mot de passe depuis un écran, la voie de secours est une commande sur le serveur, et les comptes sont créés par qui gère le serveur. Dessinées maintenant plutôt qu'ajoutées plus tard à une carte disposée sans place pour elles. Sur un serveur neuf, elles ne sont pas dessinées du tout : le bouton principal y crée déjà le premier compte, et un second qui proposerait la même chose serait deux portes vers une seule pièce. |
| **Les sommes de l'interface ont leurs tests** | **Vitest côté web, lancé par `npm --prefix web test`.** Le fichier de test vit à côté de ce qu'il teste, en `.test.ts`, et ne couvre que des fonctions pures : une conversion, un arrondi, un comptage. Ni rendu de composant, ni navigateur simulé, ni copie de l'API. La suite n'est pas dans le script de mise à jour, comme les tests Rust n'y sont pas : la vérification se fait avant le commit, la compilation dans le LXC. | La règle « tout calcul a son test » existait déjà et n'avait aucun moyen d'être tenue côté interface : il n'y avait pas de lanceur. C'est la moitié du projet où une formule fausse est la plus difficile à voir, parce qu'elle sort un nombre plausible à l'écran plutôt qu'une erreur. Vitest plutôt qu'un autre parce que Vite est déjà là et qu'il lit la même configuration : une seule dépendance de développement, aucun fichier de configuration à écrire, toute la suite en moins d'une seconde. Ce qui est volontairement laissé de côté est le test de rendu : il demanderait un navigateur simulé et une bibliothèque de plus, et ce qu'il attraperait est précisément ce que l'œil du mainteneur attrape déjà. **Mesuré dès la mise en place** : sur les vingt et un premiers tests, un a échoué, et c'était le test qui avait tort. Une note sur dix de 7,85 s'écrit 7,8 et non 7,9, parce qu'un nombre à virgule n'est pas tenu exactement par la machine. Le code était juste ; ce qui avait été supposé de lui ne l'était pas. |
| **L'administration a son propre espace** | **Sous `/admin`, réservé à l'administrateur, avec une barre latérale de douze sections** : Résumé, Bibliothèques, Métadonnées, Lecture, Transcodage, Utilisateurs, Appareils, Journal, Tâches, Sécurité, Diagnostics, Paramètres. La barre du haut reste celle de l'accueil, la même partout. L'interface d'administration est redessinée de zéro dans l'identité de l'accueil, rien n'est repris de l'ancienne page de réglages. Les anciennes adresses des tâches et du journal disparaissent, et le menu du compte mène à l'administration par une seule entrée | L'ancienne page de réglages mélangeait ce qui regarde une personne et ce qui regarde le serveur, sur une seule colonne : on n'y trouvait rien. Les fonctions et leur place approximative viennent d'Emby et de Jellyfin, pas leur apparence. La barre du haut commune garde une seule identité d'un écran à l'autre ; elle ne s'efface pas en défilant dans l'administration, pour ne pas laisser un trou au-dessus de la barre latérale. |
| **Mes réglages, séparés du serveur** | **`/settings` ne porte plus que ce qui appartient au compte** : profil, apparence (thème, couleur d'accentuation, langue), accueil (ordre, bannière, barre du haut), lecture (son, langues préférées, sous-titres, optimisation de l'appareil). Tout ce qui change le serveur pour tout le monde va dans l'administration | Chaque compte a ses réglages, seul l'administrateur a ceux du serveur. Les deux sur une page faisaient lire à un compte ordinaire des réglages auxquels il n'avait pas droit. |
| **Une fonction à venir est dessinée** | **Dans l'administration, ce qui n'est pas encore branché est dessiné quand même, désactivé et marqué « Bientôt »** : sections, blocs, boutons. Retiré s'il est abandonné | Demandé par le mainteneur, qui a besoin de voir un écran pour se le représenter. Même règle que les deux entrées éteintes de la porte : de vrais contrôles désactivés, jamais un bouton qui a l'air de marcher et ne fait rien. |
| **Couleurs d'état** | **Trois jetons nommés dans le thème, distincts de l'accentuation** : ce qui va bien, ce qui demande attention, ce qui est en panne. Aucune couleur écrite en valeur ailleurs | L'accentuation dit « actif, actionnable » et chacun peut la changer : un compte qui la choisit verte ne doit pas voir une panne en vert, ni un compte qui garde le rouge voir chaque bouton comme une alerte. |
| **Mesures du système gardées en base** | **Un point par minute gardé sept jours, puis une moyenne par heure gardée un an**, écrits par une seule tâche légère. Le direct (toutes les deux secondes) est lu en mémoire et ne touche pas la base | Un historique qui repart de zéro à chaque redémarrage ou mise à jour ne sert à rien : c'est justement après une mise à jour qu'on veut comparer. Au rythme d'une ligne par minute, une semaine tient en quelques milliers de lignes. |
| **La musique a sa place réservée** | **La sorte de médiathèque « musique » existe déjà dans l'interface** ; l'administration la montre, éteinte, là où elle ira | Prévue au projet (bibliothèque musicale, section 5 des fonctionnalités), pas encore gérée par le moteur. |
| **Ce que la machine dépense, lu par une crate à elle** | **Une crate `system`, qui ne dépend d'aucune autre crate de Melyxar**, lit la machine sans rien lancer : `/proc/stat` (processeur), la mémoire (la taille donnée par `/proc/meminfo`, l'usage compté comme Proxmox le compte : ce que le groupe de contrôle du conteneur tient, moins les fichiers gardés en cache, et `/proc/meminfo` seul hors conteneur), `/proc/loadavg` (charge), `/proc/net/dev` (réseau), la place libre de chaque disque des bibliothèques et des dossiers du serveur (un disque compté une fois même s'il porte plusieurs dossiers, nommé par le dossier où il est monté et présenté avec ce qu'il contient), et la température du processeur quand le conteneur la voit. Ce qu'elle ne sait pas lire est dit absent, jamais remplacé par un zéro | Dans un LXC, `/proc` montre déjà le conteneur et non l'hôte : c'est ce qu'on veut, puisque c'est la part de la machine donnée à Melyxar. Lire des fichiers ne coûte rien ; lancer un outil toutes les deux secondes coûterait plus que ce qu'il mesure. |
| **La carte graphique, vue par ce qu'elle déclare pour nos propres outils** | **L'occupation de la carte est lue dans les comptes que le pilote tient pour chaque programme qui l'ouvre** (`/proc/<pid>/fdinfo`), additionnés sur les processus lancés par Melyxar. Aucun outil extérieur | Les outils habituels (`intel_gpu_top`) demandent des droits qu'un conteneur non privilégié n'a pas. Le LXC ne sert qu'à Melyxar, donc ce que ses propres conversions demandent à la carte est ce que la carte fait. Honnête sur ce qu'elle ne voit pas : un autre programme de l'hôte sur la même carte n'est pas compté. |
| **Le rythme des mesures** | **Une lecture toutes les deux secondes, gardée en mémoire sur les dix dernières minutes ; chaque minute, la moyenne de la minute écrite en base.** Au-delà de sept jours, les minutes sont remplacées par leurs moyennes par heure, gardées un an. Le tout est fait par une seule tâche légère, en dehors des fils qui répondent aux pages | Le direct n'a pas besoin de la base, et l'historique n'a pas besoin de la précision de deux secondes. Une ligne par minute fait dix mille lignes par semaine, une par heure moins de neuf mille par an. |
| **Un voyant dit ce qu'il vient de vérifier** | **Chaque voyant du Résumé est vérifié à chaque fois qu'il est demandé, jamais recopié du démarrage.** FFmpeg : les deux outils sont encore là et exécutables. Carte graphique : le périphérique prouvé au démarrage s'ouvre encore. Base de données : la dernière écriture des mesures, une par minute, a réussi. Dossiers des bibliothèques : chacun existe encore, vu chaque minute par ce que le noyau garde en mémoire, sans lire le disque. Disques : moins de 90 % remplis. « Tout fonctionne normalement » n'est dit que si tous ces points passent, et sinon chaque point en défaut est nommé | Un voyant qui reste vert après que ce qu'il surveille est tombé est pire qu'aucun voyant. Aucune de ces vérifications ne lit un disque de médias : un disque endormi réveillé toutes les quinze secondes par un écran d'administration s'userait pour rien. |
| **Écrire dans les médias, seulement sur demande** | **Par défaut le service ne peut que lire les médias** (`ProtectSystem=strict`, seuls ses dossiers de données et de cache sont ouverts). Une entrée du script d'installation ouvre en écriture les dossiers des bibliothèques, et eux seuls, par un fichier complémentaire du service (`melyxar.service.d/media-write.conf`) réécrit à chaque mise à jour pour suivre les bibliothèques déclarées depuis, et la referme sur demande. Le script essaie ensuite d'écrire dans chaque dossier avec le compte du service. Pour un dossier refusé dont le groupe a déjà le droit d'écrire, il propose d'ajouter le compte à ce groupe (en le créant sous le nom `melyxar-medias` s'il n'en a pas dans le conteneur, pour que personne ne se demande plus tard d'où il vient) : aucun propriétaire ni aucun droit d'un dossier n'est jamais modifié. Un dossier dont même le groupe ne peut pas écrire, ou dont le groupe n'existe que sur l'hôte Proxmox, est nommé avec la raison. Dans la question de suppression, « Supprimer aussi du disque » est grisé, avec la raison, quand un essai d'écriture fait à l'instant échoue | Le serveur ne peut pas s'ouvrir lui-même des droits qu'il n'a pas : c'est à la personne qui a la main sur la machine de les donner. Proposer une suppression du disque pour la refuser après le oui induit en erreur. |
| **Une action dit ce qu'elle a fait** | **Ce qu'une action a donné une fois sa fenêtre fermée est dit par une notification dans le coin de l'écran**, dans la couleur de son état (réussi, à surveiller, en panne), qui part d'elle-même, plus tard pour un échec, et qu'on peut fermer. Une suppression du disque ne se croit pas sur parole : chaque fichier est cherché à nouveau une fois supprimé, n'est compté parti que s'il n'est plus là, et la notification dit combien l'ont été vérifiés | Une fenêtre qui se ferme sans rien dire laisse deviner si ça a marché. Un fichier que le système dit supprimé et qui est encore là est exactement ce que la vérification doit attraper. |
| **Ce qui se regarde, tenu en mémoire, appareil par appareil** | **Les lectures en cours vivent en mémoire, une par appareil connecté, jamais en base.** Une lecture naît quand le lecteur demande comment lire un film, lecture directe comprise : elle porte le compte, l'appareil, l'œuvre, la décision entière (méthode, raisons, ce que contient le fichier et ce qui en est refait, par la carte graphique ou par le processeur) et, quand il y en a une, la séance de conversion avec sa vitesse. Le lecteur dit à l'instant quand il se met en pause, repart ou saute ailleurs, et donne sa position toutes les dix secondes ; entre deux nouvelles, l'horloge d'un film qui n'est pas en pause avance d'elle-même, côté serveur comme côté administration. Une lecture reste vivante tant que son lecteur garde ouvert son fil vers le serveur (voir la décision suivante), même dans un onglet caché que le navigateur ralentit ; ce fil tombé sans adieu, elle est oubliée au bout de dix secondes, le temps qu'un fil coupé par le réseau se renoue. Un lecteur qui n'a jamais ouvert de fil est oublié après quarante secondes de silence. Une lecture quittée est retenue quarante secondes comme quittée, pour qu'un message du lecteur parti juste avant son adieu ne la fasse pas revenir | Une lecture directe ne laisse aucune trace sur le serveur en dehors de ces nouvelles : sans elles, elle serait invisible, et c'est pourtant la lecture la plus courante. Une base n'apporterait rien à ce qui est vrai pendant une minute ; l'historique des lectures appartient au journal d'activité. Un minuteur de page en arrière-plan est ralenti par le navigateur jusqu'à une fois par minute : une lecture en pause dans un onglet caché passait pour finie, puis revenait sans sa décision. |
| **Le serveur parle en premier, par un fil ouvert** | **Deux fils seulement, en flux d'événements (une réponse HTTP qui ne se termine pas) :** celui du lecteur, ouvert tant qu'il montre un film, par lequel le serveur lui dit de s'arrêter et par lequel il sait qu'il est encore là ; celui de l'administration, un par page visible d'un administrateur, par lequel le serveur dit à l'instant qu'une ligne du journal d'activité vient d'être écrite et, quand la page affiche les lectures en cours, envoie leur liste dès qu'elle change et toutes les deux secondes pour la vitesse de conversion. Fermé tant que la page est cachée ; à sa réouverture, ce qui suit le journal le relit. Le reste de l'interface continue de redemander à son rythme | Attendre la prochaine question du lecteur, jusqu'à dix secondes, ou relire une liste à intervalles, n'est pas l'instant qu'on attend d'un arrêt, d'une pause ou d'une ligne du journal : personne ne doit recharger la page pour voir ce qui vient de se passer. Chaque fil occupe une des six connexions qu'un navigateur ouvre vers un même serveur sans chiffrement : un par lecteur et un par page visible d'un administrateur, jamais plus, ce qui est partagé par tout ce que la page montre. Pas de compression sur ces réponses, et le mandataire est prié de ne pas les retenir, sinon rien n'arrive avant la fin. |
| **Arrêter une lecture depuis l'administration** | **L'arrêt passe par le lecteur** : le serveur le lui dit à l'instant par son fil, et encore dans la réponse à sa prochaine position pour un lecteur dont le fil est coupé. Il quitte le film et dit à la personne que l'administrateur l'a arrêté. S'il n'a pas obéi au bout de vingt-cinq secondes, parce qu'il est ancien ou coupé du réseau, la conversion est fermée par le serveur | Le serveur ne peut pas couper une lecture directe, qui n'est qu'un fichier lu morceau par morceau ; seul le lecteur peut s'arrêter proprement, là où la personne le voit. La fermeture forcée garantit qu'une conversion ne tourne pas pour personne. |
| **Le vrai nom du navigateur, dit par la page** | **Le navigateur d'un appareil est celui que la page a trouvé, et à défaut celui que lit la ligne que le navigateur envoie sur lui-même.** La page le demande au navigateur à chaque ouverture (Brave répond à qui le lui demande, et les navigateurs récents donnent leur marque sur une connexion chiffrée) et le dit au serveur, qui le garde avec l'appareil | Brave envoie exprès la même ligne que Chrome, pour ne pas être reconnu par les sites : la ligne seule ne peut pas le distinguer. La ligne « Connexion » du journal est écrite avant que la page ait pu le dire : elle retient l'appareil, et le nom trouvé ensuite lui est ajouté aussitôt. |
| **Le journal d'activité** | **Une ligne par événement dans la table `activity_log` prévue dès la première migration, gardée le nombre de jours réglé dans les Paramètres (180 par défaut) et purgée chaque nuit avec les sessions oubliées.** Sont écrits : le serveur qui démarre et s'arrête ; une connexion, une connexion refusée, un compte retenu après trop d'erreurs, une déconnexion, un mot de passe changé, un compte créé ou retiré ; chaque visionnage ; chaque tâche terminée, réussie, arrêtée ou en échec ; chaque suppression. Un visionnage est **une seule ligne, écrite quand il finit** : qui, sur quel appareil, quoi, comment il arrivait (méthode), combien de temps il a vraiment joué, où il s'est arrêté, et s'il a été arrêté par un administrateur ; un film ouvert sans que rien n'ait joué n'est pas écrit. Le nom du compte et le titre sont recopiés dans la ligne, pour qu'elle se lise encore après la suppression de l'un ou de l'autre. Une écriture qui échoue est dite dans le journal technique et ne fait jamais échouer ce qu'elle raconte | Le journal technique dit ce que le serveur a fait, pour le déboguer ; celui-ci dit ce que les gens ont fait, pour l'administrateur. Deux lignes par visionnage doublaient la liste sans rien apprendre de plus que la ligne de fin. Rien n'est lu sur le chemin chaud. |
| **À surveiller, calculé et jamais stocké** | **La liste des points à regarder est calculée à chaque demande** : les voyants en défaut du Résumé, les connexions refusées et les tâches en échec des dernières vingt-quatre heures, les conversions qui ne suivent pas en ce moment, les titres qui attendent d'être identifiés. Chaque point mène là où il se règle. **Un administrateur peut marquer comme vus les points nés d'événements ou d'un compte** (connexions refusées, tâches en échec, titres à identifier) : ils se taisent jusqu'à ce que quelque chose de nouveau arrive, un nouvel événement ou un compte plus grand. **Un disque presque plein se marque aussi comme vu** : il se tait tant qu'il reste plein, et reparle s'il se remplit de nouveau après avoir retrouvé de la place. Le panneau du serveur, lui, le montre toujours. Ce qui décrit une vraie panne (dossier introuvable, outil, carte, base, conversion trop lente) ne se cache pas : il part quand c'est réglé. Ce qui a été vu est gardé par administrateur, en base | Un voyant qu'on ne peut pas faire taire finit ignoré, un voyant qu'on fait taire alors que la panne est toujours là ment. La distinction suit ce que le point décrit : un passé qu'on a lu, ou un présent encore à régler. Un disque plein est l'exception demandée par le mainteneur : c'est un état connu, souvent voulu, et pas une panne ; le voir rappelé à chaque ouverture de la cloche le rendait justement ignoré. |
| **La cloche** | **Pour un administrateur, la cloche de la barre du haut compte les points À surveiller et les ouvre en liste, avec « Tout marquer comme vu ».** Redemandée toutes les trente secondes et dès que la page redevient visible. Pour un autre compte, elle reste éteinte et marquée « Bientôt », jusqu'à ce qu'il y ait quelque chose pour lui | Ce qui demande l'attention de l'administrateur doit le trouver où qu'il soit dans l'interface, pas seulement quand il ouvre le Résumé. |
| **Changer son nom d'utilisateur** | **Chacun peut changer le nom avec lequel il se connecte, depuis Mon profil, sans redonner son mot de passe.** Mêmes règles qu'à la création : espaces du bord retirés, jamais vide, et jamais le nom d'un autre compte, majuscules comprises. Les appareils restent connectés, et une ligne du journal dit l'ancien nom et le nouveau. Les lignes déjà écrites gardent le nom de l'époque. Toute page ouverte redemande le compte dès qu'elle revient au premier plan, ce qui porte le nouveau nom (et une nouvelle photo) dans les autres onglets et sur les autres appareils sans recharger | Tout ce qui appartient à un compte y est rattaché par son identifiant, jamais par son nom : le nom n'est qu'une étiquette et le changer ne déplace rien. Le mot de passe n'est pas redemandé parce que le nom ne protège rien : le changer ne donne accès à rien de plus, contrairement au mot de passe, qui déconnecte tout le monde. Le refus d'un nom déjà pris vient de la base elle-même, qui l'interdit déjà, et non d'une vérification faite juste avant : deux renommages au même instant ne peuvent pas passer tous les deux. |
| **La fiche d'une œuvre tient dans l'écran** | **Le haut de la fiche (titre, faits, pistes, boutons, reprise, synopsis, équipe, studios) est limité à la hauteur de la fenêtre sous la barre du haut, et c'est le synopsis qui cède.** S'il ne tient pas, la colonne s'élargit d'abord jusqu'au bord de la page ; s'il ne tient toujours pas, il est coupé sur une ligne entière et « Plus » apparaît. La place est mesurée sur la page affichée, jamais comptée en caractères | Le mainteneur ne veut pas de « Plus » quand il y a la place, et pas de fiche qui oblige à défiler pour lire qui a réalisé le film. Mesurer est la seule façon d'être juste à toutes les tailles d'écran. |
| **Choisir ses pistes avant de lancer** | **La fiche montre les pistes audio et sous-titres du plan de lecture de la copie choisie, et un choix est enregistré comme celui fait dans le lecteur** (même route, même mémoire par œuvre et même préférence de langue). Le lecteur, ouvert ensuite, repart de ce choix sans rien recevoir de plus | Un seul endroit décide des pistes : le serveur. Passer le choix au lecteur à la main aurait fait deux mémoires qui divergent. |
| **La fiche se remet à jour en quittant le lecteur** | **Fermer le lecteur redemande la fiche et son plan sans vider l'écran** : position de reprise, barre de progression, vu ou non, pistes | Le lecteur vit dans la fiche : rien ne se recharge tout seul en le fermant, et la barre de reprise mentirait jusqu'au prochain passage. |
| **Le menu de la fiche est celui des cartes** | **Identifier, Modifier les images, Supprimer et le reste passent dans le menu ⋮ de la fiche, qui est le menu des cartes**, porté par la carte de l'œuvre que le serveur envoie avec la fiche | Un seul menu à tenir, et les marques (vu, favori) posées sur la fiche se voient aussitôt sur toutes les cartes de la même œuvre. |
| **Chapitres de la fiche** | **Une rangée des chapitres que le fichier nomme, chaque carte montrant la vignette du moment tirée des planches déjà faites pour la barre de lecture ; un clic lance la lecture à ce chapitre.** Aucun chapitre inventé à intervalle régulier pour les fichiers qui n'en ont pas | Les planches existent déjà : aucune image de plus à fabriquer. Des chapitres inventés seraient une coupe arbitraire présentée comme celle du film. |
| **Titres similaires : un genre, dit dans le titre** | **Une rangée « Basé sur le genre X » : les œuvres de même sorte (films avec films, séries avec séries) qui portent X, celles qui partagent le plus de genres avec la fiche d'abord, puis les mieux notées.** X est tiré au hasard parmi les genres de l'œuvre qui remplissent une rangée (six œuvres au moins), et à défaut c'est celui qui en a le plus : deux visites d'une même fiche peuvent proposer deux rangées | Le titre dit exactement pourquoi ces cartes sont là. Les genres sont gardés sans ordre de préférence, donc « le premier » ne voudrait rien dire ; le hasard parmi ceux qui remplissent une rangée varie les propositions sans jamais montrer une rangée de deux cartes. |
| **La page d'une personne** | **Chaque personne créditée ouvre une page : photo, dates et lieu de naissance, biographie, et ses œuvres présentes sur le serveur, rangées en films et séries.** La biographie et les dates sont demandées au fournisseur la première fois que la page est ouverte, dans la langue de la bibliothèque (l'anglais à défaut), puis gardées en base. Un fournisseur injoignable n'empêche pas la page : elle montre ce qui est connu et redemandera la fois suivante | Demander à l'avance pour des milliers de personnes que personne n'ouvrira coûterait des heures d'appels au fournisseur pour rien. La première ouverture attend une fois, les suivantes sont instantanées. |
| **Pas de mention du fournisseur sur les fiches** | **Le pied de page qui cite le fournisseur n'est plus dessiné sur la fiche d'une œuvre ni sur celle d'une personne** ; il reste sur l'accueil et les grilles | Demande du mainteneur : la fiche est un écran de lecture, la mention y était du bruit. La citation reste visible dans l'interface. |
| **Revenir en arrière retrouve la page où on l'a laissée** | **Chaque page de l'historique garde sa place : la hauteur de défilement et la position de chacune de ses rangées.** En revenant (précédent, Échap), la place est redemandée à chaque image jusqu'à être atteinte et que la page ait cessé de bouger, pendant au plus huit secondes, et le moindre geste de la personne l'emporte. Une page nouvelle s'ouvre en haut ; une page qui ne fait que réécrire sa propre adresse ne bouge pas. Gardé en mémoire pour la durée de l'onglet, soixante pages au plus | L'interface défile dans une boîte à elle et non dans la fenêtre, donc le navigateur, qui retient la place des pages qu'il fait défiler lui-même, ne retenait rien : chaque retour tombait en haut. Redemander à chaque image plutôt que sauter une fois, parce qu'une page revient vide et se remplit en parlant au serveur, et qu'une grille ne tient d'abord que ses premières cartes : descendre vers la place fait charger les suivantes jusqu'à l'atteindre. |
| **La bande-annonce s'ouvre dans une fenêtre** | **Le bouton Bande-annonce ouvre une fenêtre par-dessus la fiche, sans la quitter.** Une bande-annonce YouTube ou Vimeo y est jouée par le lecteur officiel que le site propose d'intégrer, avec toute son interface ; une bande-annonce posée à côté du film y est jouée par le navigateur, avec ses commandes. Un lien vers un autre site s'ouvre à part. Le serveur ne va chercher aucune vidéo | Essayé d'abord : piloter le lecteur YouTube avec les commandes de Melyxar et masquer le sien. YouTube dessine ses propres commandes dans son cadre quoi qu'on lui dise, et une page n'a pas le droit de toucher au cadre d'un autre site ; masquer ce qui était au milieu de l'image aurait masqué l'image. Le mainteneur préfère garder le lecteur de YouTube entier, dans une fenêtre à lui, comme il l'a fait sur son propre site. |
| **Une page revient telle qu'on l'a laissée, d'un coup** | **Ce que chaque écran a reçu du serveur est gardé en mémoire pour l'onglet (quarante écrans au plus), sous le nom de ce qu'il a demandé** : l'accueil, une fiche et son plan de lecture, une personne, une grille avec toutes les cartes déjà lues. Un écran qui retrouve son nom se dessine aussitôt avec, dès sa première image, à la bonne place, puis redemande quand même au serveur et se met à jour sans rien vider. Une grille est relue discrètement aussi loin qu'elle l'avait été et remplacée d'un coup si personne n'a lu plus loin entre-temps. La bannière de l'accueil fait partie de la visite : même tirage, même affiche et même arrêt au retour d'une fiche ouverte depuis elle ; une nouvelle visite de l'accueil tire à nouveau. Tout est oublié quand le compte change | Relevé par le mainteneur : au retour, la page se montrait en train de charger, les sections apparaissaient puis la page sautait à sa place. Un écran vide suivi d'un saut n'est pas une transition. Redemander quand même garde la règle que l'interface montre toujours l'état réel. |
| **L'onglet dit ce qui est en lecture** | **Pendant une lecture, l'onglet porte le nom de ce qui est lu** : le titre d'un film, la série suivie de la saison et de l'épisode pour un épisode, dits comme le lecteur les dit. Le reste du temps, et dès que le lecteur se ferme, l'onglet porte le nom du serveur choisi par l'administrateur | Plusieurs onglets ouverts se distinguent au premier coup d'œil, et la barre des tâches dit ce qui passe. |
| **Melyxar s'installe comme une application** | **Le navigateur peut installer Melyxar (ordinateur et téléphone) grâce à un manifeste servi par le serveur, ouvert à tous comme la page elle-même.** L'application porte le nom du serveur choisi par l'administrateur, relu à chaque demande du manifeste. L'icône de l'application est dessinée par le serveur dans la couleur du logo de la personne, avec le même relief et le même mélange que l'icône de l'onglet ; l'adresse du manifeste porte cette couleur et celle du fond, lues dans les jetons du thème, et change avec l'accent. Deux formes : le logo seul sur fond transparent, et le logo resserré au centre d'un carré du fond de l'application pour les systèmes qui découpent l'icône (Android, iPhone). Le fond de l'icône et de l'écran de démarrage est toujours le fond sombre, quel que soit le thème | Un manifeste écrit une fois pour toutes ne peut porter qu'une couleur, et l'accent se change par compte. Le navigateur va chercher le manifeste et les icônes sans le cookie de session : la couleur voyage donc dans l'adresse plutôt que d'être lue sur le compte. Dessiner côté serveur plutôt que dans la page, parce que le système d'exploitation garde une adresse d'icône, pas une image calculée par un onglet. Le fond fixe évite qu'une icône installée change à la tombée de la nuit avec le thème du système. Une application déjà installée garde l'icône qu'elle avait : chaque navigateur la met à jour à son propre rythme, parfois en demandant d'abord. |
| **Le nom et le logo du serveur se changent depuis l'administration** | **L'administrateur renomme le serveur et lui donne un logo dans Réglages, Serveur.** Le nom n'est envoyé qu'au bouton Enregistrer, et un message confirme qu'il est gardé ; un second bouton rend au serveur le nom qu'il avait en arrivant. Le nom est vérifié par le moteur (ni vide, ni plus de quinze caractères, espaces compris) et enregistré seul, sans réécrire le reste des réglages. Le logo sert aussi d'icône à l'onglet et à l'application installée : deux icônes carrées en sont tirées, le logo entier sur fond transparent, et le logo resserré pour tenir dans le rond qu'un téléphone découpe, posé sur le fond de l'application ; faites à la première demande à partir du logo gardé, et servies sous une adresse qui porte le nom du logo, si bien qu'un nouveau logo est une nouvelle adresse que le navigateur et l'application installée vont chercher. Le titre des pages d'administration, qui monte dans la bande de la barre du haut, se pousse à droite du nom et du logo quand ils sont longs. Le nom et le logo remplacent ceux de Melyxar dans la barre du haut et sur l'écran de connexion ; sans logo, c'est la marque de Melyxar dans l'accent qui reste. Le logo est reconnu à ce qu'il contient comme une photo de profil, gardé entier dans sa forme et avec sa transparence, ramené à cinq cent douze points au plus sur son grand côté, écrit en WebP dans le dossier des envois et servi à tous, puisque l'écran de connexion le montre ; l'ancien est effacé. Dans le navigateur qui les a changés, la barre du haut, l'onglet, le résumé de l'administration et le coin du lecteur prennent le nouveau nom et le nouveau logo aussitôt ; les autres navigateurs le prennent au prochain chargement de la page, et l'application installée à la prochaine relecture de son manifeste | Un appel à lui seul, comme les autres réglages d'un seul champ, pour qu'un écran ouvert depuis longtemps n'écrase pas ce qu'un autre a changé entre-temps. Quinze caractères : le nom tient dans la barre du haut à côté du logo et de la flèche retour sans déborder sur la page, et sous une icône d'application sans être coupé. Avec la flèche retour, le morceau de gauche de la barre prend sa place sur la marge de l'écran plutôt que sur la page. Un logo n'est jamais recadré, contrairement à une photo de profil : il est dessiné sur le fond de la page, souvent plus large que haut. |
| **Saisons et épisodes sont des cartes comme les autres** | **Ce qui pend sous une série ou une saison est envoyé comme la carte que dessine toute rangée** (mêmes images, mêmes marques du spectateur, même image large pour un épisode), accompagnée de ce que sa place y ajoute : son numéro, son nom propre, son résumé dans la langue de la bibliothèque et le nombre de ce qu'elle contient. La fiche d'une série montre ses saisons en rangée de cartes ; celle d'une saison, ses épisodes en liste, chaque image à côté du nom, de la note, de la durée et du début du résumé ; celle d'un épisode, son image couchée et, dessous, la rangée de tous les épisodes de sa saison, ouverte sur celui-ci, qui est cerclé de l'accent. Ces épisodes voisins voyagent avec la fiche de l'épisode, et le lecteur s'en sert aussi | Une saison ou un épisode dessinés à part avaient leur propre survol et leur propre allure, différents du reste de l'interface. Une seule carte, c'est un seul survol, un seul menu et une seule façon de marquer vu ou favori, partout. Envoyer les voisins avec la fiche évite au lecteur une seconde demande et à la page un morceau qui arrive en retard. |
| **Les comptes se gèrent depuis l'administration** | **La page Utilisateurs liste chaque compte (rôle, médiathèques, appareils connectés, dernière activité) et permet de le créer, de le renommer, de lui donner ses droits, de lui mettre un mot de passe, de le déconnecter de partout et de le supprimer.** Un administrateur a toujours tous les droits et voit toutes les médiathèques, quoi qu'on demande : le moteur le ramène à cette forme. Supprimer du disque ne va jamais sans retirer de la médiathèque. Une médiathèque accordée qui n'existe pas est refusée plutôt qu'ignorée. Le serveur n'est jamais laissé sans administrateur : la vérification se fait dans la même transaction que l'écriture, donc deux administrateurs qui se retirent l'un l'autre au même instant ne passent pas tous les deux. Depuis cette page, un administrateur ne peut rien défaire de son propre compte : ni se rétrograder, ni se supprimer, ni se déconnecter de partout, ni se mettre un mot de passe sans donner l'ancien, qui se change depuis son profil. Chaque changement de droits et chaque déconnexion forcée est une ligne du journal, avec le nom de l'administrateur qui l'a fait | Un administrateur privé d'une médiathèque la lirait quand même dans l'administration, qui montre tout le serveur : une limite qui n'en est pas une est pire que pas de limite, parce qu'on s'y fie. Refuser les gestes sur soi-même évite deux pièges : l'administrateur qui se retire l'écran sur lequel il est, et la session restée ouverte sur une machine prêtée qui suffirait à voler le compte en changeant son mot de passe sans l'ancien. |
| **Un droit retiré l'est tout de suite** | **Les droits d'un compte sont relus en base à chaque requête, aucun n'est gardé en mémoire.** En plus, retirer des droits à un compte, le déconnecter de partout ou le supprimer arrête ses lectures en cours et ferme ses conversions, comme l'arrêt d'une lecture par l'administrateur ; un administrateur rétrogradé perd aussitôt la ligne en direct de l'administration | Une requête sur deux relue suffirait pour les pages, mais une lecture déjà lancée ne redemande rien à la médiathèque : sans l'arrêt, un film d'une médiathèque retirée se regarderait jusqu'au bout. |
| **Tout ce qui sert un film vérifie sa médiathèque** | **Le fichier lu directement, les sous-titres, les planches de vignettes, le film de calibration du lecteur, la page suivante d'une grille, la mémoire des pistes et le signal « en lecture » vérifient que le compte a accès à la médiathèque de l'œuvre**, et répondent comme pour une œuvre qui n'existe pas. Les planches de vignettes ne sont plus gardées par les caches partagés | Ces chemins partent d'un identifiant de fichier et non d'une œuvre : ils avaient échappé au filtre des grilles et des fiches. Un compte privé d'une médiathèque qui gardait d'anciens liens pouvait encore y lire un film entier. |
| **Chemins et dossiers réservés à l'administrateur** | **Le chemin complet d'une copie, le disque où elle se trouve et les dossiers d'une médiathèque ne sont envoyés qu'à un administrateur.** Les boutons qui agissent sur une copie (réanalyser, détacher) ne sont montrés qu'à lui | Appliqué ici, alors que la décision « Chemin et taille du fichier » l'annonçait déjà : la fiche les envoyait à tout le monde. |
| **Lectures simultanées** | **Un compte peut être limité à un nombre de lectures en même temps, de une à vingt, compté sur ses appareils en train de lire.** Lancer une lecture de trop est refusé avec un message qui le dit ; reprendre le film sur l'appareil qui le lit déjà ne compte pas deux fois. Sans limite par défaut, et jamais pour un administrateur | La lecture directe n'ouvre aucune conversion, donc la limite ne peut pas se compter sur les conversions : elle se compte sur ce que le serveur sait être en lecture. |
| **Téléchargement et limite d'âge : dessinés, pas branchés** | **Sur la page Utilisateurs, le droit de télécharger et la limite d'âge restent affichés, désactivés et marqués « Bientôt ».** Il n'existe pas encore de fonction de téléchargement, et la limite d'âge est reportée (voir plus haut) | Un interrupteur qui ne fait rien serait un droit auquel l'administrateur croirait. |
| **Une session par navigateur** | **Chaque navigateur envoie à la connexion l'identifiant qu'il s'est donné une fois pour toutes (le même qui sert déjà à sa calibration), et une nouvelle connexion du même compte sur le même navigateur remplace la session précédente au lieu de s'y ajouter.** Un navigateur qui a perdu son stockage s'invente un nouvel identifiant et compte comme un nouvel appareil. L'identifiant ne donne aucun droit : il ne sert qu'à retrouver la session d'avant du même compte, et un identifiant qui n'en a pas la forme est ignoré | Sans lui, se connecter dix fois depuis le même navigateur laissait dix sessions vivantes, dont neuf que personne ne détenait plus, et la liste des appareils aurait montré le même navigateur dix fois. C'est ce que font les autres serveurs du genre. |
| **La page Appareils** | **L'administration liste chaque appareil connecté, tous comptes confondus : le navigateur et le système, le compte, depuis quand, la dernière activité, et si la session s'arrête à la fermeture du navigateur.** Un appareil se déconnecte seul, sans toucher aux autres du même compte ; ce qu'il était en train de lire s'arrête. Chacun voit aussi ses propres appareils dans son profil et peut déconnecter les autres, par exemple un téléphone perdu, sans passer par l'administrateur. Un bouton du profil déconnecte d'un coup tous ses appareils sauf celui d'où l'on clique, pour faire le ménage sans les passer un par un. L'appareil sur lequel on regarde la page est signalé et ne se déconnecte pas depuis la liste : c'est le bouton de déconnexion. Chaque déconnexion d'un appareil est une ligne du journal | « Déconnecter partout » punit tous les appareils d'une personne pour un seul perdu. La dernière activité affichée peut retarder d'une heure, puisqu'elle n'est réécrite qu'une fois par heure (voir « Une session est un appareil »). |
| **Durée des sauts du lecteur, au choix de chacun** | **Deux réglages par compte, un pour reculer et un pour avancer, choisis parmi 5, 10, 15, 20, 25 et 30 secondes, ou tapés à la main (« Personnalisé ») jusqu'à 90 secondes.** Dix secondes en arrière et trente en avant par défaut, comme Jellyfin ; un compte resté sur les dix secondes d'origine en avant passe à trente. Les boutons du lecteur écrivent la durée choisie dans leur flèche, et les flèches gauche et droite du clavier sautent de la même durée. Le serveur ramène toute autre valeur entre 1 et 90 secondes | On recule pour réentendre une réplique et on avance pour passer un générique : une seule durée sert mal les deux. Réglé sur le compte plutôt que dans le navigateur, parce que c'est une habitude de la personne et non de l'écran. Deux chiffres au plus, parce que la durée est écrite dans l'icône. |
| **Le fond de la page de connexion se règle dans l'administration** | **Dans Paramètres, l'administrateur choisit le fond dessiné (lumière ou étagère) et peut poser une image à la place.** L'image envoyée est redressée, ramenée à 2560 pixels de large au plus sans jamais être agrandie, et gardée en WebP dans les fichiers déposés, servie par la même route publique que le logo. Une image posée gagne sur le fond dessiné, qui reste choisi en dessous pour le jour où l'image est retirée ; l'ancienne image est effacée quand une autre la remplace | Les colonnes existaient et l'écran de connexion les lisait déjà (voir « La porte porte le serveur, pas Melyxar ») ; il ne manquait que de pouvoir les écrire. La même route que le logo parce que c'est la même chose : un fichier déposé par l'administrateur, visible avant toute connexion, au nom qui change avec son contenu. |
| **Le slogan de la page de connexion se règle** | **Dans le panneau « Écran de connexion » de l'administration, un champ remplace la phrase au pied de la carte, 80 caractères au plus.** Vide, c'est celle de Melyxar qui s'affiche, traduite dans la langue de la personne qui regarde ; écrit, il s'affiche tel quel, dans toutes les langues | Oublié quand la porte a été rebranchée sur les réglages du serveur (voir « La porte porte le serveur, pas Melyxar ») : c'était le dernier texte de l'écran encore propre au projet. Une phrase écrite par l'administrateur n'a qu'une langue, la sienne ; la laisser vide garde la traduction. |
| **Le HDR gardé tel quel sur un écran qui l'affiche** | **Le lecteur demande au navigateur si l'écran est en mode HDR et, codec par codec, s'il décode et affiche l'image HDR (courbe PQ, celle du HDR10, et courbe HLG), lu en fichier entier comme en morceaux. Le serveur garde alors le film en HDR au lieu de le convertir.** Quatre règles, dans cet ordre : le Dolby Vision sans couche de base compatible (profil 5) est **toujours** converti, pour tout écran ; l'interrupteur général du serveur « ne jamais convertir » garde son sens ; une image que le serveur refait **pour une autre raison** (codec non lu, qualité réduite, sous-titres incrustés, entrelacement) est convertie, parce qu'une image refaite sort en 8 bits et ne peut pas rester en HDR ; sinon, c'est le choix du spectateur qui décide. Ce choix est un **réglage par compte** dans Mes réglages, Lecture : « Automatique » par défaut (garder le HDR si l'écran l'affiche, convertir sinon), « Toujours convertir » et « Ne jamais convertir ». **Un interrupteur dans le lecteur** le contredit pour la lecture en cours seulement, sans rien retenir. Un Dolby Vision d'un autre profil n'est gardé que sur un écran qui affiche les deux courbes, faute de savoir laquelle porte sa couche de base | La règle d'origine convertissait tout, pour tout le monde, parce que les navigateurs sous Linux affichent mal le HDR. Les PC du mainteneur sont sous Windows, où Chrome, Edge et Brave l'affichent correctement une fois le HDR activé : tout y était converti pour rien, en perdant la qualité du film et en faisant travailler la machine. Demander au navigateur plutôt que deviner d'après son nom est la règle de toute la lecture. En passant, le profil 5 n'était protégé que par l'hypothèse qu'aucun écran n'affiche le HDR : sur un écran déclaré HDR il serait parti tel quel, vert et violet. |
| **Le mode des sous-titres, par compte** | **Un réglage dans Mes réglages, Sous-titres, décide des sous-titres d'un film que personne n'a encore réglé** : « Toujours » (sous-titres complets dans la langue lue, sinon les forcés), « Intelligent » (complets seulement quand le film est entendu dans une autre langue que celle lue, sinon les forcés), « Seulement les forcés », « Comme le fichier l'indique » (la piste que le fichier marque par défaut, sinon comme « Intelligent ») et « Aucun ». « Toujours » par défaut, ce que chaque compte avait déjà. Les **forcés** sont les quelques lignes qu'un film ne dit pas dans la langue de sa bande son (un panneau, une scène dans une autre langue) : cherchés d'abord dans la langue entendue, pour laquelle ils sont faits, puis dans la langue lue. Une piste est prise pour forcée quand le fichier la marque ainsi **ou quand son titre le dit** (« Forced », « Forcés », avec ou sans accents), comme pour les sous-titres rangés à côté du film : beaucoup de fichiers ne le disent que là. Les fichiers déjà analysés le sont à la prochaine réanalyse. Parmi les complets, une piste pour malentendants ne passe qu'à défaut d'une ordinaire. **Ce qui est choisi dans un film gagne sur le mode**, y compris « désactivé », retenu pour ce film seulement ; la langue lue n'est plus effacée quand on coupe les sous-titres, puisque c'est désormais le mode qui dit s'il en faut. Le lecteur dit au serveur qu'il a coupé les sous-titres, au lieu de ne rien dire | Demandé par un proche du mainteneur, sur le modèle de Jellyfin, surtout pour les forcés : un film doublé en français dont une scène est en russe doit afficher la traduction de cette scène sans que personne ait à y penser. Avant, couper les sous-titres d'un film effaçait la langue préférée pour tous les films, seule façon de dire « pas de sous-titres » ; avec un mode, cette façon ferait disparaître aussi les forcés partout. Et le lecteur disait « pas de sous-titres » en ne nommant aucune piste, ce qui voulait aussi dire « au serveur de choisir » : avec un mode, le serveur en aurait remis une. |
| **L'ordre de l'accueil, par compte** | **Dans Mes réglages, Accueil, « Ordre de l'accueil » range les sections sous la bannière et permet d'en masquer** : raccourcis des médiathèques, continuer la lecture, à suivre, **une rangée d'ajouts récents par médiathèque**, chacune rangée et masquée à part, et récemment ajoutés. Seules les médiathèques que le compte possède sont proposées ; les autres gardent leur place dans l'ordre, pour le jour où elles arrivent. « Ordre des médiathèques » (l'ancien « Ordre de l'accueil », renommé) ne range plus que les tuiles des raccourcis. La bannière ne fait pas partie des sections : elle garde sa place et son interrupteur. Par défaut : raccourcis, continuer la lecture, à suivre, les rangées des médiathèques (Films, Séries, Animés, Perso), puis récemment ajoutés ; et Films, Séries, Animés, Perso pour les tuiles. Un compte resté sur le premier ordre passe au nouveau, un compte qui a choisi le sien le garde, sa section unique des rangées devenant une section par médiathèque à la même place, dans l'ordre de ses médiathèques. Une section masquée garde sa place dans la liste, pour revenir au même endroit. Le serveur dit à la page quelles sections dessiner et dans quel ordre, mais continue d'envoyer toutes les rangées, parce que la bannière est faite de ce qui a été laissé en cours et de ce qui vient d'arriver. « Continuer la lecture » et « À suivre » partagent une ligne seulement quand elles se suivent. **Les deux listes se rangent par glisser-déposer** : à la souris n'importe où sur la ligne, au doigt par la poignée (le reste de la ligne doit laisser défiler la page), au clavier par les flèches sur la poignée. Les autres lignes s'écartent pendant qu'on glisse, et la ligne lâchée glisse jusqu'à sa place. Écrit à la main plutôt qu'avec une bibliothèque : une centaine de lignes, et aucune dépendance de plus dans l'interface | Demandé par le mainteneur, qui voulait pouvoir masquer la rangée d'une seule médiathèque. Les flèches monter et descendre obligeaient à cliquer autant de fois qu'il y avait de places à franchir. Les rangées rangées par l'ordre de l'accueil, les tuiles par celui des médiathèques : deux réglages qui ne rangent jamais la même chose ne peuvent pas se contredire. |
| **La reprise d'un film arrêté en cours, par compte** | **Dans Mes réglages, Lecture, « Reprise de la lecture »** : un **retour en arrière à la reprise** (aucun par défaut, ou les mêmes durées que les sauts), retiré du point de reprise par le serveur, jamais sous le début ; et trois règles à la manière de Jellyfin, appliquées par le serveur à chaque position reçue. En dessous du **pourcentage minimum** (5 % par défaut), le film compte comme non commencé et sa position revient au début ; à partir du **pourcentage maximum** (90 %, le seuil d'avant), ou à la fin, il compte comme vu ; une vidéo plus courte que le **temps de reprise minimum** (120 secondes) ne se reprend jamais et compte comme vue passé le minimum. Un interrupteur sous ces règles les rend **séparées par type de médiathèque** : chaque type part des règles communes jusqu'à ce qu'on lui en donne. Les règles sont bornées pour ne jamais se croiser : le minimum va de 0 à 50 %, le maximum de 50 à 100 %, le temps de 0 à une heure. Une marque « vu » posée à la main gagne toujours | Demandé par le mainteneur sur le modèle de Jellyfin. Le seuil unique de 90 % mettait dans « Continuer la lecture » un film lancé par erreur et coupé après dix secondes, et ne distinguait pas un clip perso de deux minutes d'un film de trois heures. Décidé côté serveur plutôt que dans la page, pour que l'accueil, les cartes et la fiche disent la même chose quel que soit l'écran qui a envoyé la position. |
| **Vu à la main et point de reprise** | **Marquer vu efface le point de reprise ; marquer non vu le garde.** Un film vu puis relancé jusqu'au quart reste vu et garde sa barre de reprise, et il apparaît dans « Continuer la lecture ». Le marquer non vu ne change rien à la barre ni à la reprise, il repasse seulement « en cours ». Le marquer vu ensuite fait disparaître la barre, partout. Un film compté vu par les règles (à la fin ou passé le pourcentage maximum) lâche lui aussi sa position. **« Continuer la lecture » est donc ce qui a un point de reprise**, vu ou non, et la carte, la fiche, l'accueil et la liste des épisodes lisent tous ce même point | Demandé par le mainteneur : marquer non vu faisait disparaître la barre et marquer vu la faisait revenir, soit l'inverse de ce qu'on attend. Dire qu'on n'a pas vu un film ne ramène personne au début, et le marquer vu dit qu'il n'y a plus rien à reprendre. Comme dans Jellyfin, « vu » et « où j'en suis » sont deux choses distinctes. Les positions laissées par des films comptés vus avant cette règle sont remises au début à la migration. |
| **Les sagas sur la fiche d'un film** | **Un film qui appartient à une saga montre, juste au-dessus de la rangée « Basé sur le genre », une rangée au nom de la saga avec tous ses films présents sur le serveur et accessibles au compte**, le film de la page compris, entouré, la rangée ouverte sur lui ; dans l'ordre de sortie. Pas de rangée pour un film seul de sa saga ici. Les sagas sont celles du fournisseur (TMDB), qui les découpe finement : « Iron Man », « Avengers », pas un univers entier | Les sagas étaient déjà enregistrées à l'identification et ne s'affichaient nulle part. Placées avant les genres parce que les films qui précèdent et suivent celui-ci en sont plus proches que tout ce qui partage un genre. |
| **Les films qui partagent les personnages d'une saga** | **La rangée de la saga continue, après ses propres films, avec les films où reviennent ses personnages principaux, joués par le même acteur**, du plus présent au moins présent. Personnages principaux : les cinq premiers du générique de chaque film de la saga, et un personnage compte d'autant plus qu'il est haut dans le générique et présent dans plusieurs films de la saga. Un film apparenté compte d'autant plus que ces personnages y sont haut dans le générique. Deux noms de personnage désignent le même quand tous les mots de l'un se retrouvent dans l'autre, alias par alias (« Thor » et « Thor Odinson »), accents et majuscules mis de côté ; « lui-même » et « narrateur » ne relient jamais rien. Films seulement, vingt au plus. **Une saga dont un seul film est sur le serveur n'a pas de rangée**, quoi qu'elle relie. **Un film sans saga** a la sienne, intitulée « Avec les mêmes personnages », faite des films où reviennent ses propres personnages principaux, lui-même exclu | Demandé par le mainteneur : le fournisseur découpe l'univers Marvel en petites sagas (« Thor », « Avengers »), et un film de Thor doit mener aux Avengers où Thor revient. Une logique plutôt qu'une liste, pour que toutes les sagas en profitent, et les films sans saga aussi : un film à part dont l'héroïne revient dans les films d'équipe y mène de la même façon. Une rangée au nom d'une saga qui n'y montre qu'un de ses films ne ressemble pas à une saga, d'où le seuil de deux. Le même acteur **et** le même personnage, parce que l'acteur seul relierait toute sa filmographie, et le personnage seul confondrait deux « John » sans rapport. |
| **La surveillance en temps réel des médiathèques** | **Un interrupteur par médiathèque, dans son panneau de l'administration, décoché par défaut. Coché, le serveur surveille ses dossiers (le mécanisme de surveillance du noyau Linux) et, dès qu'un fichier est ajouté, déplacé, renommé ou supprimé, relance le scan ordinaire de cette médiathèque, une fois le calme revenu.** Le calme, c'est dix secondes sans aucun changement dans la médiathèque et des fichiers touchés dont la taille ne bouge plus : un film en cours de copie écrit sans arrêt, il n'est donc pris qu'une fois la copie finie, comme le fait Jellyfin. Pas de scan partiel : le scan ordinaire sait déjà reconnaître un nouveau fichier, un déplacement, une disparition, analyser et identifier, et un second chemin qui le referait à moitié serait deux vérités à tenir. Un scan déjà en cours n'est pas doublé : le changement attend qu'il finisse et en relance un. Les fichiers et dossiers cachés sont ignorés. Quand la surveillance est impossible (le système refuse d'en surveiller davantage, dossier absent), le panneau le dit avec la raison et la façon d'y remédier, et le serveur réessaie de lui-même | Demandé par le mainteneur, à l'image de l'option « Activer la surveillance en temps réel » de Jellyfin. Jellyfin et Emby la font marcher dans le même genre de conteneur non privilégié : la surveillance du noyau fonctionne sur des disques montés dans le conteneur. Sa seule limite réelle est le nombre de dossiers surveillés par utilisateur, qui se règle sur l'hôte Proxmox si une grande collection le dépasse. |

## Environnement de production

- Hôte Proxmox : Ryzen 7 3700X (8 cœurs, 16 threads), 32 Go DDR4, Intel Arc A380, NVMe. Noyau hôte `7.0.14-12-pve`.
- LXC Melyxar : Debian 13, **non privilégié**, 12 threads, 16 Go, 100 Go sur NVMe.
- Médias : quatre disques montés dans le LXC sous `/mnt/`, un dossier par disque, chacun contenant des dossiers `Films`, `Séries`, `Animés`, `Émissions`. Une bibliothèque regroupe donc les quatre dossiers de même nom. Les dossiers sont lisibles par tous les utilisateurs (droits `rwxrwxr-x`), la lecture ne demande donc aucun alignement d'identifiant. Une écriture future (fichiers annexes, suppression) demanderait que l'utilisateur `melyxar` appartienne au groupe propriétaire des dossiers. Les chemins réels vivent dans la configuration du serveur, jamais dans le dépôt.
- Films posés à plat dans leur dossier, sans sous-dossier par film.
- Bibliothèque de test : le dossier `Films` existant, environ 50 films.
- Première cible client : Brave / Chromium sous Windows, en réseau local.
- Le mainteneur ne lit pas le code : les journaux, la commande de diagnostic et la page de diagnostic sont conçus pour lui.

## Règles de travail

- **Langue du code : anglais.** Noms de crates, modules, types, fonctions, variables, tables et colonnes, routes de l'API, messages de commit, commentaires dans le code, journaux techniques : tout suit les standards anglais habituels.
- **Langue de tout le reste : français.** Documentation, explications, revues, décisions, échanges avec le mainteneur.
- Le em dash est banni de tout texte du projet.
- Textes d'interface toujours passés par l'internationalisation, anglais d'abord, français ensuite.
- Tout journal de débogage est protégé par un contrôle de type `BuildConfig.DEBUG` ou équivalent Rust (`cfg(debug_assertions)`).
- Pas de code mort, pas de contournement temporaire, pas de commentaire inutile.
- **Tout se fait depuis l'interface web.** Ni l'administrateur ni le spectateur ne doivent avoir à ouvrir un terminal pour faire marcher le serveur : lancer un scan, corriger une fiche, changer un réglage, voir ce qui tourne. Les commandes en ligne existent pour le diagnostic et pour le mainteneur qui débogue, jamais comme seul chemin vers une fonction.
- **Une panne se lit sur l'écran qui l'a provoquée.** Un travail qui échoue écrit sa raison, la fiche d'un film dit pourquoi il n'a pas de nom, un bouton refusé affiche le refus, et un seul bouton copie le rapport complet de l'installation. Chercher la cause dans un journal est le dernier recours du mainteneur, jamais le chemin normal.
- **Rien de long ne se lance sans se montrer.** Un bouton qui déclenche un travail de plusieurs minutes affiche ce travail et sa progression, et la page se remplit d'elle-même quand il finit. Un bouton qui ne montre rien est indiscernable d'un bouton cassé : on le presse une deuxième fois, puis on va voir dans un terminal.
- **Personne ne recharge jamais la page à la main.** Tout ce qui change côté serveur se voit tout seul sur l'écran ouvert : la position reprise dès qu'on quitte un film, la fiche corrigée dès qu'elle est identifiée, le réglage enregistré, la ligne de travail qui avance, la bibliothèque qui grossit pendant un scan. Une action faite dans l'interface met à jour tout de suite tous les endroits de l'interface qui la montrent, y compris la page d'où elle est partie et celles qu'on retrouve en revenant en arrière. Aucun écran n'a le droit d'afficher un état périmé en attendant un F5 : si une donnée peut changer pendant qu'on regarde, l'écran qui l'affiche sait la redemander ou se la fait pousser. C'est la raison d'être de l'interface en TypeScript plutôt que de pages rendues une fois pour toutes.
